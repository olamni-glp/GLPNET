# Phase 0 Research — `/D2NET-init` Skill Wrapper

**Feature**: `006-d2net-init-skill` — see [spec.md](spec.md) and [plan.md](plan.md)

The feature is small and self-contained: a single `SKILL.md` file under `.claude/skills/D2NET-init/` whose body procedurally instructs Claude how to wrap the existing `d2net-init` binary. All three clarifications are resolved (offer-build with single confirmation, JSON outputs bypass truncation, single-token shortcut). No `NEEDS CLARIFICATION` markers remain.

This document records the technology / convention decisions the spec leaves to plan time.

---

## R1 — Skill file format and frontmatter

**Decision**: Match the convention established by the existing `.claude/skills/speckit-*` skills (which were generated by GitHub's spec-kit and serve as the proven reference). Frontmatter keys: `name`, `description`, `argument-hint`, `compatibility`, `metadata` (with `author` and `source`), `user-invocable: true`, `disable-model-invocation: false`. The body is markdown with named sections (User Input, Pre-Execution Checks, Outline, Post-Execution Checks).

**Concrete shape** for `.claude/skills/D2NET-init/SKILL.md`:

```yaml
---
name: "D2NET-init"
description: "Wrap the d2net-init CLI as a Claude Code skill: locate the binary, derive flags from natural-language or pass-through, confirm before destructive operations, run, and surface results."
argument-hint: "Describe the action (e.g. 'init for glp_runtime', 'list', 'force rebuild') or pass --flag args verbatim. Empty input shows --help."
compatibility: "Requires tools/d2net/src/D2Net.Init/ in the repo and a built or buildable d2net-init binary. Node.js >= 20 required at runtime (the binary's PGLite bridge subprocess)."
metadata:
  author: "GLPNET"
  source: "specs/006-d2net-init-skill/spec.md"
user-invocable: true
disable-model-invocation: false
---
```

**Rationale**:
- Reusing the spec-kit convention means Claude Code's loader recognises the skill without any infrastructure changes.
- `user-invocable: true` is required so `/D2NET-init` is bindable as a slash command.
- `disable-model-invocation: false` keeps the option open for the model to invoke this skill autonomously when relevant (low risk because the skill always confirms destructive operations).
- Casing of `name` matches the user's literal request `D2NET-init` and the directory path.

**Alternatives considered (rejected)**:
- Inventing a new skill format: the spec-kit format is in production use across 14 sibling skills in this repo; deviating gains nothing.
- Splitting into multiple skills (`/D2NET-init`, `/D2NET-list`, `/D2NET-force-rebuild`, …): more files, fragmented UX. The spec is explicit that one skill covers init + inspection.

## R2 — Skill body procedural shape

**Decision**: The body of `SKILL.md` is a procedural script Claude follows at invocation time, structured as numbered steps. Sections in order:

1. **User Input block** — repeats the standard `$ARGUMENTS` pattern (matches sibling skills).
2. **Pre-flight: locate the binary** — implements FR-004's three-step search (Release → Debug → `dotnet run` fallback). On miss, follow FR-006 build-confirmation flow.
3. **Pre-flight: detect stale binary** — compare `bin/<config>/net8.0/d2net-init.exe` mtime against the newest `.cs` file under `tools/d2net/src/D2Net.Init/`. If stale, run FR-006 build-confirmation flow.
4. **Parse user intent** — three branches per FR-008/FR-009/FR-010/FR-011: (a) empty/`help` → `--help`; (b) all tokens flag-style → pass-through + `--non-interactive`; (c) natural-language with key-value or verbs or single-token shortcut → derive flags.
5. **Single-token shortcut handling** (FR-009 sub-bullet): when input is one bare token AND `<token>/` exists as a direct subdirectory of CWD AND token is not a verb, derive `--source <token> --target-extension _net --target <token>_net`, confirm, then proceed.
6. **Destructive-operation gate (FR-012/FR-013/FR-014)** — scan input for the closed marker word list OR the literal `--FORCE --DELETE-EXISTING` pair; if matched, emit confirmation prompt naming the absolute path, wait for affirmative reply, record the path in a session-scoped "confirmed destructive" set so subsequent invocations against the same path don't re-prompt.
7. **Augment with `--non-interactive` and `--accept-suggested-exclusions`** per FR-007 if absent.
8. **Invoke** the binary via Bash tool.
9. **Surface results** per FR-015/FR-017/FR-018 — distinguish JSON vs plain-text output, apply 50-line truncation only to plain text, surface stderr verbatim on non-zero exit.
10. **Recap on success-init** — extract workspace path, dart-file count, bridge port from the binary's stdout summary, append a brief Claude-side recap.
11. **Hint pass-through** — for `BridgePortInUse` (5), suggest `--bridge-port <next>`; for `DbOpenFailed` (8) with `pglite_init_failed`, surface the recovery hint without auto-running `--FORCE --DELETE-EXISTING`.

**Rationale**:
- Numbered procedural shape mirrors the speckit skills, which Claude has been observed to execute reliably.
- Front-loading the pre-flight checks (binary discovery + staleness) means failure modes surface before the destructive-operation gate, so a user who needs to build first sees the build prompt before the destructive prompt — fewer round-trips.

**Alternatives considered (rejected)**:
- Free-form prose body: less reliable; the speckit skills explicitly use numbered procedure and Claude Code's evaluation has bear that out.
- Embedding code/scripts directly: skills are model-driven, not script-driven; calling the Bash tool from within the procedure is the right primitive.

## R3 — Stale-binary detection mechanics

**Decision**: Compare `Get-Item bin/<config>/net8.0/d2net-init.exe | Select LastWriteTime` against the newest `LastWriteTime` from `Get-ChildItem -Recurse tools/d2net/src/D2Net.Init -Filter *.cs`. If the binary is older than any `.cs` source file, declare stale.

**Rationale**:
- This is a coarse but reliable check: `.cs` mtime newer than binary implies the binary doesn't reflect that source. False positives only on filesystem mtime weirdness (which is rare on developer laptops).
- The vendored `pgbridge/` directory is explicitly excluded from the staleness check — `bridge-direct.mjs` is a runtime asset, not a build input, and changes to it don't necessitate a `dotnet build`.
- The skill MUST run this check via the Bash tool with PowerShell on Windows or `find` on Unix; the SKILL.md procedure spells out the exact command.

**Alternatives considered (rejected)**:
- Track the binary's embedded `<InformationalVersion>`: requires running the binary to read it, which defeats the "skip the run if stale" goal.
- File hash comparison: more expensive; mtime is sufficient for the developer-laptop case.

## R4 — Session-scoped destructive confirmation cache (FR-013)

**Decision**: The cache is a Claude-conversation-scoped concept, not a filesystem concept. The skill notes the absolute path of `.D2NET/` in the conversation transcript when a destructive confirmation is given (e.g., as a structured Claude-side note: "destructive-confirmed: D:\\repo\\.D2NET — this session"). Subsequent skill invocations in the same conversation read that note and skip the prompt for the same path.

**Rationale**:
- Filesystem persistence (e.g., a `.D2NET/.destructive-confirmed` marker) would survive the user closing Claude and re-opening — defeating the FR-013 "fresh session re-prompts" intent.
- Conversation-scoped means: same Claude Code session = same cache. New session = empty cache. Aligns with FR-013 word-for-word.
- The cache is implementation-internal; users do not see it.

**Post-compaction behaviour (acceptable degradation)**: Claude Code's auto-compaction may summarise prior turns and drop the structured marker line from the surviving conversation context. After compaction, the destructive-confirmation cache MAY be effectively cleared and the user MAY be re-prompted for an already-confirmed destructive operation against the same `.D2NET/`. This is acceptable degradation, not a defect — FR-013's "no re-prompt within session" is best-effort and prefers a redundant prompt over a silently-skipped destructive action. The skill's procedure does NOT compensate via filesystem persistence (see Decision above).

**Alternatives considered (rejected)**:
- Disk-backed cache with TTL: complexity for negligible gain.
- No cache at all: violates FR-013 (user would re-confirm every invocation).

## R5 — Output handling and JSON detection

**Decision**: After invoking the binary, the skill examines the resolved flag set (the actual flags passed) for `--json`. If present, surface stdout verbatim (FR-017 second paragraph). If absent, apply the 50-line truncation. Detection is by literal `--json` in the resolved invocation — natural-language phrases like "in json" / "as json" are translated by FR-009 into `--json` BEFORE this point, so the JSON-detection step only inspects the flag set, not the user's raw input.

**Rationale**:
- Looking at the resolved flag set is the most reliable proxy for "does the binary emit JSON".
- Translation-then-detect is a two-stage pipeline; the skill's procedure already separates the stages cleanly.

**Alternatives considered (rejected)**:
- Attempt to JSON-parse the binary's stdout to determine format: brittle; the binary's plain-text output sometimes accidentally parses as JSON (e.g., empty output).
- Always treat as plain text and let the user opt out of truncation: defeats the whole point of FR-017's JSON exception.

## R6 — Confirmation-prompt round-trip semantics

**Decision**: A "confirmation prompt" is a single message Claude sends to the user, ending with a yes/no question. Claude waits for the user's next input before proceeding. The skill never spins or polls — it just stops the current turn. When the user replies, the skill resumes execution from where it stopped, using the user's reply as the answer.

**Rationale**:
- This matches how Claude Code naturally handles user input: each user turn produces one Claude response. A "wait for confirmation" is just "end this turn and resume on the next".
- No special wait-loop or async primitive needed in SKILL.md — the model's natural turn-taking IS the wait mechanism.

**Alternatives considered (rejected)**:
- Embed a polling loop in the SKILL.md: would require the model to invent a state machine on every turn; brittle.
- Use a separate "awaitable" tool: not available in standard Claude Code; over-engineering.

## R7 — Bridge-port collision recovery (FR-016)

**Decision**: On `BridgePortInUse` (5), the skill computes `next = (last_attempted_port + 1) if last_attempted_port < 65535 else 54401`, suggests it in its response ("retry with `--bridge-port <next>`?"), and on user confirmation re-invokes the binary with the new port. The "next" suggestion ladder is bounded — after 3 consecutive collisions the skill stops suggesting and asks the user to specify a port manually.

**Rationale**:
- The `+1` suggestion is the simplest behaviour that gives forward progress on transient collisions.
- The 3-attempt cap prevents accidental port-walk if the user's machine has many bound ports in the same range.
- Specific ports (54401, 54402, 54403) are explicitly chosen over relying on the binary's default to avoid surprising the user with an unexpectedly-different persisted port.

**Alternatives considered (rejected)**:
- Auto-pick a random free port via `TcpListener(IPAddress.Loopback, 0)`: would change `connection.port` in settings to an unpredictable value; bad for external-tool stability.
- Always suggest 54401: stops working after the first collision walks to it.

## R8 — Test/validation strategy for a model-driven skill

**Decision**: Validation is a combination of:
1. **Static lint of `SKILL.md`** — frontmatter parses as YAML, body is markdown with the expected procedure-section headers.
2. **Smoke test via Claude Code** — manually invoke `/D2NET-init` with each of the FR-009 / SC-002 inputs and verify the binary is called with the expected flags. Recorded as a `validation.md` artifact in the spec dir.
3. **Reference the underlying binary's existing test suite** (89 tests in `D2Net.Init.Tests`) for end-to-end coverage of the binary itself — the skill is a thin invocation wrapper and does not need its own Dart-file-tree fixtures.

**Rationale**:
- Skills are markdown — there is no runtime to unit-test.
- The most meaningful "tests" of a skill are recorded interactions: did `/D2NET-init list` produce the expected behavior on a real workspace?
- Avoiding a dedicated test harness keeps the feature small and maintainable.

**Alternatives considered (rejected)**:
- Write an automated harness that invokes Claude Code from outside, types `/D2NET-init`, parses the response: enormous infrastructure for marginal coverage.
- Add unit tests of the underlying binary's CLI parsing that mimic the skill's translations: duplicates the binary's own ArgParser tests, which already exist.

## R9 — Distribution and discoverability

**Decision**: The skill ships as a tracked file at `.claude/skills/D2NET-init/SKILL.md`, committed to git on the same branches that ship the underlying binary. No separate package, no install step. Users who clone the repo and open Claude Code in it see `/D2NET-init` in their slash-command list automatically.

**Rationale**:
- Matches every other skill in `.claude/skills/`.
- Skills are not currently distributable as standalone artifacts in Claude Code; they live in the repo that uses them.

**Alternatives considered (rejected)**:
- Publish as a Claude Code plugin: not standard practice in this repo.
- Symlink from `~/.claude/skills/`: cross-developer fragility.

---

## R10 — Naming and casing

**Decision**: Skill file path is `.claude/skills/D2NET-init/SKILL.md` (preserving the user's literal `D2NET-init` casing from the request). Frontmatter `name: "D2NET-init"` matches. Slash-command invocation `/D2NET-init` matches.

**Rationale**:
- The user's literal request was `/D2NET-init`. Honoring exact casing matches the brand of the underlying CLI (which spells itself `D2NET.Init` / `D2Net.Init` / `d2net-init` in different contexts; the skill picks the user's chosen rendering).
- Windows is case-insensitive at the filesystem layer; this is purely cosmetic on dev machines. On case-sensitive hosts (Linux, macOS APFS-CS), the directory must be created with the exact casing.

**Alternatives considered (rejected)**:
- Lowercase `d2net-init` to match Unix convention: contradicts the user's request and breaks consistency with the underlying CLI's branding.
- Mixed case `D2net-init`: arbitrary; not what the user asked for.
