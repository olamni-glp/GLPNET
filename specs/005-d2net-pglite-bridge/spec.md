# Feature Specification: D2NET.Init — Storage Swap to PGLite WASM via Direct Postgres-Wire Bridge

**Feature Branch**: `005-d2net-pglite-bridge`
**Created**: 2026-04-30
**Status**: Draft
**Input**: User description: "upgrade current D2NET.init to use fix for pglite bridge and pglite wasm instead of sqlite"

## Background

The shipped `D2NET.Init` (v2026.04.30-2, branch `002-d2net-init`) stores the workspace database as a single embedded SQLite file at `.D2NET/pgdb/workspace.sqlite`. That choice was a forced fallback documented in `specs/002-d2net-init/spec.md` (Clarifications Q6): the original PGLite + `pg-gateway` + ODBC stack failed end-to-end during implementation. The follow-up RCA (PR #3, tag `v2026.04.30-3`, branch `003-pglite-bridge-rca`) identified two distinct bugs (PGLite's implicit trailing `Z` from `execProtocolRaw`, and `pg-gateway` 0.3.0-beta.4's response-stream corruption) and ships a working hand-rolled Postgres-wire bridge — `docs/research/pgbridge-reference/bridge-direct.mjs` — as a reference artifact. That bridge is verified working with both Npgsql 8.0.3 (extended protocol) and the modern `PostgreSQL ODBC Driver(UNICODE)`.

This feature applies that fix: it re-points `D2NET.Init` away from embedded SQLite and back to PGLite WASM, accessed by .NET through the proven `bridge-direct.mjs` lifecycle. Externally observable behaviour of every other clause in `specs/002-d2net-init/spec.md` (the four CLI inputs, the prompt/exclusion flow, the five-table schema, the `--list`/`--Exclusions`/`--current-phase`/`--FORCE --DELETE-EXISTING` semantics, the deny-from-wrong-CWD rule) is preserved unchanged. **The only thing that changes is the storage engine and the connection contract that downstream tools see.**

## Clarifications

### Session 2026-04-30

- Q: Is psqlODBC a hard release-blocking guarantee or best-effort compatibility? → A: Hard guarantee for the full RCA-verified surface (Npgsql 8.x extended protocol + `PostgreSQL ODBC Driver(UNICODE)` basic SELECT against the five workspace tables, plus the RCA's smoke goals on the seeded `t (x INT)` table); anything outside that surface stays best-effort.
- Q: Is the v1 cross-platform guarantee Windows-only, two OSes, or all three? → A: Windows-only release-blocking guarantee for v1. macOS and Linux are "expected to work but unverified" — best-effort; bug reports accepted; not release blockers. SC-* hard requirements apply only on Windows.
- Q: How does `--bridge-port` behave on inspection commands (`--list`, `--Exclusions`, `--current-phase`)? → A: Inspection commands default to the persisted `connection.port`; `--bridge-port` on a non-init invocation overrides only the live run and does NOT modify `D2NET-Settings.json` or the `setting` table. The persisted port is rewritten only by init (fresh init or `--FORCE --DELETE-EXISTING` re-init).
- Q: How does the upgraded command behave when an existing workspace's PGLite data tree is corrupt? → A: Manual recovery only. The bridge's `BRIDGE_ERROR pglite_init_failed …` (or any equivalent PGLite open failure) MUST be surfaced verbatim, immediately followed by an explicit recovery hint pointing the user at `--FORCE --DELETE-EXISTING`. No automatic rebuild, no interactive prompt; the destructive step stays gated behind the same explicit override the rest of the spec uses.
- Q: Should an ODBC-style connection string be persisted alongside the Npgsql one? → A: Yes. Persist both `connection.connection_string` (Npgsql/.NET, current behaviour) AND `connection.connection_string_odbc` (psqlODBC, using the verified modern-installer driver name `PostgreSQL ODBC Driver(UNICODE)`) in `D2NET-Settings.json`, with matching `db_connection_string` and `db_connection_string_odbc` rows in the `setting` table. The ODBC string is correct on Windows hosts with the modern psqlODBC installer (the v1 supported configuration); users on other ODBC variants edit the `Driver={…}` clause manually.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Initialise a fresh workspace backed by PGLite WASM (Priority: P1)

A developer who is preparing to use the D2NET toolkit on a Dart codebase runs the upgraded `D2NET.Init` once at the repository root. The command collects the same four inputs as the shipped command (source directory name, target extension, target directory name, approved exclusion list) and produces the same five tables (`setting`, `excluded_directories`, `dart_files`, `phase_sequence`, `phase_status`) — but the underlying database is now a PGLite WASM instance whose data tree lives under `.D2NET/pgdb/`. While the command is running, the database is exposed on a well-known local TCP port through a Postgres-wire bridge (a Node.js subprocess running the hand-rolled `bridge-direct.mjs`). The connection details persisted in `setting` and `D2NET-Settings.json` describe that bridge port. When the command exits, the bridge subprocess is shut down cleanly; the data tree on disk is preserved for the next command.

**Why this priority**: This is the entire upgrade. Without a working PGLite-backed workspace, none of the value of switching off SQLite is delivered: downstream tooling cannot use Postgres-specific features (JSONB operators, array types, full-text search, the `pg_*` system catalogs), and the mismatch between the user's stated requirement ("PGLite WASM-based single-user Postgres") and the shipped artifact (SQLite) remains. Every other behaviour preserved by this feature is meaningless until the storage swap itself works.

**Independent Test**: From a clean repository (no `.D2NET` folder), invoke the upgraded `D2NET.Init` with explicit parameters supplying the source directory (`glp_runtime`), the target extension (`_net`), and the target directory name (`glp_runtime_net`), accepting the suggested exclusions non-interactively. Verify (a) `.D2NET/` exists, (b) `.D2NET/D2NET-Settings.json` parses as JSON and contains a `connection` block whose `engine` is `pglite` plus host, port, database, user, password and full Postgres-style connection string, (c) `.D2NET/pgdb/` is a PGLite data tree (a directory of files PGLite recognises on next open) — **not** a single `.sqlite` file, (d) the `dart_files`, `excluded_directories`, `phase_sequence`, `phase_status`, and `setting` tables are present and have the expected row counts (FR-014/FR-013/FR-015/FR-016/FR-012 from `specs/002-d2net-init/spec.md`), (e) the command exits with status 0, (f) the Node.js bridge subprocess that the command spawned is no longer running after the command exits.

**Acceptance Scenarios**:

1. **Given** a repo root with a `glp_runtime` source directory containing 200 `.dart` files outside any excluded subdirectory, and no pre-existing `.D2NET` folder, **When** the developer runs `D2NET.Init --source glp_runtime --target-extension _net --target glp_runtime_net --accept-suggested-exclusions`, **Then** `.D2NET/D2NET-Settings.json` is created with `connection.engine` = `pglite` and Postgres-flavoured connection details; `.D2NET/pgdb/` is a PGLite data tree (multi-file Postgres data layout, not `workspace.sqlite`); the five tables are populated as in the shipped 002 spec; and the command exits with status 0.
2. **Given** the command has just initialised the database, **When** an external Postgres client (Npgsql, psqlODBC, `psql`, JetBrains DataGrip, DBeaver) connects to `127.0.0.1:<recorded_port>` using the connection details from `setting`/`D2NET-Settings.json` **while a subsequent `D2NET.Init --list` invocation is running**, **Then** the client can execute `SELECT * FROM dart_files ORDER BY full_path` and receives one row per `.dart` file from the non-excluded source tree.
3. **Given** a successful init, **When** the command exits, **Then** the bridge subprocess no longer holds the port open and a fresh `D2NET.Init --list` (or any other D2NET command) can spin up its own bridge on the same port without `EADDRINUSE`.

### User Story 2 - External Postgres tooling reads the workspace while a D2NET command is running (Priority: P2)

After the upgrade, the developer can point any standard Postgres client at the well-known local port recorded in `D2NET-Settings.json` and run `SELECT` queries against any of the five workspace tables, using the same connection details that downstream D2NET commands use internally. This works for the duration of any D2NET command's execution (per the existing per-invocation bridge lifecycle from FR-011a) and supports both extended-protocol drivers (Npgsql) and ODBC drivers (psqlODBC).

**Why this priority**: This is the user-facing payoff of moving to PGLite. With SQLite the workspace was queryable only by SQLite-aware tools (DB Browser for SQLite, the `sqlite3` CLI, JetBrains' SQLite plugin). After the upgrade the workspace is queryable by any Postgres client the developer already has installed. It is not strictly required for the workspace to function (User Story 1 produces a usable workspace on its own), but it is the visible justification for the swap.

**Independent Test**: After User Story 1 has succeeded, in a second shell run `D2NET.Init --list` (which keeps a bridge alive for its duration). In a third shell, connect with `psql` or DBeaver using the recorded connection details and execute `SELECT count(*) FROM dart_files` and `SELECT path FROM excluded_directories ORDER BY path`. Both queries return the same data the `--list` and `--Exclusions` outputs would print.

**Acceptance Scenarios**:

1. **Given** an initialised workspace, **When** an external Npgsql client connects using the persisted connection string while a D2NET command is running, **Then** the connection succeeds, server reports a Postgres `server_version`, and `SELECT 1`, `SELECT count(*) FROM dart_files`, `SELECT * FROM phase_status` all return correct results.
2. **Given** an initialised workspace, **When** an external psqlODBC client connects using the persisted ODBC-style connection string while a D2NET command is running, **Then** the connection succeeds and at least `SELECT count(*) FROM dart_files` returns the correct row count without the host process crashing (the historical `STATUS_STACK_BUFFER_OVERRUN` regression is gone).
3. **Given** no D2NET command is currently running and no bridge has been started manually, **When** an external client tries to connect to the recorded port, **Then** the connection fails (port closed) and the client error is the standard "connection refused" — consistent with the per-invocation bridge lifecycle.

### User Story 3 - Detect and refuse a pre-upgrade SQLite workspace without explicit override (Priority: P3)

A developer with an existing `.D2NET` workspace that was created by the shipped (SQLite-backed) `D2NET.Init` re-runs the upgraded command. Because the storage engine has changed and there is no online migration path, the command MUST detect the pre-existing workspace (by the same rule as the shipped FR-003: `.D2NET` directory exists at the CWD) and refuse to touch it unless the developer explicitly supplies `--FORCE --DELETE-EXISTING`. With those flags the upgraded command deletes the old SQLite-backed workspace in full and rebuilds it from scratch as a PGLite-backed workspace.

**Why this priority**: Required for correctness (a SQLite file under `.D2NET/pgdb/` is not openable by PGLite and the connection details would silently lie). Not required for fresh-init MVP value: a developer who has never run the shipped 002 command never sees this case. Most existing SQLite workspaces are cheap to recreate (the source tree is rewalked), so an automatic data migration is intentionally out of scope.

**Independent Test**: In a working tree where the shipped 002 implementation has previously created `.D2NET/pgdb/workspace.sqlite`, run the upgraded `D2NET.Init` with no override flags and confirm it aborts with the existing "workspace already exists" message and a non-zero exit status — and crucially does not delete or open the old `.sqlite` file. Then run with `--FORCE --DELETE-EXISTING`; the old workspace is removed wholesale and a fresh PGLite-backed workspace is created.

**Acceptance Scenarios**:

1. **Given** a `.D2NET` directory containing the SQLite-era layout (`.D2NET/pgdb/workspace.sqlite` plus `D2NET-Settings.json` recording `engine: sqlite`), **When** the developer runs the upgraded `D2NET.Init` with no override flags, **Then** the command reports "workspace already exists at .D2NET; use --FORCE --DELETE-EXISTING to recreate it", makes no change to any file under `.D2NET`, and exits with a non-zero status.
2. **Given** the same SQLite-era `.D2NET`, **When** the developer runs `D2NET.Init --FORCE --DELETE-EXISTING` together with the configuration parameters, **Then** the entire `.D2NET` directory (including `pgdb/workspace.sqlite`) is deleted, a fresh PGLite-backed workspace is created, and `D2NET-Settings.json`'s `connection.engine` is `pglite`.
3. **Given** no `.D2NET` directory exists at the repo root, **When** the developer runs the upgraded `D2NET.Init` with neither flag, **Then** the command proceeds to create a fresh PGLite-backed workspace exactly as in User Story 1.

### Edge Cases

- **Bridge port already in use**: When the upgraded command is asked to start its bridge on a port that is already bound by another process (another D2NET invocation that has not yet exited, an unrelated local Postgres instance, a stale crashed bridge), the command MUST fail fast with a clear "bridge port <port> is already in use" error, MUST kill any bridge subprocess it has already spawned, MUST NOT modify any file under `.D2NET`, and MUST exit with a non-zero status. The user can retry with `--bridge-port <other>`.
- **Node.js runtime missing or too old**: When the host machine does not have a Node.js runtime on PATH at or above the minimum supported version, the command MUST fail fast with a clear "node.js >= <minimum> required to run the PGLite bridge; install it from https://nodejs.org/ and retry" error, MUST NOT modify any file under `.D2NET`, and MUST exit with a non-zero status.
- **Vendored `bridge-direct.mjs` or its `node_modules` is missing/corrupt**: When the command cannot find the bundled bridge script or its pinned `@electric-sql/pglite` install, it MUST fail fast with a clear "PGLite bridge files are missing or corrupt; reinstall D2NET" error, MUST NOT modify any file under `.D2NET`, and MUST exit with a non-zero status.
- **Bridge subprocess does not print `BRIDGE_READY` within the timeout**: The command MUST kill the bridge subprocess, MUST NOT modify any file under `.D2NET`, MUST report whatever `BRIDGE_ERROR …` line (if any) the subprocess emitted on stdout, and MUST exit with a non-zero status. Default timeout: 15 seconds.
- **Bridge subprocess crashes mid-command**: The command MUST detect the bridge has exited unexpectedly (its stdout/stderr stream closes, or the SQL connection drops), MUST report a clear "PGLite bridge exited unexpectedly" error including any final stderr line from the bridge, MUST NOT leave a partially populated workspace on disk, and MUST exit with a non-zero status.
- **Bridge subprocess does not exit during teardown**: When the command closes its own SQL connection cleanly and then closes the bridge's stdin (the standard shutdown signal per `bridge-direct.mjs`'s contract), but the subprocess is still alive after a small grace window, the command MUST send SIGTERM (or the platform-equivalent termination signal) and wait again, then MUST hard-kill the process. The command MUST emit a non-fatal warning that the bridge required forced termination but MUST still report success if the actual workspace mutation completed.
- **External Postgres client uses SSL/TLS**: The bridge does not accept TLS (it explicitly replies `N` to `SSLRequest`). External clients MUST disable SSL in their connection settings (`SSL Mode=Disable` for Npgsql, `SSLmode=disable` for psqlODBC). The command's persisted connection string MUST include the appropriate SSL-disabled directive for downstream tools to copy/paste.
- **Pre-existing SQLite-format `.D2NET/pgdb/workspace.sqlite` and `D2NET-Settings.json` recording `engine: sqlite`**: Treated identically to "workspace already exists" by FR-014. The command does not silently overwrite; it does not attempt automatic migration.
- **Existing workspace's PGLite data tree is corrupt or unreadable** (filesystem corruption, manual file edit, hard kill of a previous bridge subprocess that left torn writes, antivirus quarantine of a `pgdb/` file, etc.): The bridge subprocess's PGLite open call fails and the bridge prints `BRIDGE_ERROR pglite_init_failed …` (per `bridge-direct.mjs`'s contract) before exiting. The D2NET command surfaces that error verbatim per FR-005 and additionally emits a one-line recovery hint pointing the user at `--FORCE --DELETE-EXISTING`. No automatic rebuild — the user explicitly chooses to discard the corrupt state and re-walk the source tree.
- **`pg-gateway` accidentally pulled into the dependency tree**: The vendored `package.json` for the bridge MUST list `@electric-sql/pglite` as the only runtime dependency. Build/release tooling MUST verify that `pg-gateway` is not present in the shipped `node_modules` tree. (This is a guard against regression: the RCA is unambiguous that `pg-gateway` is the cause of the second-symptom crashes.)
- **All other edge cases from `specs/002-d2net-init/spec.md`** (invoked from wrong directory, source missing, source has zero `.dart` files, repo root not writable, interactive prompt interrupted, duplicate filenames in different paths, archive-marker false-positive, target name not equal to source+extension, target directory already exists, `--list`/`--Exclusions` against missing workspace, `--current-phase` against empty `phase_status`): Behaviour is unchanged from the shipped spec.

## Requirements *(mandatory)*

These requirements describe **only what changes** in the upgrade. Every requirement in `specs/002-d2net-init/spec.md` (FR-001 through FR-022) remains in force for the upgraded command except where this section explicitly supersedes it. FR-023 ("`--bridge-port` is a no-op under SQLite") is repealed and replaced by FR-012 below.

### Functional Requirements

#### Storage engine

- **FR-001**: The workspace database MUST be a **PGLite WASM** instance (the `@electric-sql/pglite` Node package, pinned to the version recorded in the vendored `package.json`). Its data tree MUST live under `.D2NET/pgdb/` exactly as written in the user's original requirement, and `.D2NET/pgdb/` MUST be the directory PGLite operates against on every command — no single-file SQLite database is created.
- **FR-002**: The five workspace tables (`setting`, `excluded_directories`, `dart_files`, `phase_sequence`, `phase_status`) MUST be created in the PGLite database with externally equivalent semantics to the shipped SQLite schema: same column names, same primary keys, same NOT NULL constraints on the same columns, same `kind ∈ {tool, pattern, manual}` constraint on `excluded_directories`, same one-row-per-key contract on `setting`, same monotonic auto-generated id on `dart_files`, same `last_updated` timestamp recorded as ISO-8601 UTC text on read for `phase_status`. Implementation is free to use Postgres-native types (`SERIAL` / `GENERATED ... AS IDENTITY`, `TIMESTAMPTZ`, `TEXT`, `CHECK` constraints) provided the externally observable behaviour is preserved.
- **FR-003**: After a successful init run, the count of rows in `dart_files` MUST equal the count of `.dart` files in the non-excluded source tree (preserves SC-004 from the shipped spec); `excluded_directories` MUST contain exactly the developer-approved list (preserves SC-005); `phase_sequence` and `phase_status` MUST be empty (preserves SC-006).

#### Postgres-wire bridge (per-invocation)

- **FR-004**: Every D2NET.Init invocation that needs to read or write the workspace database MUST spawn a Node.js subprocess running the vendored hand-rolled bridge script `bridge-direct.mjs` (verbatim ports of `docs/research/pgbridge-reference/bridge-direct.mjs` are acceptable; functional equivalence to that script's behaviour is mandatory). The subprocess MUST be started with `--pgdir <absolute path to .D2NET/pgdb>` and `--port <chosen port>` and MUST be the only process holding the data tree open for the duration of the command.
- **FR-005**: The command MUST wait for the bridge subprocess to print the literal line `BRIDGE_READY port=<port> pid=<pid>` on its stdout before opening any SQL connection. The maximum wait time is fixed by this spec at **15 seconds**; on timeout the command MUST kill the subprocess, MUST NOT modify any file under `.D2NET`, and MUST exit with a non-zero status. If the subprocess prints a `BRIDGE_ERROR <message>` line on stdout instead, the command MUST report that exact message verbatim in its own error output and exit non-zero. **When the `BRIDGE_ERROR` is `pglite_init_failed` (or any other failure mode in which PGLite cannot open the existing data tree), the command MUST also append a single explicit recovery hint to its error output naming the `--FORCE --DELETE-EXISTING` flag combination and the fact that the workspace will be rebuilt from the source tree** — so a user encountering a corrupt workspace mid-session learns the recovery path from a single command output without needing to consult docs. No automatic rebuild and no interactive recovery prompt: the destructive rebuild remains gated behind the explicit override.
- **FR-006**: Before the command exits (success or failure), it MUST shut down the bridge subprocess cleanly. The shutdown sequence is:
  1. Close the command's own SQL connection.
  2. Close the bridge subprocess's stdin (this is the documented graceful-shutdown signal in `bridge-direct.mjs`).
  3. Wait up to 5 seconds for the subprocess to exit.
  4. If still alive, send SIGTERM (or platform equivalent) and wait up to 2 more seconds.
  5. If still alive, hard-kill the process.

  In cases 4 and 5 the command MUST emit a non-fatal warning naming the bridge PID; the warning MUST NOT change the exit code if the actual workspace mutation completed successfully.
- **FR-007**: The bridge subprocess MUST NOT outlive the D2NET command. The command MUST register the appropriate process-exit / signal handler so that an interrupted command (Ctrl-C, kill) still tears down the bridge. The command MUST be safe to invoke twice in series in the same shell without a residual port-bind error.
- **FR-008**: `pg-gateway` MUST NOT be listed as a runtime dependency in the vendored bridge's `package.json` and MUST NOT be present in the shipped `node_modules` tree. Release/packaging tooling MUST treat the appearance of `pg-gateway` (or any package depending on it) anywhere under the bridge directory as a build-time error.

#### Connection contract

- **FR-009**: The connection details persisted in both `D2NET-Settings.json` (under the `connection` JSON block, retaining the shipped key name) and the `setting` table MUST describe the **bridge endpoint** the user (or a downstream tool) connects to, not the raw PGLite data directory. Required fields are: `engine` = `"pglite"` (lowercase), `host` (default `"127.0.0.1"`), `port` (the integer the bridge listened on for this run), `database` (default `"d2net"`), `user` (default `"d2net"`), `password` (default `"d2net"`), `data_dir` (absolute path to `.D2NET/pgdb/`, recorded for diagnostic and disaster-recovery use only — clients connect via the wire protocol, not the data directory), `connection_string` (a Postgres-style connection string suitable for Npgsql: `Host=127.0.0.1;Port=<port>;Database=d2net;Username=d2net;Password=d2net;SSL Mode=Disable`), and `connection_string_odbc` (a psqlODBC-style connection string suitable for the v1 supported configuration — Windows host with the modern `PostgreSQL ODBC Driver(UNICODE)` installed: `Driver={PostgreSQL ODBC Driver(UNICODE)};Server=127.0.0.1;Port=<port>;Database=d2net;Uid=d2net;Pwd=d2net;SSLmode=disable;`). The shipped SQLite-era field `db_file` MUST NOT appear; `data_dir` replaces it. Users on non-default ODBC drivers (legacy `PostgreSQL Unicode(x64)`, ANSI variant, Linux/macOS unixODBC drivers) MUST edit the `Driver={…}` clause manually; the spec does not enumerate every driver name.
- **FR-010**: The `setting` table MUST contain one row per connection field with keys `db_engine`, `db_host`, `db_port`, `db_database`, `db_user`, `db_password`, `db_data_dir`, `db_connection_string`, `db_connection_string_odbc` (preserving the `db_*` prefix convention from the shipped spec for forward compatibility with any tool that already reads those keys). Values MUST agree with the JSON `connection` block byte-for-byte after JSON-string unescaping (this includes both `connection_string` and `connection_string_odbc`).
- **FR-011**: The connection details MUST be sufficient for **two** Postgres-wire client surfaces — the surface verified by the RCA — to open a session and run the listed operations against any of the five workspace tables while a D2NET command is running:
  - **Npgsql 8.x** (or any later compatible release the implementation pins to) using the extended protocol: opening a session, simple parameterised `SELECT`, and executing the User Story 2 acceptance queries (`SELECT 1`, `SELECT count(*) FROM dart_files`, `SELECT * FROM phase_status`, `SELECT version()`).
  - **`PostgreSQL ODBC Driver(UNICODE)`** (psqlODBC) in modern installer form: opening a session, simple `SELECT` against any of the five workspace tables, and executing `SELECT count(*) FROM dart_files` without the host process exiting via `STATUS_STACK_BUFFER_OVERRUN`.

  Both client surfaces are **release-blocking**: failure of either surface to perform the listed operations on a supported host is a release blocker. Operations outside this enumerated surface — prepared statements with custom OIDs, server-side cursors, `COPY`, `NOTIFY`/`LISTEN`, `PostgreSQL ANSI(x64)` (the legacy psqlODBC variant), other Postgres clients (psql command-line, pgAdmin, JDBC, etc.) — remain best-effort: they likely work because the bridge is wire-faithful, but they are not promised by this spec and their breakage is not a release blocker. Compatibility with `pg-gateway`-based stacks is out of scope and explicitly NOT a requirement (the bridge does not use `pg-gateway`).

#### CLI surface and flag semantics

- **FR-012**: `--bridge-port <int>` MUST be a meaningful, accepted CLI option on every invocation form (init and inspection commands). The port lifecycle is:
  - **Fresh init** (no pre-existing `.D2NET`, or `--FORCE --DELETE-EXISTING` re-init): the bridge MUST listen on the supplied `--bridge-port` if given, otherwise on the spec-fixed default `54400` (chosen to match the verbatim example in `docs/research/pgbridge-reference/README.md`). The chosen port MUST be persisted to `connection.port` in `D2NET-Settings.json` and to the `db_port` row in the `setting` table. **Init is the only command that writes the port to settings.**
  - **Inspection commands** (`--list`, `--Exclusions`, `--current-phase`) and any other non-init invocation: the bridge MUST default to the **persisted** `connection.port` read from `D2NET-Settings.json` at command start. If `--bridge-port` is supplied on an inspection command, it MUST override the live invocation's listening port only and MUST NOT modify `D2NET-Settings.json` or the `setting` table. The persisted port remains whatever init wrote.

  The shipped spec's FR-023 (`--bridge-port` is a no-op under SQLite) is **repealed** by this requirement.
- **FR-013**: All other CLI flags from the shipped spec — `--source`, `--target-extension`, `--target`, `--accept-suggested-exclusions`, the interactive prompt flow, `--FORCE`, `--DELETE-EXISTING`, `--list`, `--Exclusions`, `--current-phase`, `--json` — MUST behave identically to the shipped command. The only externally observable change is in the contents of the `connection` block, in the on-disk shape of `.D2NET/pgdb/` (data tree, not a file), and in the bridge lifecycle that supports the inspection options.
- **FR-014**: When detecting "workspace already exists" for FR-003 of the shipped spec (refuse without `--FORCE --DELETE-EXISTING`), the upgraded command MUST also accept a SQLite-era layout (`.D2NET/pgdb/workspace.sqlite` plus a `D2NET-Settings.json` whose `connection.engine` is anything other than `pglite`) as triggering the same refusal. No automatic migration of data from a SQLite-era workspace is performed; the developer is expected to use `--FORCE --DELETE-EXISTING` and accept that the source tree will be rewalked.

#### Bundled assets

- **FR-015**: The vendored bridge bundle (the `bridge-direct.mjs` script plus its pinned `node_modules`) MUST ship as part of the `D2Net.Init` artifact and MUST be locatable by the running command on every supported host OS without any developer-side `npm install` step. The exact on-disk location of the bundle within the install tree is an implementation detail; the requirement is that the command Just Works after installation.
- **FR-016**: The bridge bundle's `package.json` MUST pin `@electric-sql/pglite` to a single version (the version recorded in `docs/research/pgbridge-reference/package.json` is the recommended baseline — currently `0.2.17`). Bumping that pin is allowed, but MUST be done deliberately and MUST be accompanied by a re-run of the RCA's verification steps against both Npgsql and psqlODBC before release.

### Key Entities *(include if feature involves data)*

- **PGLite data tree (`.D2NET/pgdb/`)**: A multi-file Postgres data layout produced by `@electric-sql/pglite` when initialised against this directory. Treated as an opaque on-disk artifact; only the bridge subprocess opens it directly. Replaces the shipped `.D2NET/pgdb/workspace.sqlite` single file.
- **Postgres-wire bridge (`bridge-direct.mjs`)**: A short Node.js script (verbatim or functionally equivalent to `docs/research/pgbridge-reference/bridge-direct.mjs`) that listens on a local TCP port, handles the Postgres `StartupMessage` and `SSLRequest` by hand, then forwards subsequent batched extended-protocol frames to `pglite.execProtocolRaw` and ships the response straight back. Lives as a bundled asset of `D2Net.Init`.
- **Bridge subprocess**: A short-lived Node.js process spawned at the start of every D2NET command and torn down before the command exits. Holds the only open handle to the PGLite data tree for the duration of the command.
- **Connection block (`connection` in `D2NET-Settings.json`, and the `db_*` rows in `setting`)**: The Postgres-flavoured handshake info that lets any external Postgres client (Npgsql, psqlODBC, `psql`, DBeaver, JetBrains DataGrip) connect to the bridge port while a D2NET command is running. Replaces the shipped SQLite-flavoured block (engine `sqlite`, single `db_file` field).
- **All entities from `specs/002-d2net-init/spec.md`** (Repository root, Source directory, Target directory, Excluded directory, Workspace `.D2NET`, Settings file, Dart source file record, Phase, Current phase): preserved unchanged in meaning. Only "Workspace database" is redefined: it is now a PGLite WASM instance reachable through the per-invocation bridge, not an embedded SQLite file.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A single non-interactive `D2NET.Init` invocation against a source tree of up to 500 `.dart` files (across up to 100 non-excluded directories) completes in under 15 seconds and exits with status 0 on a developer workstation with a modern multi-core CPU and an SSD. (5-second budget over the shipped SQLite SC-001 to absorb bridge spawn / `BRIDGE_READY` / clean teardown.)
- **SC-002**: After a successful init, `.D2NET/D2NET-Settings.json` parses as JSON; `connection.engine` equals `"pglite"`; `connection.port` equals the supplied `--bridge-port` when given, otherwise the default `54400`; `connection.connection_string` parses as a valid Npgsql connection string with `SSL Mode=Disable`; `connection.connection_string_odbc` is a non-empty string beginning with `Driver={PostgreSQL ODBC Driver(UNICODE)};` and ending with `SSLmode=disable;`.
- **SC-003**: After a successful init, `.D2NET/pgdb/` is a directory containing more than one regular file (i.e. a PGLite data tree, not a single `.sqlite` file). The substring `workspace.sqlite` does not appear anywhere under `.D2NET/`.
- **SC-004**: While **any** D2NET command is executing, an external Npgsql client using the persisted connection string can open a session, run `SELECT version()` (returns a Postgres-format version string, not SQLite), and run `SELECT count(*) FROM dart_files` returning the same integer as the line count of `D2NET.Init --list`.
- **SC-005**: While **any** D2NET command is executing, an external psqlODBC client using the persisted connection details can open a session and run `SELECT count(*) FROM dart_files` returning the correct integer **without** the host process exiting via `STATUS_STACK_BUFFER_OVERRUN` (the historical regression from the RCA must remain absent).
- **SC-006**: After a D2NET command exits, no Node.js subprocess started by that command remains running, and no socket is bound on the bridge port. A second `D2NET.Init --list` immediately afterwards succeeds without `EADDRINUSE`.
- **SC-007**: When the supplied `--bridge-port` is already in use at command start, the command exits with a non-zero status, leaves no `.D2NET/` partially mutated, and emits a stderr message identifying both the port and the already-bound process where the OS will tell us (best effort).
- **SC-008**: When Node.js is missing from PATH, the command exits with a non-zero status and emits a stderr message naming the minimum supported Node.js version and the canonical install URL. No `.D2NET/` directory is created or modified.
- **SC-009**: A pre-existing SQLite-format `.D2NET` workspace (the shipped 002 layout) is detected by the `--FORCE --DELETE-EXISTING` gate exactly as a fresh-init double-run would be: no SQL is executed against the SQLite file, no PGLite data tree is created on top of it, and the command exits non-zero unless both override flags are supplied.
- **SC-010**: `pg-gateway` is absent from the bundled `node_modules` of every shipped D2Net.Init artifact, verified by a build-time check.

## Assumptions

- The hand-rolled `bridge-direct.mjs` from `docs/research/pgbridge-reference/` is the authoritative reference for the bridge's Postgres-wire behaviour. The plan/implementation phase will copy it into `tools/d2net/src/D2Net.Init/pgbridge/server.mjs` (or similar) as the runtime asset; any deviation from its protocol handling MUST be justified against the failure-analysis document at `docs/research/pglite-pg-gateway-odbc-failure-analysis.md`.
- The recommended .NET-side Postgres client is **Npgsql** (per the RCA's "Recommend Npgsql over ODBC inside .NET" guidance). The current `D2Net.Init` `csproj` references `Microsoft.Data.Sqlite` and will swap to `Npgsql` (currently 8.x, the version verified in the RCA). psqlODBC is supported but not used by `D2Net.Init` itself.
- The default bridge port `54400` is chosen for consistency with the published reference (`docs/research/pgbridge-reference/README.md`'s example uses port 54400). It does not collide with the standard Postgres port 5432, with the modern PGLite-tooling convention 54321, or with the macOS Time Machine / standard developer-tooling ports we are aware of. Callers in environments with port conflicts are expected to use `--bridge-port`.
- The minimum supported Node.js version is whichever LTS the implementation phase verifies against (Node.js 24.14.0 was the version used during the RCA; LTS Node.js 20 is the most likely floor). The exact floor is a plan-time decision and will be documented in the install README; this spec only requires that the minimum is enforced and reported.
- "Single-user" semantics from the shipped spec are preserved: only one D2NET command may operate on the workspace at a time, and the per-invocation bridge lifecycle naturally enforces this (the second invocation cannot bind the port). True multi-tenant isolation is not in scope.
- The PGLite database, bridge user/password (`d2net`/`d2net`), and bind address (`127.0.0.1`) are not security boundaries; they are placeholders to satisfy Postgres-style connection-string completeness on a per-developer local file-backed DB. No password rotation, no remote bind, no TLS termination is in scope.
- **Supported hosts (v1)**: Windows is the only release-blocking host. The acceptance scenarios, success criteria (SC-001 through SC-010), and FR-011's psqlODBC clause apply as hard requirements **only** on Windows. macOS and Linux are "expected to work but unverified" — bug reports accepted, fixes welcome, but failures on those hosts do not block release. (The RCA was run on Windows 11 Pro 10.0.26200; the `STATUS_STACK_BUFFER_OVERRUN` regression that SC-005 guards against is a Windows-specific artefact, and the modern psqlODBC `PostgreSQL ODBC Driver(UNICODE)` likewise.) macOS/Linux verification — including the corresponding iODBC/unixODBC + psqlODBC story — is tracked as a follow-up, not as part of this feature.
- All other assumptions from `specs/002-d2net-init/spec.md` (cross-platform .NET runtime, forward-slash path normalisation, exclusion-marker substring set, `--current-phase` semantics, etc.) carry forward unchanged. The 002 spec's "cross-platform .NET" note is narrowed by this feature to "Windows hard-guaranteed; macOS/Linux best-effort" until separately re-verified.
- The upgrade is scoped to **`D2NET.Init`** only. Companion commands (`D2NET.Scaffold` and any future `D2NET.Analyze`/`D2NET.Port`/etc.) remain on their currently shipped storage choice until separately re-targeted at the PGLite workspace; making them PGLite-aware is out of scope for this feature.

## Out of Scope

- **Online migration of an existing SQLite-format `.D2NET` to PGLite.** Existing workspaces are recreated from scratch via `--FORCE --DELETE-EXISTING`. The cost is one rewalk of the source tree, which the shipped SC-001 already budgets at 10 seconds for 500 `.dart` files; this is well below any threshold that would justify a one-shot ETL tool.
- **Long-running daemon bridge.** The shipped per-invocation bridge model (one Node.js subprocess per D2NET command) is preserved verbatim. A "keep the bridge alive between commands" optimisation is intentionally not pursued: it adds inter-process state, lifecycle bugs, and debug surface for a one-time-per-command startup cost of a few hundred milliseconds.
- **Updating `D2NET.Scaffold` (or any other companion command) to use the PGLite workspace.** Only `D2NET.Init` is upgraded by this feature.
- **Contributing fixes upstream to `pg-gateway` or PGLite.** The RCA documents two upstream bugs and good-citizen TODOs for both; that work is explicitly tracked in the RCA document and is not part of this feature.
- **Authenticated, encrypted, or multi-tenant access to the PGLite database.** The bridge accepts only `127.0.0.1` connections, replies `N` to `SSLRequest`, and accepts the placeholder `d2net`/`d2net` credentials.
