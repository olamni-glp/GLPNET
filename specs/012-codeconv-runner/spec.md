# Feature Specification: codeconv-runner — overarching codeconv harness with unified `.pgdb` backing

**Feature Branch**: `012-codeconv-runner`
**Created**: 2026-05-09
**Status**: Draft
**Input**: User description (consolidated across the dialog opening this feature):

1. "create an overarching /codeconv-runner skill and python tool using dbos with pglite backing exactly as in hatzinor/ulpani and in BREENDEV/aigrid INFRA opskit-init skill and tool to run individual code conversion codeconv tools and create an initial /codeconv-discover that reads all the .dart source code in this repo and builds up a pglite inventory of each in the pglite config instance in this repo and also create in a sub dir a full set of inventory tombstones for all dart files with path, name, purpose, key idea/algorithm approach, and also known dependencies of a file and known downstream users/callers of the file from which the DB record can always be rapidly rebuilt"
2. "create a new PGDB folder in the repo root and move the .D2NET/pgdb/ instance there and rewrite the bridge to look there and adapt .D2NET to work with the new bridge and location. We must implement file-based semaphore/lock to ensure the db instance files are and can only ever be used by one WASM and PGLite bridge at a time. The bridge must implement a single session pool as PGLite can only handle one call/transaction at a time and call/txn must therefore be queued."

## Context

Glpnet has a working merged PGLite Postgres-wire bridge at `prereq-patterns/pglite/pglite_bridge.mjs` (delivered by feature 011, the prereq-patterns catalog). The bridge already handles in-process serialisation across all client connections via a `globalWorkChain`, hand-rolls the Postgres-wire startup handshake (no `pg-gateway`), buffers protocol frames to flush boundaries before forwarding to PGLite's `execProtocolRaw()`, and confirms compatibility with both Python (`psycopg` / SQLAlchemy / DBOS) and .NET (`Npgsql` / `psqlODBC`) consumers per `prereq-patterns/pglite/applicability.md`.

What is missing today: (a) **cross-process exclusion** — there is no mechanism preventing a second bridge process from opening the same data directory while a first is running; (b) a **canonical, repo-wide PGLite location** — D2NET runs its own per-workspace PGLite under `.D2NET/pgdb/`, and any future codeconv tooling would naively copy the bridge into its own working tree, leaving the repo with multiple disjoint PGLite stores; (c) an **overarching code-conversion harness** — there is no skill or Python tool that registers and runs individual code-conversion tools against shared inventory state; and (d) any **inventory of the Dart code that requires conversion**.

This feature delivers (a) through (d) in one step. It evolves the prereq-pattern into a single repo-wide deployment at `.pgdb/`, adds OS-level cross-process locking around it, migrates the existing `.D2NET/pgdb/` data into it without loss, converts D2NET to connect to the unified bridge instead of launching its own, then layers on a `/codeconv-runner` slash command + Python tool (using DBOS for durable execution and SQLAlchemy with the prereq-pattern's PGLite engine kwargs) that registers individual codeconv tools as sibling slash commands. The first registered tool is `/codeconv-discover`, which walks `D:\BSTDEV\research\GLP\GLPNET\glp_runtime_net\` (and descendants) for `.dart` files, populates a `codeconv` schema in PGLite with one inventory row per file plus dependency and caller edges, and writes per-file Markdown tombstones at `.codeconv/tombstones/<rel-path>.md`. The tombstones are designed so dropping the `codeconv` schema and re-running discover with `--from-tombstones` reproduces the inventory.

The reference implementations are already in this developer's universe: the BREENDEV `opskit-init` skill at `D:\BREENDEV\aigrid\AWS-Infra\.claude\skills\opskit-init\SKILL.md` provides the slash-skill-as-thin-wrapper-around-CLI pattern (the CLI is the source of truth; the skill forwards arguments verbatim). The hatzinor/ulpani Python application at `D:\BSTDEV\lang\hatzinor_ai-ddp\ulpani\` provides the DBOS / SQLAlchemy / Alembic-on-PGLite engine recipe (via the `pglite_engine_kwargs` helper, the `_apply_pglite_compat_patch()` shim for DBOS's `migration_one`, and the `pglite_compat_loaders.py` `timestamptz` / `timestamp` parser fix that all consumers in unified `.pgdb/` MUST install).

## Clarifications

### Session 2026-05-09

- Q: Where does the unified PGLite data directory live? → A: **Repo-root `.pgdb/`** (hidden, alongside `.D2NET/`, `.claude/`, `.specify/`).
- Q: What is the granularity of the cross-process lock? → A: **Single bridge process per repo.** First bridge wins, holds the lock for its lifetime; all clients connect to that one bridge. Second-bridge attempts fail fast.
- Q: Stale-lock recovery story? → A: **OS-level lock via `proper-lockfile` (npm).** Kernel releases the lock automatically on process exit, eliminating the need for stale-lock heuristics.
- Q: How does D2NET adapt to the new location? → A: **D2NET converts to a connect-to-existing-bridge client.** D2NET no longer launches its own bridge; it acquires the lock and spawns the unified bridge if no other client has yet, otherwise it reads `.pgdb/bridge.json` and connects.
- Q: Existing `.D2NET/pgdb/` data — preserve or recreate? → A: **Preserve.** Migration is a move (rename), not a re-create. A backup is taken before the move so the operation is reversible.
- Q: Where do tombstones live and in what format? → A: **`.codeconv/tombstones/<rel-path>.dart.md`** as Markdown with YAML frontmatter (`path`, `name`, `purpose`, `key_idea`, `dependencies`, `callers`, `mtime`, `sha256`).
- Q: Scope of "all .dart source"? → A: **Only `D:\BSTDEV\research\GLP\GLPNET\glp_runtime_net\` and its descendants.** Files outside that subtree are originals/duplicates and MUST be excluded.
- Q: What does codeconv eventually convert to? → A: **Dart → C# / .NET** in this repo.
- Q: Does `/codeconv-discover` populate `purpose` and `key_idea`, or are those deferred? → A: **Mechanical-only on first pass.** Discover seeds `purpose` and `key_idea` from the file's leading documentation comment block verbatim if present, otherwise leaves them blank. Semantic enrichment (LLM-backed inference of purpose / algorithm) is out of scope for `/codeconv-discover` and reserved for a future codeconv-* tool.
- Q: Bridge lifecycle — manual launcher or auto-spawn-on-demand? → A: **Auto-spawn-on-demand.** Every client (D2NET, codeconv, future tools) attempts to acquire the bridge lock at process start; if it acquires, it spawns the bridge as a detached background process and waits for `BRIDGE_READY`; if the lock is already held, it reads `.pgdb/bridge.json` and connects. A manual launcher script is provided as an operator escape hatch but is not the primary path.
- Q: Schema isolation in unified `.pgdb/`? → A: **Triple-isolated.** D2NET keeps whatever schema(s) it currently uses; codeconv tables go in a `codeconv` schema; DBOS uses its standard `dbos` schema. Each client sets `search_path` accordingly. No tenant collides on `public`.
- Q: D2NET migration boundary? → A: **Only `.D2NET/pgdb/` moves to `.pgdb/`.** The rest of `.D2NET/` (notably `D2NET-Settings.json`) stays in place. D2NET remains a multi-workspace concept (one `.D2NET/` per workspace), but PGLite is now repo-wide and shared.
- Q: Caller-graph scope? → A: **Inside-only.** The caller graph for files in `glp_runtime_net/` is computed only over imports BY other files in `glp_runtime_net/`. Imports from files outside the subtree are an anomaly — discover MUST emit a warning and MUST NOT record them as caller edges.
- Q: Performance SLO for `/codeconv-discover`? → A: **≤ 60 s on a fresh checkout (128 files), ≤ 5 s on idempotent re-run.**
- Q: Row uniqueness on `dart_imports` / `dart_callers`? → A: **UNIQUE `(from_path, to_path)` on both tables.** Duplicate `import` directives in a single Dart file are warned in the discover log and deduplicated to one row.
- Q: Git status of `.pgdb/` and `.codeconv/`? → A: **`.pgdb/` entirely gitignored**; **`.codeconv/tombstones/` checked in** (including `.codeconv/tombstones/.orphaned/`); **`.D2NET/pgdb.bak.*/` migration-backup directories gitignored.**
- Q: Orphan re-appearance? → A: **Revive.** A previously-orphaned `.dart` file that reappears at the same path is moved back from `dart_files_orphaned` to `dart_files` and from `.codeconv/tombstones/.orphaned/` to `.codeconv/tombstones/`, with `mtime` and `sha256` refreshed from the new file. Edges are recomputed normally.
- Q: Bridge log destination? → A: **`.pgdb/bridge.log`** with size-based rotation (~5MB × 3 retained). The `BRIDGE_READY` token is captured over a pipe by the spawning client BEFORE the bridge detaches; post-detach, nothing leaks into the spawning client's terminal.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Repo-wide unified PGLite with cross-process exclusion (Priority: P1)

A developer working in this repo opens any client that wants to talk to PGLite — `D2NET-init`, `D2NET-scaffold`, the future `/codeconv-runner` Python tool, or a one-off SQL session via `psql` against the bridge — and that client connects to a single PGLite WASM session backed by the repo-root `.pgdb/` directory. There is exactly one running bridge process per repo at any moment. If a second instance attempts to start, it fails fast with a clear error naming the running bridge's PID. If the running bridge dies, the OS releases the lock automatically and the next client to start succeeds without manual cleanup.

**Why this priority**: Without this, every other story in this spec is unsafe — concurrent bridges on the same data directory corrupt PGLite. This is the precondition layer.

**Independent Test**: On a fresh checkout, run two parallel scripts that each try to start the bridge against `.pgdb/`. Exactly one succeeds and serves clients; the other exits within 1 second with an error message identifying the holder. Killing the winning bridge process and immediately retrying succeeds without manual lock cleanup.

**Acceptance Scenarios**:

1. **Given** a fresh checkout with no prior bridge state, **When** a client invokes any tool needing PGLite, **Then** the tool acquires the lock at `.pgdb/.bridge.lock`, spawns the bridge as a detached background process, waits for the `BRIDGE_READY port=<n> pid=<p>` token, writes `.pgdb/bridge.json` with `{port, pid, started_at}`, and proceeds with normal work.
2. **Given** a bridge is already running for this repo, **When** a second client invokes a tool needing PGLite, **Then** the second client fails to acquire the lock, reads `.pgdb/bridge.json`, opens a TCP connection to the listed port, and connects to the same PGLite session as the first client (without spawning a second bridge).
3. **Given** a running bridge process is force-killed (no graceful shutdown), **When** a new client invokes a tool needing PGLite, **Then** the new client successfully acquires the released lock within 1 second and spawns a fresh bridge against the same `.pgdb/` directory.
4. **Given** two clients are connected to the running bridge, **When** they fire concurrent transactions (Python via psycopg + .NET via Npgsql, or two of the same), **Then** the bridge's in-process serialisation chain orders all work safely and neither client sees `lost synchronization with server` errors over 100 sequential cycles.

3. **Given** a `/codeconv-*` workflow is interrupted (process kill, machine reboot), **When** the same command is re-invoked, **Then** DBOS resumes the workflow from the last durable checkpoint without re-running already-completed steps.

### Edge Cases

- **Bridge process killed during a transaction**: The OS releases the lock; in-flight clients see TCP-level disconnects. Their next call reconnects (auto-spawning a new bridge if necessary). PGLite's data dir is consistent because PGLite's own writes are atomic at the storage layer (PGLite's standard model, not an invariant added by this feature).
- **Two clients race to acquire the lock**: `proper-lockfile`'s OS-level primitive resolves the race deterministically; exactly one wins, the other reads the sidecar JSON.
- **Sidecar JSON stale (lock-holder crashed before writing it, or wrote it then died)**: Clients MUST treat absence-of-lock as authoritative. If the sidecar exists but the lock is unheld, clients ignore the sidecar and re-acquire the lock themselves.
- **`.D2NET/pgdb/` has been moved manually before this feature lands**: Migration detects an absent source and exits successfully (no-op).
- **`.pgdb/` already exists and is non-empty before migration runs**: Migration refuses and surfaces a clear message; the operator decides whether to delete `.pgdb/` (forfeit) or move it aside before retry.
- **Tombstone hand-edited by a developer between discover runs**: `purpose` and `key_idea` are populated mechanically (verbatim doc-comment) and are overwritten on re-run if the underlying doc-comment changed; engineer-curated semantic content (intended for the future enrichment tool) is NOT supported by this feature's tombstone format and would be lost. Engineers wanting to preserve hand-written semantics MUST use the future enrichment tool's protocol (out of scope here).
- **`.dart` file is unreadable (permissions, broken symlink)**: Discover logs the file path and the error, skips it, and proceeds. The summary at end of run includes a count of skipped files; the workflow exit code is non-zero only if all files were skipped.
- **Symlink inside `glp_runtime_net/` pointing outside the subtree**: Treated as outside-the-subtree; not followed; not recorded.
- **DBOS migration runs against the unified `.pgdb/` for the first time**: `_apply_pglite_compat_patch()` handles the missing `uuid-ossp` extension. DBOS's tables go into the `dbos` schema. D2NET's tables (in their existing schema(s)) are unaffected.
- **PGLite refuses `COPY ... FROM STDIN`**: Per the prereq-pattern, this is unconditionally unsupported. No part of this feature MAY issue `COPY FROM STDIN`.
- **Duplicate `import` directives in a single Dart file**: Discover emits a warning naming the source file and the duplicated target, then deduplicates to one `(from_path, to_path)` row per FR-019.
- **Previously-orphaned `.dart` file reappears at the same path**: Revived per FR-025 — row moved back from orphaned table, tombstone moved back from `.orphaned/`, both refreshed with new `mtime` + `sha256`.
- **Bridge log directory unwritable or full**: Bridge emits a warning over its still-connected pipe to the spawning client BEFORE detach, then continues serving without log writes per FR-030; log-write failure MUST NOT block client work.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001 (unified data directory)**: A single PGLite data directory MUST exist at `.pgdb/` at the repo root (peer of `.D2NET/`, `.claude/`, `.specify/`). All clients in this repo MUST use this directory and no other for repo-wide PGLite work.
- **FR-002 (single bridge per repo)**: At most one bridge process MAY be active for `.pgdb/` at any time. Enforcement MUST be by an OS-level lock at `.pgdb/.bridge.lock` whose acquisition and release are kernel-managed (no PID + heartbeat heuristic).
- **FR-003 (lock release on crash)**: If the bridge process dies (graceful exit, signal, hard kill, host crash), the lock MUST be released by the OS automatically; no manual cleanup may be required for the next bridge to start.
- **FR-004 (sidecar discovery)**: The lock-holding bridge MUST write a sidecar JSON file at `.pgdb/bridge.json` containing at least `{port: <integer>, pid: <integer>, started_at: <ISO-8601 timestamp>}` immediately after it begins listening, and clients that fail to acquire the lock MUST read this file to discover where to connect.
- **FR-005 (in-process serialisation preserved)**: The bridge MUST preserve the in-process serialisation already implemented in `prereq-patterns/pglite/pglite_bridge.mjs` (the `globalWorkChain` global FIFO across all connections, the per-frame buffering to `endsAtFlushBoundary()`, the synthetic `ROLLBACK` on each new TCP connection, and PGLite pinned at `@electric-sql/pglite@0.2.17`). No regression of these behaviours is acceptable.
- **FR-006 (auto-spawn-on-demand bridge lifecycle)**: Every PGLite-using tool in this repo MUST follow this start-up protocol: (1) attempt to acquire the OS-level lock at `.pgdb/.bridge.lock`; (2) if acquired, spawn the bridge as a detached background process, wait for `BRIDGE_READY port=<n> pid=<p>` on stdout (or up to a timeout, default 10 seconds), confirm `.pgdb/bridge.json` is written, then proceed; (3) if not acquired, read `.pgdb/bridge.json` and connect via TCP to the listed port. A manual launcher script MUST also exist as an operator escape hatch but is NOT the primary path.
- **FR-007 (.D2NET/pgdb migration: data preserved)**: An automated migration step MUST move (rename, not copy) `.D2NET/pgdb/` to `.pgdb/`, taking a backup of the source at a timestamped sibling path before the move so the operation is reversible. The migration MUST NOT modify any other content under `.D2NET/` (notably `.D2NET/D2NET-Settings.json`).
- **FR-008 (.D2NET/pgdb migration: refuse on conflict)**: The migration MUST refuse to run if `.pgdb/` already exists with non-empty content; it MUST surface a clear message naming both paths and asking the operator to resolve the conflict manually.
- **FR-009 (.D2NET/pgdb migration: idempotent)**: Re-running the migration when `.D2NET/pgdb/` is absent MUST exit successfully with a no-op message. Migration MUST NOT depend on out-of-band state (e.g., a "migrated" flag file).
- **FR-010 (D2NET converts to unified-bridge client)**: D2NET tooling under `tools/d2net/` (notably `D2Net.Init`, `D2Net.Scaffold`, and any related .NET projects) MUST be modified so it no longer launches its own PGLite bridge process. Instead, D2NET MUST follow the auto-spawn-on-demand protocol from FR-006 against `.pgdb/`.
- **FR-011 (D2NET regression-free behaviour)**: All existing D2NET commands and downstream operations MUST produce the same observable outcomes (database state, files written, exit codes, logged messages where consequential) before and after migration. The only acceptable difference is the connection target.
- **FR-012 (canonical bridge file)**: The bridge file at `prereq-patterns/pglite/pglite_bridge.mjs` MUST remain the single source of truth for the bridge implementation. The OS-level lock acquisition + sidecar JSON writing + auto-spawn-aware lifecycle MUST be added to this file (not to a parallel copy). The `prereq-patterns/pglite/description.md` policy that "adapting the pattern means copying the cited files into your feature" MUST be amended in this feature to reflect that, repo-wide, the canonical bridge is also the live deployment when run against `.pgdb/`.
- **FR-013 (`/codeconv-runner` skill — slash + CLI)**: A Claude Code skill `/codeconv-runner` MUST exist as a thin wrapper around the underlying `codeconv` Python CLI, following the same wrapper pattern as BREENDEV's `/opskit-init`. The slash form MUST forward arguments to the CLI verbatim and not interpret them.
- **FR-014 (codeconv Python tool — DBOS over PGLite)**: The codeconv Python package MUST use DBOS for durable execution and SQLAlchemy as the engine layer, configured via the prereq-pattern's `pglite_engine_kwargs(application_name='codeconv')` helper. `_apply_pglite_compat_patch()` MUST be applied before DBOS first migration. `apply_to_engine(engine)` (the `pglite_compat_loaders` patch) MUST be installed on every engine the tool creates so `timestamptz` and `timestamp` reads do not crash psycopg.
- **FR-015 (schema isolation)**: The codeconv tool MUST place all of its persistent tables in a `codeconv` PGLite schema (created by codeconv's own migrations). It MUST NOT create tables in `public`. DBOS's tables MUST stay in DBOS's standard `dbos` schema. D2NET's tables MUST remain in whichever schema(s) D2NET currently uses; no D2NET schema rewrite is permitted as part of this feature.
- **FR-016 (tool registry by file-system convention)**: The runner MUST discover individual codeconv tools by scanning `codeconv/tools/<name>/` for modules that expose a registered tool class. Each registered tool MUST be invocable both as `/codeconv-<name>` (separate Claude Code skill at `.claude/skills/codeconv-<name>/SKILL.md`, also a thin wrapper) AND as a positional argument to the runner CLI (`codeconv <name> ...`). Adding a new tool MUST require no edits to the runner's own code.
- **FR-017 (durable workflows)**: Every codeconv tool's main work MUST be wrapped in a DBOS workflow such that interrupting the process and re-invoking the same command resumes from the last durable step. No tool MAY proceed past durability boundaries with non-idempotent operations.
- **FR-018 (`/codeconv-discover` — scope)**: `/codeconv-discover` MUST scan `D:\BSTDEV\research\GLP\GLPNET\glp_runtime_net\` and all descendants for files with extension `.dart`. It MUST NOT process any `.dart` file outside that subtree. It MUST exclude generated artifacts (`*.g.dart`, `*.freezed.dart`, `*.gen.dart`) and any path containing `.dart_tool/` or `build/` segments.
- **FR-019 (`/codeconv-discover` — inventory schema)**: For each discovered `.dart` file, discover MUST insert or update one inventory row in `codeconv.dart_files` with at least: `path` (relative to `glp_runtime_net/`), `name` (file basename), `purpose` (verbatim leading doc-comment block, or empty), `key_idea` (verbatim — same value as `purpose` when a single block, blank otherwise), `mtime`, `sha256`. Discover MUST also populate `codeconv.dart_imports` and `codeconv.dart_callers`, both with a `UNIQUE (from_path, to_path)` constraint. `dart_imports` carries one row per unique `(from_path, to_path)` pair where the from-path's file contains an `import` directive resolving to to-path inside the subtree; duplicate import directives in a single Dart file MUST be warned in the discover log and deduplicated to one row. `dart_callers` has the same shape and uniqueness, computed as the inverse of `dart_imports`.
- **FR-020 (`/codeconv-discover` — semantic-field policy)**: `purpose` and `key_idea` MUST be populated mechanically only — verbatim from the leading doc-comment block of the file. Discover MUST NOT use heuristics, AI inference, or any non-deterministic source for these fields. Engineer- or AI-curated semantic enrichment is reserved for a future codeconv-* tool not delivered by this feature.
- **FR-021 (`/codeconv-discover` — tombstones)**: For each discovered `.dart` file, discover MUST write one Markdown tombstone at `.codeconv/tombstones/<rel-path>.dart.md` (where `<rel-path>` is the file's path relative to `glp_runtime_net/`, with `.dart` replaced by `.dart.md`). Each tombstone MUST contain YAML frontmatter with at minimum: `path`, `name`, `purpose`, `key_idea`, `dependencies` (list of relative paths), `callers` (list of relative paths), `mtime`, `sha256`. The body of the tombstone MUST be the verbatim doc-comment block, or empty.
- **FR-022 (`/codeconv-discover` — rebuild from tombstones)**: `/codeconv-discover --from-tombstones` MUST read every tombstone in `.codeconv/tombstones/`, populate the `codeconv` schema from the YAML frontmatter alone (no `.dart` source reading), and exit successfully. The result MUST be identical to running discover normally on the same source state.
- **FR-023 (`/codeconv-discover` — caller-graph scope)**: When computing `dart_callers`, discover MUST look only at imports BY other files inside `glp_runtime_net/`. If discover detects an import BY a file outside the subtree pointing INTO the subtree, it MUST emit a warning to its log naming both files but MUST NOT record a caller edge for it.
- **FR-024 (`/codeconv-discover` — idempotence)**: Re-running `/codeconv-discover` against an unchanged source state MUST produce zero diff in `codeconv.dart_files`, `codeconv.dart_imports`, `codeconv.dart_callers`, and `.codeconv/tombstones/`.
- **FR-025 (`/codeconv-discover` — orphan handling and revival)**: If a `.dart` file disappears between discover runs, discover MUST handle the orphaned inventory row and tombstone consistently: the inventory row is moved to `codeconv.dart_files_orphaned` (same columns plus an `orphaned_at` timestamp) and the tombstone is moved from `.codeconv/tombstones/<rel>.dart.md` to `.codeconv/tombstones/.orphaned/<rel>.dart.md`. If a previously-orphaned file later reappears at the same path on a subsequent run, discover MUST revive it: the row is moved back from `dart_files_orphaned` to `dart_files` and the tombstone is moved back from `.orphaned/` to `.codeconv/tombstones/`, both with `mtime` and `sha256` refreshed from the new file. Dependency and caller edges are recomputed normally for revived files. Orphans MUST NOT be silently ignored.
- **FR-026 (no `COPY FROM STDIN`)**: No code introduced by this feature MAY issue `COPY ... FROM STDIN` against PGLite under any circumstance, per the prereq-pattern's unconditional restriction.
- **FR-027 (no client-side prepared-statement caching)**: Every PGLite client introduced by this feature MUST disable prepared-statement caching per the prereq-pattern's per-consumer guidance: psycopg-style consumers via `prepare_threshold=None`; Npgsql via `Pooling=false`; psqlODBC via the documented connection-string flags. No client may run `Prepare` against the unified bridge.
- **FR-028 (target language for codeconv)**: The codeconv pipeline's eventual conversion target in this repo is C# / .NET. This feature does not deliver any Dart→C# conversion logic; only the `discover` tool and the runner harness are in scope. Future codeconv tools (e.g. `/codeconv-translate`, `/codeconv-validate`, semantic enrichment) are explicitly out of scope here.
- **FR-029 (.gitignore policy)**: The repo's `.gitignore` MUST exclude `.pgdb/` entirely (the PGLite cluster files are binary, machine-local, and rebuildable from migrations + tombstones). It MUST exclude any timestamped migration-backup directories created by FR-007 (e.g. `.D2NET/pgdb.bak.*/`). It MUST NOT exclude `.codeconv/tombstones/` (the canonical artefact set for rebuild-from-tombstones), and MUST NOT exclude `.codeconv/tombstones/.orphaned/` (so orphan history is reviewable in pull requests).
- **FR-030 (bridge log destination)**: The bridge process MUST write all stdout and stderr produced after detach to `.pgdb/bridge.log`. The log file MUST rotate by size (default ~5MB per file × 3 retained generations). The `BRIDGE_READY port=<n> pid=<p>` token MUST still be captured by the spawning client over a pipe BEFORE the bridge detaches, so the client can proceed; once detached, no bridge output may leak into the spawning client's terminal. If the log directory is full or otherwise unwritable at startup, the bridge MUST emit a warning over its still-connected pipe to the spawning client and continue serving — log-write failure MUST NOT block bridge work.

### Key Entities

- **Unified PGLite data directory (`.pgdb/`)**: The single repo-root directory holding the PGLite cluster files. Identified by location. Owns the bridge lock, the sidecar JSON, and the WASM session's on-disk state.
- **Bridge process**: A Node.js process running the canonical bridge (`prereq-patterns/pglite/pglite_bridge.mjs`) against `.pgdb/`. At most one is active per repo. Identified by PID.
- **Bridge lock**: An OS-level lock at `.pgdb/.bridge.lock`. Held by the bridge process for its lifetime; released by the kernel on process exit. Granularity is whole-data-directory, not per-table or per-connection.
- **Bridge sidecar**: A JSON file at `.pgdb/bridge.json` written by the lock-holding bridge after it begins listening. Carries `{port, pid, started_at}` (and possibly a hostname for parity with the prereq-pattern's `sidecar.json` convention). Read by clients that lose the lock race.
- **Codeconv schema**: A PGLite schema named `codeconv` housing inventory tables (`dart_files`, `dart_imports`, `dart_callers`, `dart_files_orphaned`) plus the codeconv-specific migrations metadata. DBOS-managed durable-workflow tables live separately in DBOS's own `dbos` schema, not in `codeconv`.
- **Codeconv runner**: The Python CLI + Claude Code slash skill (`/codeconv-runner`) that orchestrates registered tools through DBOS workflows.
- **Codeconv tool**: A registered Python module under `codeconv/tools/<name>/` that exposes a tool class implementing the runner's tool contract. Each tool has a sibling slash skill `/codeconv-<name>` (thin wrapper) and is invocable via the runner CLI.
- **Inventory row (`codeconv.dart_files`)**: One row per `.dart` file inside `glp_runtime_net/`. Keyed by relative path. Carries name, doc-comment-derived purpose / key_idea (verbatim), mtime, sha256.
- **Dependency edge (`codeconv.dart_imports`)**: One row per `import` directive in a Dart file pointing at another file inside `glp_runtime_net/`. From-path × to-path.
- **Caller edge (`codeconv.dart_callers`)**: The inverse view of `dart_imports`, denormalised into its own table for query convenience. From-path × to-path (where from is the caller). Computed inside the subtree only.
- **Tombstone**: A Markdown file at `.codeconv/tombstones/<rel-path>.dart.md` carrying YAML frontmatter (mirroring the inventory row + edges) and a body containing the verbatim doc-comment block. Sufficient on its own to reconstruct the inventory row + edges via `--from-tombstones`.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001 (single bridge guarantee)**: A second attempt to start the bridge against `.pgdb/` while a first is running exits within 1 second with a clear error message that names the holder's PID and the path of the lock file. Verified by running two parallel bridge starts.
- **SC-002 (lock auto-release)**: After the bridge process is force-killed (SIGKILL on POSIX / `Stop-Process -Force` on Windows), a fresh bridge start succeeds within 1 second without any manual cleanup of `.pgdb/.bridge.lock`. Verified by a kill-and-restart cycle in test.
- **SC-003 (concurrent client safety)**: Two clients of different stacks (one Python via psycopg, one .NET via Npgsql, both following the queue-of-one config from the prereq-pattern) running 100 sequential transactions each against the unified bridge produce zero `lost synchronization with server` errors, zero `DuplicatePreparedStatement` errors, and zero data corruption.
- **SC-004 (D2NET migration: data preserved)**: After migration, `SELECT count(*)` on every table that existed in `.D2NET/pgdb/` returns the same value when run against `.pgdb/`. A timestamped backup of the original data exists at a recorded path.
- **SC-005 (D2NET regression-free)**: Every D2NET command that worked before migration works after migration without modification beyond the connection target. Verified by running the existing D2NET test suite (or the highest-coverage smoke set if no full suite exists) end-to-end.
- **SC-006 (codeconv-discover: completeness on golden subtree)**: Running `/codeconv-discover` on a fresh checkout against `glp_runtime_net/` produces exactly 128 rows in `codeconv.dart_files` (matching the file count) and exactly 128 tombstone files at `.codeconv/tombstones/`. Files outside `glp_runtime_net/` are not represented.
- **SC-007 (rebuild-from-tombstones bit-for-bit)**: Dropping the `codeconv` schema and running `/codeconv-discover --from-tombstones` reproduces `codeconv.dart_files`, `codeconv.dart_imports`, and `codeconv.dart_callers` such that a logical dump (`pg_dump --schema=codeconv`, schema-only + data, with timestamp-typed columns excluded) of the rebuilt state is byte-identical to the same dump taken before the schema drop.
- **SC-008 (discover idempotence)**: Running `/codeconv-discover` twice in a row on an unchanged source state produces zero row diff in any `codeconv.*` table and zero file diff in `.codeconv/tombstones/`.
- **SC-009 (durability: discover resumes)**: Killing `/codeconv-discover` after it has processed N files (N < 128) and re-invoking the same command completes the run without re-processing the first N files. Verified by an instrumented run that records per-file progress.
- **SC-010 (skill discoverability)**: Typing `/codeconv-` in Claude Code's slash menu surfaces both `/codeconv-runner` and `/codeconv-discover` (and any future `/codeconv-<name>` siblings the runner registers) without any extra configuration step.
- **SC-011 (caller-graph correctness scope)**: For every Dart file in `glp_runtime_net/`, the union of its `dart_callers` rows is a strict subset of `glp_runtime_net/` paths. Any import BY a file outside the subtree is recorded only as a warning in the discover log, never as a caller edge. Verified by query.
- **SC-012 (no leaks across schemas)**: After full feature is in place, `\dn` against the unified PGLite shows at minimum `dbos`, `codeconv`, and whatever schema(s) D2NET uses; no codeconv table appears outside `codeconv`, and no DBOS table appears outside `dbos`.
- **SC-013 (discover performance SLO)**: On a fresh checkout against `glp_runtime_net/` (128 files), `/codeconv-discover` MUST complete within 60 seconds wall-clock from invocation to summary print. On an idempotent re-run against the same unchanged source state, `/codeconv-discover` MUST complete within 5 seconds.

## Assumptions

- The merged bridge at `prereq-patterns/pglite/pglite_bridge.mjs` (delivered by feature 011) is the right starting point. This feature evolves it with cross-process locking + sidecar JSON + auto-spawn-aware lifecycle, not from scratch.
