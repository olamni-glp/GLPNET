# Feature Specification: D2NET.Scaffold — Source-Tree Mirror with Per-Dart-File Working Directories

**Feature Branch**: `009-scaffold-mirror`
**Created**: 2026-05-01
**Status**: Draft
**Input**: User description: "refactor D2NET.Scaffold to take the settings for source and target directory and target dir extension from the settings created by D2NET-init. The tool must be refactored to ensure all excluded directories from D2NET-init settings and their child directories are not copied to the target. For each directory in src not excluded copy all files to the target including the .dart files. For each .dart file create a subdirectory in the same directory as that dart file with a name that is the name of the .dart file prefixed with `__` (two underscores) and the .dart extension removed. So for `glp_repl.dart` the directory should be `__glp_repl`. The directory name should be added as a new column to the dart_files table in the PGLite db and the actual name be recorded there. Check also that that table has a column with the full path so for `glp_repl.dart` there should be a column where for that row `D:\BSTDEV\research\GLP\GLPNET\glp_runtime\bin` is recorded for that file as the path to the dart file and its `__`-prefixed working directory."

## Clarifications

### Session 2026-05-01

- Q: What path-separator policy should the new `target_parent_dir` column use? → A: Native separators (Windows `\`, POSIX `/`), absolute path. Confirmed: matches the operator's explicit example in the original spec input, is operationally useful for shell scripts and host-OS tooling, and the workspace database is single-user and tied to a specific local source tree (cross-OS portability of this column is not a real requirement). The existing `full_path` column stays forward-slash repo-rooted for cross-OS portability of indexing metadata.
- Q: How should scaffold mark a target tree as "scaffold-managed" (FR-012's detection mechanism)? → A: Hybrid — a workspace-database row is the authoritative tracker; a small sentinel file inside the target tree (e.g., `<target>/.d2net-scaffold-tracker`) is a non-semantic visual marker. FR-012's "is this target ours?" check consults the DB row (transactional, atomic with `dart_files` updates, queryable). The sentinel file is purely a hint for operators browsing the target tree on disk; it carries no authority and may be deleted without affecting scaffold correctness. On `--FORCE --DELETE-TARGET`, the sentinel file dies with the target tree (good); the DB row is cleared as part of the destructive flow's atomic transaction (so the next scaffold sees a clean tracker state). Implementation may use a `setting` row (suggested key: `scaffold.target_inventory_hash`) or a small `scaffold_tracker` table for the authoritative side; choice deferred to plan.
- Q: What atomicity mechanism should scaffold use for the filesystem mutations? → A: Staging directory + atomic rename. Write all new content to `<target>.d2net-tmp/` first; on the database COMMIT for the same run, atomically rename the staging directory over the live target. On any failure before COMMIT, delete the staging directory; the live target is never in a half-written state. Confirmed: mirrors features 007/008's write-temp-then-rename pattern at directory granularity, makes failure rollback trivial, and the temporary 2× disk usage is acceptable for the SC-001 ceiling of 1,000 dart + 5,000 non-dart files.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Mirror the source tree to the target, honouring exclusions and creating per-dart-file working directories (Priority: P1)

A developer working on a D2NET conversion has already initialised the workspace with `d2net-init` (specifying source `glp_runtime`, target extension `_net`, target directory `glp_runtime_net`, and an approved exclusion list). They now invoke `d2net-scaffold` with no arguments. The tool reads the source directory name, target directory name, target extension, and the full exclusion list directly from the workspace (via `.D2NET/D2NET-Settings.json` and the workspace database), walks the on-disk source tree skipping every excluded directory and all of its descendants, and produces a target directory tree that mirrors the non-excluded parts of the source. Every file in a non-excluded directory — `.dart` files and every other extension — is copied into the corresponding location in the target. For each `.dart` file copied, the tool also creates a sibling subdirectory in the target with the name `__<basename>` (the `.dart` extension stripped and a leading `__` prefix). The workspace database's `dart_files` table is updated so each row records the directory the dart file lives in (its parent directory) and the working-directory name for that file. The developer can then use the target tree as the staging area for downstream conversion phases.

**Why this priority**: This is the entire MVP. The downstream conversion pipeline assumes a target tree exists, mirrors the source layout, honours the exclusions decided at init time, and provides a per-`.dart` file working directory in which generated `_net` artefacts (stubs, partial conversions, intermediate IR) can land. Until this story is shipped, the conversion pipeline cannot run.

**Independent Test**: Initialise a workspace with `glp_runtime` containing 4 directories of source code: `lib/` (3 `.dart` files plus a `pubspec.yaml`), `bin/` (1 `.dart` file plus a `.sh` script), `test_archive/` (excluded), and `.dart_tool/` (excluded). Invoke `d2net-scaffold` with no arguments. Verify (a) the target directory `glp_runtime_net/` was created at the repo root; (b) `glp_runtime_net/lib/` contains the 3 `.dart` files plus `pubspec.yaml` AND 3 sibling working directories `__file1/`, `__file2/`, `__file3/`; (c) `glp_runtime_net/bin/` contains the 1 `.dart` file plus the `.sh` script AND 1 sibling working directory `__glp_repl/`; (d) `glp_runtime_net/test_archive/` does not exist; (e) `glp_runtime_net/.dart_tool/` does not exist; (f) the `dart_files` table has 4 rows, each with the parent-directory path and the working-directory name correctly populated.

**Acceptance Scenarios**:

1. **Given** an initialised workspace with source `glp_runtime`, target `glp_runtime_net`, target extension `_net`, and exclusion list `[".dart_tool", "bin/archive", "build", "test_archive"]`, **When** the developer runs `d2net-scaffold` with no arguments, **Then** the tool reads all four settings from the workspace, mirrors `glp_runtime/` to `glp_runtime_net/` skipping every excluded subtree, copies every non-excluded file (`.dart` and otherwise) verbatim, creates a `__<basename>/` working directory next to every copied `.dart` file, and updates the `dart_files` table with the new columns; the command exits 0.
2. **Given** a workspace where the source tree contains a file `glp_runtime/bin/glp_repl.dart`, **When** scaffold runs, **Then** `glp_runtime_net/bin/glp_repl.dart` exists as a copy of the original AND `glp_runtime_net/bin/__glp_repl/` exists as an empty sibling directory; the `dart_files` row for that file records the parent directory path (the absolute path to the directory holding both the `.dart` file and its working directory, native separators) and the working-directory name (`__glp_repl`).
3. **Given** an excluded directory `glp_runtime/test_archive/old/` whose ancestor `glp_runtime/test_archive/` is in the exclusion list, **When** scaffold runs, **Then** neither `test_archive/` nor `test_archive/old/` is created in the target; no files from either directory are copied; no `dart_files` rows reference these paths.

### User Story 2 - Re-run the scaffold idempotently after the exclusion list has changed (Priority: P2)

After an initial scaffold run, the developer adjusts the exclusion list (via `--add-exclude` or `--remove-exclude`). They re-invoke `d2net-scaffold`. The tool re-reads the current settings, walks the source tree again, and reconciles the target tree with the now-current exclusions: directories that were previously copied but are now excluded MUST be removed from the target; directories that were previously excluded but are no longer excluded MUST be created and populated; for each newly-introduced `.dart` file the corresponding `__<basename>/` working directory is created; for `.dart` files that disappear (because their containing directory is now excluded), the corresponding working directory in the target is removed (preserving any sibling unaffected files). The `dart_files` table rows are kept in sync.

**Why this priority**: Without idempotent re-running, any exclusion-list change forces the developer to manually clean the target tree, which is error-prone. Idempotency makes scaffold safely re-runnable as a routine part of the conversion workflow.

**Independent Test**: After User Story 1's scaffold run, add `bin` to the exclusion list via `--add-exclude bin`, re-run scaffold, confirm `glp_runtime_net/bin/` no longer exists. Then remove the exclusion via `--remove-exclude bin --allow-system-exclusions` (since `bin` is auto-detected as `kind='tool'`), re-run scaffold, confirm `glp_runtime_net/bin/` is recreated with the original `.dart` file plus its `__<basename>/` working directory. `dart_files` row counts match the source state at each step.

**Acceptance Scenarios**:

1. **Given** a target tree from a prior scaffold run, **When** the developer adds an exclusion for a directory that was previously included AND re-runs scaffold, **Then** the now-excluded directory and every file and subdirectory beneath it is removed from the target; the corresponding `dart_files` rows are removed.
2. **Given** a target tree from a prior scaffold run, **When** the developer removes an exclusion that was previously in the list AND re-runs scaffold, **Then** the previously-excluded directory is created in the target with all its files copied across, and `__<basename>/` working directories are created for every `.dart` file under it.
3. **Given** an idempotent re-run with no changes since the last scaffold, **When** the developer re-invokes scaffold, **Then** the target tree is byte-identical to its prior state, the `dart_files` table is unchanged, and the run summary reports zero net additions and zero net removals.

### User Story 3 - Diagnose misuse and recover gracefully (Priority: P3)

A developer or skill invokes `d2net-scaffold` against a directory with no `.D2NET/` workspace, against a workspace whose source directory no longer exists on disk, or in a state where the target directory contains a `__<basename>/` collision (a pre-existing real file or non-empty directory of that name). In each case, the tool produces a distinct, documented exit code and a stderr message that names the specific obstruction. The tool refuses to overwrite or merge into pre-existing user content; collisions cause the entire scaffold run to be rejected with no partial application.

**Why this priority**: Predictable failure semantics let the calling skill (and downstream automation) react intelligently — for example, by suggesting `d2net-init` first when the workspace is missing, or by surfacing the colliding paths so the operator can resolve them. Without distinct exit codes, every failure collapses to a generic non-zero exit.

**Independent Test**: From a directory with no `.D2NET/`, invoke `d2net-scaffold` and confirm a workspace-missing exit code distinct from any other exit code in the binary's catalogue. From an initialised workspace where the source directory has been deleted, invoke scaffold and confirm a source-missing exit code with a stderr message naming the missing source directory. Construct a target tree containing a pre-existing `glp_runtime_net/lib/__foo/` that is a real file (not a directory) or a non-empty directory not produced by a prior scaffold run, then invoke scaffold and confirm a working-dir-collision exit code with a stderr line naming the offending path.

**Acceptance Scenarios**:

1. **Given** the current directory has no `.D2NET/` subfolder, **When** the developer runs `d2net-scaffold`, **Then** the command exits with the workspace-missing code, prints a stderr message instructing the developer to run `d2net-init` first, and creates no files.
2. **Given** an initialised workspace where the configured source directory does not exist on disk, **When** scaffold runs, **Then** the command exits with the source-missing code, names the missing path in stderr, and creates no files.
3. **Given** an initialised workspace where the target tree already contains a non-empty `__<basename>/` directory or a real file at that path NOT produced by a prior scaffold run, **When** scaffold runs, **Then** the command exits with the working-dir-collision code, names every offending path in stderr, makes no changes to the target tree, and makes no changes to the `dart_files` table.

### Edge Cases

- **Source file with no extension**: copied verbatim, no working directory created (working dirs are `.dart`-specific).
- **Source file with `.dart` extension that is actually a non-Dart file**: still treated as a `.dart` file by name (extension is the only signal); a `__<basename>/` working directory is created. The user is responsible for ensuring `.dart` is reserved for Dart sources in the source tree.
- **Two `.dart` files in different directories with the same basename**: each gets its own `__<basename>/` working directory in its own parent directory; the `dart_files.full_path` column (existing) and the new parent-directory column distinguish them.
- **A `.dart` file whose basename collides with an existing non-`.dart` directory in the source tree** (e.g., `bin/glp_repl.dart` next to `bin/__glp_repl/` already on disk): the tool MUST refuse to scaffold this file — the collision is reported as a working-dir-collision (US3 acceptance scenario 3). This case includes both real pre-existing directories AND files whose name happens to be `__<basename>`.
- **Symbolic links and junctions in the source tree**: the tool follows the same walking rules as `d2net-init`'s scanner (does not follow symlinks across mount points; treats Windows junctions as ordinary directories) so the target mirror reflects the same view of the source as `dart_files` already records.
- **Empty non-excluded directory in source**: copied as an empty directory in the target. No `__<basename>/` working directories. No `dart_files` rows added.
- **Non-readable file in source**: scaffold rejects the run with a copy-error exit code; partial application is not permitted.
- **Insufficient disk space**: scaffold detects and rejects the run with a copy-error exit code; partial application is not permitted.
- **Concurrent invocation**: same fail-fast lock-contention semantics as features 007 and 008. The loser exits with the lock-contention code; no waiting.
- **Workspace `excluded_directories` table empty**: every non-empty source directory is mirrored; the auto-detected exclusion set was deliberately none.
- **Source directory removed after init but before scaffold**: surfaces as the source-missing exit code (US3 acceptance scenario 2).
- **Target directory pre-exists but was not produced by a prior scaffold run** (e.g., the developer hand-created `glp_runtime_net/`): the tool refuses to scaffold into it. Detection: the target tree must be either non-existent or carry a tracker file (e.g., `.d2net-scaffold-tracker.json`) that scaffold itself created. Rejection exit code is the working-dir-collision code (semantically the same: pre-existing user content blocks the operation). The operator may override this protection by re-invoking with `--FORCE --DELETE-TARGET` (per FR-012a), which surfaces an interactive confirmation prompt naming the absolute target path and only proceeds on an affirmative reply.
- **Operator declines the `--FORCE --DELETE-TARGET` confirmation**: the tool exits with the operator-cancelled exit code, makes no filesystem changes, makes no database changes, leaves the target directory bit-identical to its pre-prompt state.
- **`--FORCE --DELETE-TARGET` supplied but target directory does not exist**: the destructive prompt is skipped (nothing to delete); the tool proceeds with the normal scaffold flow as though the flags were absent. This is documented behaviour: the flag pair authorises *deletion if needed*, not "always delete". Equivalent to a no-op on the deletion path.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: `d2net-scaffold` MUST read the source directory name, target directory name, target extension, and exclusion list from the workspace at `<cwd>/.D2NET/`. The tool MUST NOT accept these values from CLI arguments any more (the prior CLI-arg-based interface is removed).
- **FR-002**: The tool MUST require an existing `.D2NET/` workspace at the current working directory. Absence MUST exit with a distinct, documented workspace-missing exit code, mirroring the convention established by features 007 and 008.
- **FR-003**: The tool MUST verify that the configured source directory exists on disk under the repo root before walking. Absence MUST exit with a distinct, documented source-missing exit code naming the missing path.
- **FR-004**: The tool MUST walk the on-disk source tree using the same skip-walk semantics as `d2net-init`'s scanner: every directory listed in the workspace's exclusion list AND every descendant of an excluded directory MUST be skipped entirely.
- **FR-005**: For every file (every extension, including `.dart`) in a non-excluded directory of the source tree, the tool MUST copy the file verbatim into the corresponding location in the target tree, preserving the relative directory structure under the target root.
- **FR-006**: For every `.dart` file copied to the target, the tool MUST create a sibling subdirectory at the same parent directory in the target tree with the name `__<basename>` where `<basename>` is the file name with the `.dart` extension stripped. Example: `glp_runtime/bin/glp_repl.dart` produces both `glp_runtime_net/bin/glp_repl.dart` (copied) and `glp_runtime_net/bin/__glp_repl/` (created empty).
- **FR-007**: For every `.dart` file produced by FR-006, the tool MUST update the workspace's `dart_files` table row for that file to populate two new columns: a column recording the absolute path to the parent directory of the `.dart` file in the target tree (using native path separators on the host OS) and a column recording the working-directory name (`__<basename>`).
- **FR-008**: The tool MUST add the two new columns described in FR-007 to the `dart_files` table schema if they do not already exist. The new columns MUST coexist with the existing `id`, `filename`, and `full_path` columns; existing rows MUST remain valid.
- **FR-009**: The tool MUST NOT modify `phase_sequence` or `phase_status` directly except to record its own phase progress (per the existing phase-tracking convention from feature 002). Specifically, `d2net-scaffold` MAY upsert a row in `phase_status` with phase = `scaffold` and status = `IN_PROGRESS` at start, and update it to `COMPLETED` (or `FAILED`) at end. It MUST NOT touch any phase row whose phase name is not `scaffold`.
- **FR-010**: The tool MUST be idempotent. Re-running with no underlying changes MUST produce zero net additions or removals to the target tree and zero net changes to the `dart_files` table.
- **FR-011**: The tool MUST reconcile the target tree with the current exclusion list on every run. A directory previously copied that is now excluded MUST be removed from the target tree along with all of its descendants; a directory previously excluded that is no longer excluded MUST be created and populated.
- **FR-012**: The tool MUST refuse to scaffold into a target directory whose contents were not created by a prior scaffold run. Detection mechanism is the workspace-database tracker (clarified 2026-05-01): a `setting` row or `scaffold_tracker` row records the last successful scaffold inventory; absence of that row in the workspace DB AND a non-empty / pre-existing target directory MUST cause refusal. A non-semantic sentinel file inside the target tree (e.g., `<target>/.d2net-scaffold-tracker`) MAY be written for operator visibility but does NOT participate in the FR-012 decision. The tool MUST NOT silently overwrite or merge with user-created content. The operator MAY override this protection by supplying the explicit flag pair `--FORCE --DELETE-TARGET`; the override flow is specified in FR-012a.
- **FR-012a**: When the operator supplies `--FORCE --DELETE-TARGET` (the literal flag pair, mirroring `d2net-init`'s `--FORCE --DELETE-EXISTING` shape), the tool MUST take this as authorisation to delete a pre-existing target directory regardless of whether scaffold's own tracker file is present. Before deleting, the tool MUST emit a single confirmation prompt naming the absolute path of the target directory ("This will recursively delete `<abs target path>` and all of its contents. Proceed? (yes/no)") and wait for an affirmative reply (`yes`, `y`, `confirmed`, `proceed`). On affirmative reply, the tool deletes the target directory and proceeds with the normal scaffold flow against an empty target. On any non-affirmative reply, the tool MUST exit with a distinct, documented operator-cancelled exit code and make no filesystem changes. Supplying only one of the two flags (e.g., `--FORCE` alone or `--DELETE-TARGET` alone) is a usage error (exit 1). The interactive confirmation MUST NOT be skipped by `--non-interactive`-style flags; this is a hard safety gate. The skill or automation invoking the tool is responsible for honouring the prompt; it MUST NOT pipe a prepared `yes` answer without the operator's explicit knowledge.
- **FR-013**: The tool MUST detect collisions where creating a `__<basename>/` working directory would overwrite a pre-existing real file or non-empty directory at that path. Collisions MUST cause the entire run to be rejected with a distinct, documented working-dir-collision exit code; no partial application.
- **FR-014**: The tool MUST commit all filesystem writes and database mutations as one all-or-nothing operation. On any error mid-run, the target tree and the `dart_files` table MUST end up bit-identical to their pre-run state. (Implementation note: a transactional staging area or a tracker-file-based rollback are both acceptable approaches.)
- **FR-015**: The tool MUST emit a concise human-readable summary on success: number of files copied, number of `__<basename>/` working directories created, number of `dart_files` rows updated, number of directories pruned (if any), and total wall-clock duration. The summary MUST be `--json`-switchable to a stable structured form consistent in style with the JSON output of features 007 and 008.
- **FR-016**: The tool MUST use distinct, documented, non-zero exit codes for at least the following failure conditions: workspace-missing, source-missing, working-dir-collision (also covers target-not-empty-from-prior-scaffold per FR-012), copy-error (filesystem IO failure), db-write-failed, workspace-lock-contention, and operator-cancelled-target-deletion (per FR-012a — the operator declined the destructive confirmation prompt). None of these codes MAY collide with feature 007's or 008's codes (12–21).
- **FR-017**: The tool MUST be documented in its own `--help` output. The CLI surface accepts `--help`, `--version`, `--json`, and the destructive override flag pair `--FORCE --DELETE-TARGET` (FR-012a) as the only flags; no positional arguments. (Refresh-mode and other prior CLI options of `d2net-scaffold` are removed by this refactor.)
- **FR-018**: After the tool returns success, an inspection invocation of `d2net-init --list` MUST reflect the updated `dart_files` rows including the two new columns. The new columns MUST also be visible via the `--list --json` form (added to the existing JSON shape).
- **FR-019**: The tool MUST honour fail-fast lock-contention semantics if another `d2net-init` or `d2net-scaffold` invocation holds the workspace database lock. The exit code MUST be distinct from existing 007/008 lock-contention codes (or reuse one if the semantic is identical at the operator level).

### Key Entities *(include if feature involves data)*

- **Source tree node**: a file or directory at a path under the configured source root. Files are copied verbatim; directories are recursed into unless excluded.
- **Target tree node**: a file or directory at the corresponding path under the configured target root. Created by scaffold; cleaned by scaffold when the corresponding source node disappears or becomes excluded.
- **Per-dart working directory**: an empty directory at `<target>/<rel-parent>/__<basename>/` corresponding to each `.dart` file at `<target>/<rel-parent>/<basename>.dart`. Created empty by scaffold; the contents are populated by downstream conversion phases (out of scope for this feature).
- **Dart file row** (modified): the existing row in `dart_files` (`id`, `filename`, `full_path`) gains two new columns: one recording the target-tree absolute parent directory (native separators), one recording the working-directory name (`__<basename>`).
- **Tracker** (hybrid): the **authoritative** marker is a workspace-database entry (a `setting` row or `scaffold_tracker` row) recording the last successful scaffold inventory. A **non-semantic sentinel file** inside the target tree (e.g., `<target>/.d2net-scaffold-tracker`) MAY also be written for operator visibility but carries no authority — FR-012's decision consults the database row only. Cleared atomically as part of the `--FORCE --DELETE-TARGET` destructive flow.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Running scaffold against a workspace with up to 1,000 `.dart` files plus 5,000 non-`.dart` files completes in under 60 seconds on a developer workstation, measured from process start to process exit.
- **SC-002**: Every non-excluded source file is present in the target tree after scaffold completes, byte-identical to its source counterpart, with zero false-positive copies and zero false-negative omissions, in 100 % of test runs.
- **SC-003**: Every `.dart` file copied has exactly one corresponding `__<basename>/` empty sibling directory at the correct path in the target tree, in 100 % of test runs.
- **SC-004**: After scaffold completes, every `dart_files` row has its two new columns populated; the parent-directory column matches the actual on-disk parent directory of the copied `.dart` file (native separators); the working-directory-name column matches the actual on-disk `__<basename>/` directory name. Verified by exact equality in 100 % of test rows.
- **SC-005**: Phase rows for any phase other than `scaffold` are byte-identical to their pre-run state in 100 % of scaffold runs (success or failure).
- **SC-006**: Re-running scaffold immediately after a successful run produces a target tree byte-identical to the post-first-run state and a `dart_files` table whose rows are byte-identical to the post-first-run state, in 100 % of test runs.
- **SC-007**: A simulated process kill or storage error mid-run leaves the target tree and the `dart_files` table in either their pre-run state OR the post-success state — never an intermediate partial state — in 100 % of induced-failure tests.
- **SC-008**: Each of the seven documented error conditions (FR-016, including operator-cancelled-target-deletion per FR-012a) produces a distinct, documented exit code in 100 % of triggering runs, and the offending path (where applicable) appears verbatim in the stderr message in 100 % of relevant runs.
- **SC-010**: When the operator supplies `--FORCE --DELETE-TARGET` and a pre-existing target directory exists, the tool MUST prompt for confirmation naming the absolute target path before any deletion in 100 % of runs. On an affirmative reply, the target directory and every file beneath it MUST be removed before the new scaffold is laid down; on any non-affirmative reply, the target tree MUST be byte-identical to its pre-prompt state in 100 % of runs.
- **SC-009**: After scaffold has run for a workspace, an inspection via `d2net-init --list --json` returns rows whose JSON includes the two new columns with their populated values, in 100 % of test runs.

## Assumptions

- **CLI surface**: `d2net-scaffold` takes no positional arguments and no behavioural flags. Source / target / extension / exclusions all come from the workspace. The only accepted flags are `--help`, `--version`, and `--json`. The previous CLI-arg-based interface is removed; the binary's prior `--refresh` mode is subsumed by FR-010 / FR-011 (every run is idempotent and reconciliatory).
- **Working-directory semantics**: `__<basename>/` directories are created **empty**. Their population is the responsibility of downstream conversion phases. Scaffold's role here is purely to set up the staging skeleton.
- **Working-directory name format**: literal `__` (two underscores) prefix, followed by the `.dart` file's basename with the `.dart` extension stripped. No additional sanitisation. If the basename contains characters that are unusual in directory names (spaces, non-ASCII), they pass through verbatim.
- **`dart_files` schema additions**: two new columns added — implementation MAY name them as appropriate (suggested: `target_parent_dir` for the absolute parent path with native separators, and `target_workdir_name` for `__<basename>`). The existing `id`, `filename`, `full_path` columns are unchanged. No DDL migration logic is needed because PGLite holds workspace-local state; scaffold creates the columns on first run if missing (idempotent `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`).
- **Path separator convention**: the new `target_parent_dir` column stores native separators (Windows: backslashes; POSIX: forward slashes). This is a deliberate divergence from the existing `full_path` column (which is forward-slash repo-root-relative on every host). The target_parent_dir column is consumed by host-OS tooling that runs scripts and follows paths; native separators are the operationally useful form. The full_path column remains as-is for cross-OS portability of `--list` output.
- **Idempotency mechanism**: a workspace-database tracker row (authoritative; `setting` row or small `scaffold_tracker` table) records the inventory scaffold produced on its last successful run. A non-semantic sentinel file inside the target tree provides operator visibility but does not affect correctness. On re-run, scaffold compares the live source state against the DB tracker to compute additions / removals; the same DB tracker is consulted by FR-012 for the "scaffold-managed?" check. Confirmed in clarification session 2026-05-01.
- **Atomicity mechanism**: scaffold writes to a sibling staging directory (e.g., `<target>.d2net-tmp/`) and atomically renames it over the live target only after the database transaction commits. On any failure pre-rename, the staging directory is deleted; the live target is untouched. Mirrors features 007/008's write-temp-then-rename pattern at directory granularity. Confirmed in clarification session 2026-05-01.
- **Phase tracking**: scaffold updates exactly one `phase_status` row (phase = `scaffold`). Any other phase rows belong to other tools (analyze, port, etc.) and MUST NOT be touched.
- **Storage engine**: same per-invocation PGLite bridge as features 007 and 008. No new storage infrastructure.
- **Lock contention**: scaffold uses the same bridge subprocess; the same lock semantics apply. The exit code MAY reuse 007's or 008's lock-contention code, since the operator-visible signal is identical.
- **Out of scope for this feature**: the actual conversion of `.dart` files to `_net` target language; populating the `__<basename>/` directories with anything; bidirectional sync; tracker-file format migrations; partial-tree scaffold (scaffold operates on the whole non-excluded source tree). Adding/removing exclusions is handled by features 007/008; this feature consumes the resulting list.
