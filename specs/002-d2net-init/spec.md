# Feature Specification: D2NET.Init — Workspace and Metadata DB Initializer

**Feature Branch**: `002-d2net-init`
**Created**: 2026-04-30
**Status**: Draft
**Input**: User description: "create a new D2NET.Init companion command to D2NET.Scaffold with the following functionality: create a .D2NET subdirectory in the repo root. In it create a D2NET-Settings.json that contains the full name of the source directory from repo root that is to be converted (e.g. 'glp_runtime'), the extension for the target directory (e.g. '_net'), the full name of the target directory (e.g. 'glp_runtime_net'), and a list of all the subdirs in the source directory that should not be included in the conversion. Source, extension, target and excluded directories should be obtained from params or by prompting the user. The tool should ask if common known tool subdirs like .git etc. should be excluded, and then walk the source dir tree and find dirs which include 'archive', 'backup', 'old' or similar variants and abbreviations and if found include in the list suggested to the user as to be excluded. The user should be able to exclude and re-list suggested exclusions and then approve the final list. Init should also create a pglite WASM-based single-user Postgres DB in a pgdb subfolder in .D2NET, and capture the settings in two tables — one being `setting` and the second being `excluded_directories`. The DB should also include a third table that has one row per .dart source file in a non-excluded part of the source tree, with auto-generated id, the filename (separately) and its full path from repo source. If .D2NET already exists, abort unless the user specifically used the --FORCE --DELETE-EXISTING flag combination in the command. D2NET.Init should have a --list option that lists all Dart files as captured in the PGLite Postgres single-user DB, and a --Exclusions option that does the same for excluded parts of the tree. The DB should also have a phase_sequence table with phase as primary key and sequence as integer, and a phase_status table with phase as PK, a status text field, and a last_updated column. D2NET should have a --current-phase option showing the row in phase_status not in 'COMPLETED' status. The setting table should also include connection details for the ODBC connection to the WASM PGLite Postgres single-user DB instance for D2NET."

## Clarifications

### Session 2026-04-30

- Q: What lifecycle model should D2NET assume for the PGLite ↔ ODBC bridge that exposes the workspace database to tools and external clients? → A: Per-invocation bridge. Every D2NET command brings up its own Postgres-wire bridge for the duration of the call and shuts it down on exit; ODBC connection details in `setting` describe the well-known local port the bridge listens on each time.
- Q: How should `D2NET.Init` determine the repository root? → A: The current working directory is treated as the repo root. The command refuses to proceed if the CWD does not look like a repo root — i.e. it contains neither a `.git/` directory nor a pre-existing `.D2NET/` directory and the supplied source directory does not exist as a direct subdirectory of the CWD.
- Q: What separator should `dart_files.full_path` use? → A: Always forward slashes (`/`), regardless of host OS. The database is portable across machines and operating systems; consumers do not need OS-specific path normalization.
- Q: What schema should the `setting` table use? → A: Flat key/value table `setting (key text PRIMARY KEY, value text NOT NULL)`. Each configured value (source dir, target extension, target dir, and every ODBC connection field) is one row. Trivially extensible by future D2NET commands without schema migration.
- Q: What output format should the inspection options (`--list`, `--Exclusions`, `--current-phase`) produce on standard output? → A: Plain text by default (one record per line, human-readable). All three options also accept a `--json` flag that switches the output to a stable JSON document for scripting and test assertions.
- Q: PGLite + pg-gateway proved to crash psqlODBC and confuse Npgsql at the extended-query-protocol layer during implementation. What is the workspace storage engine? → A: **Embedded single-user SQLite** via Microsoft.Data.Sqlite. SQLite preserves every property the user asked for (single-user, file-backed metadata DB, queryable by standard tooling) and removes the Node + bridge + ODBC dependency surface entirely. The `pgdb/` folder name is preserved for backward compatibility with the user's original instruction; it now holds a single SQLite database file (`workspace.sqlite`) instead of a Postgres data tree. Per-invocation bridge requirements (FR-011a, FR-011b) become trivially satisfied (no bridge, nothing to listen on a port). External SQL clients connect with any SQLite-compatible tool (DB Browser for SQLite, JetBrains DataGrip, sqlite3 CLI). The `setting` table still records connection details but they are SQLite-flavoured (the JSON's `odbc.*` block is renamed to `connection.*`).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Initialize a fresh D2NET workspace for a Dart source tree (Priority: P1)

A developer who is preparing to use the D2NET toolkit on a Dart codebase runs `D2NET.Init` once at the repository root. The command gathers four inputs — the source directory name, the target-directory extension, the target directory full name, and the list of source-directory subfolders to exclude from conversion — either from command-line parameters or by interactively prompting the developer for any value not supplied. After collecting these inputs, the command creates a hidden `.D2NET` workspace folder at the repo root, writes a `D2NET-Settings.json` settings file, creates a single-user PGLite (WASM-backed) Postgres database under `.D2NET/pgdb/`, populates that database with the settings, the excluded-directories list, and one row per `.dart` source file found in the non-excluded part of the source tree, and creates the empty `phase_sequence` and `phase_status` tables for downstream commands to use. After this run, the developer has a complete, queryable D2NET workspace from which the conversion workflow (scaffold, analyze, port, etc.) can proceed.

**Why this priority**: This is the entire MVP. Without a configured `.D2NET` workspace and metadata database, no other D2NET command can locate its inputs, persist its progress, or coordinate phases. Every subsequent feature in the toolkit reads from or writes to artifacts produced by this single command.

**Independent Test**: From a clean repository (no `.D2NET` folder), invoke `D2NET.Init` with explicit parameters supplying the source directory (`glp_runtime`), the target extension (`_net`), and the target directory name (`glp_runtime_net`), and accepting the suggested exclusions non-interactively. Verify (a) `.D2NET/` exists at the repo root, (b) `.D2NET/D2NET-Settings.json` exists and parses as JSON containing the four configured fields plus ODBC connection details, (c) `.D2NET/pgdb/` exists and contains a working single-user PGLite Postgres database, (d) the database has tables `setting`, `excluded_directories`, `dart_files`, `phase_sequence`, and `phase_status`, (e) `setting` contains rows for source dir, target extension, target dir, and ODBC connection details, (f) `excluded_directories` contains one row per directory the developer chose to exclude, (g) `dart_files` contains one row per `.dart` file in the non-excluded portion of the source tree with an auto-generated id, the bare filename, and the file's full path relative to the repo root, and (h) `phase_sequence` and `phase_status` exist with the correct schema and are empty. Delivers value the moment it completes — downstream D2NET commands can immediately read configuration and inventory from a single canonical location.

**Acceptance Scenarios**:

1. **Given** a repo root with a `glp_runtime` source directory containing 200 `.dart` files outside any excluded subdirectory, and no pre-existing `.D2NET` folder, **When** the developer runs `D2NET.Init --source glp_runtime --target-extension _net --target glp_runtime_net --accept-suggested-exclusions`, **Then** `.D2NET/D2NET-Settings.json` is created with the source name `glp_runtime`, target extension `_net`, target name `glp_runtime_net`, the approved exclusion list, and ODBC connection details for the PGLite database; `.D2NET/pgdb/` contains a PGLite single-user Postgres database with the five required tables; the `dart_files` table contains exactly 200 rows; and the command exits with status 0.
2. **Given** a repo root with a `glp_runtime` source directory and no pre-existing `.D2NET` folder, **When** the developer runs `D2NET.Init` with no parameters, **Then** the command interactively prompts for source, extension, target, and approval of the suggested exclusion list, and on completion produces the same artifacts as the parameterized run.
3. **Given** the command has just walked the source tree, **When** it finishes scanning, **Then** before any database write the developer is shown the proposed exclusion list — comprising (a) any well-known tool subdirectories that exist in the source tree (e.g. `.git`, `.dart_tool`, `build`, `.idea`, `.vscode`) for opt-in confirmation and (b) any directory whose name contains a recognised archive/backup/old marker — and is given the chance to remove items from, re-display, and finally approve the list before it is persisted.
4. **Given** the source directory contains a subdirectory named `archive_2024`, **When** the source tree is walked, **Then** that directory is included in the suggested exclusion list (because its name contains the marker `archive`), and any `.dart` files contained anywhere beneath it are absent from the final `dart_files` table after the developer approves the suggestion.

### User Story 2 - Inspect the workspace through CLI options (Priority: P2)

After `D2NET.Init` has succeeded, the developer can re-invoke the same command with inspection flags to read back the workspace state without modifying it. `--list` prints every Dart source file that the init step recorded in the database; `--Exclusions` prints every directory the init step recorded as excluded; `--current-phase` prints the single phase row that downstream tools have most recently advanced but not yet marked COMPLETED.

**Why this priority**: The init step is what creates the data; these inspection commands are what make the data useful day-to-day. They are essential for the developer to verify that init recorded what they expected and to track progress across phases, but they are not required for the first successful workspace creation that delivers MVP value.

**Independent Test**: After User Story 1 has run successfully, invoke `D2NET.Init --list` and verify the output is the complete, sorted list of Dart files captured in the `dart_files` table. Invoke `D2NET.Init --Exclusions` and verify the output is the complete list of excluded directories from the `excluded_directories` table. Invoke `D2NET.Init --current-phase` and verify the output identifies the lowest-sequence row in `phase_status` whose status is anything other than `COMPLETED`, or reports "no active phase" if every row is `COMPLETED` or the table is empty.

**Acceptance Scenarios**:

1. **Given** a workspace where `dart_files` has 200 rows, **When** the developer runs `D2NET.Init --list`, **Then** the command prints 200 lines (each line containing the filename and the full path from the repo root), exits with status 0, and modifies no file in the workspace.
2. **Given** a workspace where `excluded_directories` has 7 rows, **When** the developer runs `D2NET.Init --Exclusions`, **Then** the command prints 7 lines and modifies no file in the workspace.
3. **Given** a workspace where `phase_status` has rows `(scaffold, COMPLETED, …)`, `(analyze, IN_PROGRESS, …)`, `(port, NOT_STARTED, …)` with `phase_sequence` ordering them 1, 2, 3, **When** the developer runs `D2NET.Init --current-phase`, **Then** the command prints the `analyze` row (the lowest-sequence row whose status is not `COMPLETED`).
4. **Given** a workspace where every row in `phase_status` has status `COMPLETED`, or where `phase_status` is empty, **When** the developer runs `D2NET.Init --current-phase`, **Then** the command prints a clear "no active phase" message and exits with status 0.

### User Story 3 - Safely re-initialize an existing workspace (Priority: P3)

A developer who has already initialized a `.D2NET` workspace and now wants to start over (because the source directory has been renamed, the exclusion list needs major revision, or the workspace has been corrupted) re-runs `D2NET.Init`. By default the command refuses to touch the existing workspace and exits with a clear error. Only when the developer supplies the exact flag combination `--FORCE --DELETE-EXISTING` does the command delete the existing `.D2NET` directory and recreate it from scratch.

**Why this priority**: Important for safety and for recovering from configuration drift, but not required for the first successful init that delivers MVP value. Without this safeguard the tool is still useful; with it, the developer is protected against accidental loss of an in-progress workspace.

**Independent Test**: Run `D2NET.Init` once successfully. Modify a row in the database (or edit `D2NET-Settings.json`). Run `D2NET.Init` again with no flags and confirm it aborts without touching the workspace. Run `D2NET.Init --FORCE` alone and confirm it aborts. Run `D2NET.Init --DELETE-EXISTING` alone and confirm it aborts. Run `D2NET.Init --FORCE --DELETE-EXISTING` and confirm the previous `.D2NET` is removed and a fresh one is built.

**Acceptance Scenarios**:

1. **Given** a `.D2NET` directory already exists at the repo root, **When** the developer runs `D2NET.Init` with no override flags, **Then** the command reports "workspace already exists at .D2NET; use --FORCE --DELETE-EXISTING to recreate it", makes no change to any file or directory under `.D2NET`, and exits with a non-zero status.
2. **Given** a `.D2NET` directory already exists, **When** the developer runs `D2NET.Init --FORCE` alone or `D2NET.Init --DELETE-EXISTING` alone, **Then** the command reports that both flags are required together, makes no change to `.D2NET`, and exits with a non-zero status.
3. **Given** a `.D2NET` directory already exists, **When** the developer runs `D2NET.Init --FORCE --DELETE-EXISTING` together with the configuration parameters (or interactive prompts), **Then** the existing `.D2NET` directory is fully deleted, a fresh `.D2NET` is created exactly as in the User Story 1 happy path, and the command exits with status 0.

### Edge Cases

- **Invoked from the wrong directory** (CWD has no `.git/`, no `.D2NET/`, and no subdirectory matching the supplied source name): The command refuses to run with a clear "current directory does not look like a D2NET repository root" error and creates no `.D2NET` folder. It does **not** silently walk up to a parent directory.
- **Source directory does not exist**: The command refuses to run, reports the missing source path, and creates no `.D2NET` folder (even partial).
- **Source directory exists but contains zero `.dart` files outside excluded subdirectories**: The workspace is created normally and `dart_files` is empty (zero rows). This is a valid workspace.
- **Source directory has Dart files only inside subdirectories that the developer chose to exclude**: Same as above — `dart_files` is empty.
- **Repo root is not writable** (permission denied creating `.D2NET`): The command aborts with a clear error and creates no partial directory.
- **Interactive prompt is interrupted** (Ctrl-C, EOF, terminal closed): The command aborts and removes any partial `.D2NET` directory it had begun to create.
- **The same Dart filename exists in multiple non-excluded directories** (e.g. `runner.dart` in both `lib/foo/` and `lib/bar/`): Both rows are recorded in `dart_files` with distinct ids and distinct full-path values; the bare filename column is identical between them, which is allowed.
- **Source directory subfolder name contains a marker substring used by the archive heuristic but the developer wants to keep it**: The directory is suggested for exclusion; the developer can remove it from the suggestion before approving the final list, and the workspace is built without excluding that directory.
- **The user-supplied target directory name does not equal source name + extension** (e.g. source `glp_runtime`, extension `_net`, target `myport`): The command accepts the explicit target name as authoritative — it does not enforce the convention; the three values are stored independently in the `setting` table.
- **Settings file and database disagree** (cannot occur after a fresh init, but can occur after manual editing): Out of scope for this MVP; the database is treated as authoritative for downstream commands and `D2NET-Settings.json` is treated as a human-readable mirror.
- **Target directory `glp_runtime_net` already exists** in the repo at init time: Init does not create or modify the target directory itself — that is `D2NET.Scaffold`'s job. Init only records its name in settings.
- **`--list` or `--Exclusions` invoked when no `.D2NET` exists**: The command reports "no D2NET workspace found at <repo root>; run D2NET.Init first" and exits with a non-zero status.
- **`--current-phase` invoked when `phase_status` table is empty**: Reported as "no active phase" with status 0 (not an error).

## Requirements *(mandatory)*

### Functional Requirements

#### Workspace creation

- **FR-001**: The command MUST be invocable as `D2NET.Init` and MUST be a sibling/companion command to the existing `D2NET.Scaffold`. It MUST be runnable as a standalone CLI from the repository root.
- **FR-002**: The command MUST create a single workspace directory named `.D2NET` at the repository root and MUST place all workspace artifacts (settings file, database, future per-phase artifacts) inside it. The repository root is taken to be the **current working directory** at invocation time. The command MUST refuse to proceed when the current working directory does not look like a repo root — defined as: it contains neither a `.git/` directory nor a pre-existing `.D2NET/` directory, **and** the supplied (or prompted) source directory does not exist as a direct subdirectory of the current working directory. In that case the command MUST exit with a non-zero status and a clear "current directory does not look like a D2NET repository root" error, and MUST NOT walk up to parent directories.
- **FR-003**: The command MUST refuse to run when `.D2NET` already exists at the repository root, UNLESS the user supplied both flags `--FORCE` and `--DELETE-EXISTING` together. Either flag alone MUST be rejected. When both are supplied, the existing `.D2NET` directory MUST be deleted in full before the fresh workspace is created.
- **FR-004**: The command MUST refuse to run when the supplied (or prompted) source directory does not exist as a subdirectory of the repository root, and MUST not create any `.D2NET` artifacts in that case.

#### Input collection

- **FR-005**: The command MUST collect four inputs — `source` (the full name of the source directory under the repo root, e.g. `glp_runtime`), `target_extension` (the suffix appended to the source name to form the target name, e.g. `_net`), `target` (the full name of the target directory, e.g. `glp_runtime_net`), and `excluded_directories` (the final approved list of source subdirectories to omit from conversion). Each input MUST be obtainable either from a corresponding command-line parameter or, if absent, by interactive prompt.
- **FR-006**: The command MUST offer the user a list of well-known tool subdirectories (at minimum `.git`, `.dart_tool`, `build`, `.idea`, `.vscode`) that exist anywhere within the source tree, and MUST ask the user whether to exclude them. The user's response MUST control whether each such directory appears in the final exclusion list.
- **FR-007**: The command MUST walk the source directory tree and identify every directory whose name contains any of the markers `archive`, `archives`, `backup`, `backups`, `bak`, `old`, `obsolete`, `deprecated`, `legacy`, `attic` (case-insensitive substring match), and MUST add each such directory to the suggested exclusion list.
- **FR-008**: The command MUST present the combined suggested exclusion list (well-known tool subdirectories the user opted into, plus archive/backup/old matches) to the user, MUST allow the user to remove individual entries from the suggestion, MUST allow the user to redisplay the updated suggestion any number of times, and MUST require the user to explicitly approve the final list before it is persisted to the workspace.

#### Settings file

- **FR-009**: The command MUST write a single JSON file `.D2NET/D2NET-Settings.json` containing at least: a `schema_version` integer (`1` for this MVP), the source directory name, the target directory extension, the target directory name, the approved excluded-directory list (sorted ascending), the connection details required to reach the embedded single-user SQLite database under `.D2NET/pgdb/` (database engine, absolute database file path, full connection string), and a `created_at` ISO-8601 UTC timestamp recording when the fresh-init run completed. The `created_at` value MUST be set on a fresh init and MUST NOT be modified by `--FORCE --DELETE-EXISTING` re-init (the re-init writes a fresh `created_at` because the workspace is being recreated).
- **FR-010**: The connection details written to the settings file MUST include every field a downstream tool needs to open the workspace database (database engine string, absolute database file path, full ADO.NET-style connection string). The same connection details MUST also be persisted as rows in the `setting` table inside the database itself (so a tool that has any way to reach the DB can read every other connection field).

#### Metadata database

- **FR-011**: The command MUST create an **embedded single-user SQLite** database file at `.D2NET/pgdb/workspace.sqlite`, in a state that allows any later D2NET command (and any external SQLite-compatible client) to open the database directly using the connection details persisted in `D2NET-Settings.json` and in the `setting` table. No daemon, no network listener, no separate bridge process is involved.
- **FR-011a**: Every D2NET command that needs to read or write the workspace database opens the SQLite file in-process for the duration of the invocation and closes it before exit. No D2NET command may leave any background process or open file handle after it returns.
- **FR-011b**: If at the start of an invocation the SQLite database file cannot be opened (file is missing when expected, file is locked by another process, file is corrupt), the command MUST fail fast with a clear error message naming the file path, MUST NOT modify any file under `.D2NET`, and MUST exit with a non-zero status.
- **FR-012**: The database MUST contain a table named `setting` with exactly two columns: `key` (text, primary key) and `value` (text, NOT NULL). Each configured value is one row. At minimum the table MUST contain rows for the keys: `source_dir`, `target_extension`, `target_dir`, and one row per connection field enumerated by FR-010 (`db_engine`, `db_file`, `db_connection_string`). Future D2NET commands MAY add additional rows under new keys without altering the schema.
- **FR-013**: The database MUST contain a table named `excluded_directories` with two columns: `path` (text, primary key — relative to the source directory, forward slashes) and `kind` (text, NOT NULL, drawn from the closed enumeration `{"tool", "pattern", "manual"}`). One row per approved excluded directory. `kind` records why the exclusion exists: `tool` for a well-known tool subdirectory the developer opted into (FR-006), `pattern` for an archive/backup/old heuristic match (FR-007), and `manual` for an exclusion supplied by an explicit CLI flag.
- **FR-014**: The database MUST contain a table named `dart_files` containing one row per `.dart` file found in the source tree outside any excluded directory. Each row MUST have an auto-generated primary key (id), the bare filename column (e.g. `runner.dart`) stored separately from the full path, and a full-path column containing the file's path from the repository root using **forward-slash (`/`) separators on every host OS** (e.g. `glp_runtime/lib/runtime/runner.dart` on both Windows and Linux). The command MUST NOT write OS-native backslash separators into `full_path`, regardless of the platform on which it runs.
- **FR-015**: The database MUST contain a table named `phase_sequence` with columns `phase` (text, primary key) and `sequence` (integer). The init command MUST create this table empty; it is populated by downstream D2NET commands.
- **FR-016**: The database MUST contain a table named `phase_status` with columns `phase` (text, primary key), `status` (text), and `last_updated` (timestamp). The init command MUST create this table empty; it is populated by downstream D2NET commands.

#### Inspection options

- **FR-017**: The command MUST accept a `--list` option which, when supplied, prints every row of the `dart_files` table to standard output and makes no modification to the workspace, then exits. Default format is plain text — one row per line containing the bare filename and the full path — **sorted by `full_path` ascending** (lexicographic, byte-wise; the same ordering MUST be used in both plain text and `--json` modes).
- **FR-018**: The command MUST accept a `--Exclusions` option which, when supplied, prints every row of the `excluded_directories` table to standard output and makes no modification to the workspace, then exits. Default format is plain text — one excluded directory path per line — **sorted by `path` ascending** (lexicographic, byte-wise; the same ordering MUST be used in both plain text and `--json` modes).
- **FR-019**: The command MUST accept a `--current-phase` option which, when supplied, prints the single row from `phase_status` whose `phase` corresponds to the lowest `sequence` value in `phase_sequence` among all phases whose `status` is anything other than `COMPLETED`, then exits. Default format is plain text — a single line with phase, status, and last-updated timestamp. The `last_updated` value MUST be rendered as an **ISO-8601 UTC** timestamp with a trailing `Z` (e.g. `2026-04-30T13:01:22Z`) in both plain-text and `--json` output. If no such row exists (every phase is `COMPLETED`, or `phase_status` is empty, or `phase_sequence` is empty), the command MUST print a clear "no active phase" message and exit with status 0.
- **FR-019a**: All three inspection options (`--list`, `--Exclusions`, `--current-phase`) MUST also accept a `--json` flag that switches stdout from plain text to a stable JSON document, with the following shapes:
  - `--list --json` → `{ "dart_files": [ { "id": <int>, "filename": <string>, "full_path": <string> }, … ] }`
  - `--Exclusions --json` → `{ "excluded_directories": [ <string>, … ] }`
  - `--current-phase --json` → either `{ "phase": <string>, "status": <string>, "last_updated": <ISO-8601 string>, "sequence": <int> }` or `{ "phase": null }` when no active phase exists.

  In `--json` mode the command MUST emit no other text on stdout (no banners, no progress, no trailing newline beyond what the JSON encoder produces). Human-readable diagnostics, if any, MUST go to stderr.
- **FR-020**: When any of `--list`, `--Exclusions`, or `--current-phase` is supplied and no `.D2NET` workspace exists at the current working directory, the command MUST report the missing workspace clearly and exit with a non-zero status without creating any directory. In `--json` mode the error MUST go to stderr; stdout MUST remain empty.

#### Safety and reporting

- **FR-021**: At the end of a successful init run, the command MUST print to standard output a human-readable summary including the resolved source/target/extension, the size of the approved exclusion list, the count of rows written to `dart_files`, the location of `D2NET-Settings.json`, and the location of the PGLite database. No additional report file is produced.
- **FR-022**: If the command aborts at any point during workspace creation (interactive prompt cancelled, source missing, ODBC initialisation failed, etc.), it MUST leave the repository root in a clean state — either no `.D2NET` directory at all (if it had not yet started writing) or the pre-existing `.D2NET` directory in its original state (if `--FORCE --DELETE-EXISTING` had not been supplied or had not yet executed the deletion).
- **FR-023**: With the SQLite pivot (Q6 in Clarifications), `--bridge-port` is **no longer applicable**. The CLI MUST still accept the flag for backward compatibility but MUST treat it as a no-op (silently ignored), and `setting`/`D2NET-Settings.json` MUST NOT record any port field. Documentation MUST flag the option as deprecated.

### Key Entities *(include if feature involves data)*

- **Repository root**: The directory the user is in when `D2NET.Init` is invoked. The `.D2NET` workspace lives directly under it; the source directory is a named subdirectory of it. `D2NET.Init` does **not** walk up to find a `.git/` ancestor — the current working directory is taken as authoritative, and if it does not look like a repo root the command refuses to run (see FR-002).
- **Source directory**: The Dart codebase to be converted, identified by its name relative to the repository root (e.g. `glp_runtime`). Read-only as far as `D2NET.Init` is concerned; only its tree structure and file list are inspected.
- **Target directory**: The future destination of the conversion (e.g. `glp_runtime_net`). `D2NET.Init` only records its name; it neither creates nor inspects it.
- **Excluded directory**: A subdirectory of the source tree (identified by path relative to the source root) that is explicitly omitted from the conversion. Excluded directories suppress every file beneath them — including `.dart` files — from inclusion in the `dart_files` inventory.
- **Workspace (`.D2NET`)**: The hidden directory created at the repository root holding all D2NET state. Contents of the MVP workspace are: `D2NET-Settings.json` and `pgdb/`.
- **Settings file (`D2NET-Settings.json`)**: The human-readable JSON projection of the workspace's configuration. Mirrors a subset of the database `setting` table.
- **Workspace database (PGLite)**: A single-user, file-backed, WASM-based Postgres instance stored under `.D2NET/pgdb/`. The authoritative store of workspace state, queryable via ODBC by any downstream D2NET tool.
- **Dart source file (record)**: A row in the `dart_files` table representing one `.dart` file from the non-excluded portion of the source tree. Carries an auto-generated id, the bare filename, and the full path relative to the repository root.
- **Phase**: A logical step in the D2NET conversion workflow (e.g. scaffold, analyze, port, test). `D2NET.Init` creates the `phase_sequence` and `phase_status` tables empty; phases are introduced and updated by downstream commands.
- **Current phase**: The phase exposed by `--current-phase`. Defined as the row in `phase_status` whose `phase` has the lowest `sequence` value in `phase_sequence` among all phases whose `status` is not `COMPLETED`.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: From a clean repo, a single non-interactive `D2NET.Init` invocation against a source tree of up to 500 `.dart` files (across up to 100 non-excluded directories) completes in under 10 seconds and exits with status 0 on a developer workstation with a modern multi-core CPU and an SSD.
- **SC-002**: After a successful init run, `.D2NET/D2NET-Settings.json` parses as JSON and contains all four required configuration fields plus the ODBC connection block.
- **SC-003**: After a successful init run, the workspace database contains exactly five tables — `setting`, `excluded_directories`, `dart_files`, `phase_sequence`, `phase_status` — and an ODBC client using the connection details from `D2NET-Settings.json` can open a session and run `SELECT` queries against each.
- **SC-004**: After a successful init run, the count of rows in `dart_files` equals the count of `.dart` files found in the source tree outside the approved excluded directories.
- **SC-005**: After a successful init run, the count of rows in `excluded_directories` equals the count of entries in the developer-approved exclusion list.
- **SC-006**: After a successful init run, `phase_sequence` and `phase_status` contain zero rows.
- **SC-007**: Re-invoking `D2NET.Init` with no override flags against an existing workspace makes zero changes to any file under `.D2NET` and exits with a non-zero status.
- **SC-008**: Invoking `D2NET.Init --FORCE --DELETE-EXISTING` against an existing workspace leaves no file from the previous `.D2NET` and produces a workspace identical in shape (same five tables, same JSON shape) to a fresh init.
- **SC-009**: `--list`, `--Exclusions`, and `--current-phase` each modify zero bytes under `.D2NET` and exit with status 0 when a valid workspace exists. With `--json`, the stdout output of each parses as JSON and conforms to the schema fixed in FR-019a; without `--json`, output is one record per line.
- **SC-010**: At least 95% of common archive/backup/old directory names — variants such as `archive`, `archives`, `backup`, `backups`, `bak`, `old`, `obsolete`, `deprecated`, `legacy`, `attic`, and `_old`-style suffixes — are correctly proposed for exclusion when the source tree is walked, as measured against a curated test fixture of 20 directory names mixing positive and negative cases.

## Assumptions

- The command runs in a Windows / cross-platform .NET environment alongside the existing `D2NET.Scaffold` console app and is delivered as a sibling executable (parallel project under `tools/d2net/`). The exact host runtime is left to implementation; the spec only fixes externally observable behaviour.
- "PGLite WASM-based single-user Postgres" is taken to mean an in-process, file-backed Postgres instance whose data files live under `.D2NET/pgdb/`. To expose this database via ODBC the implementation provides a Postgres-wire-compatible bridge process. Per FR-011a, every D2NET command brings the bridge up at the start of the invocation and tears it down before exit (per-invocation lifecycle); no daemon is left running between commands.
- The ODBC connection details persisted in FR-010 are sufficient to allow any standard Postgres ODBC client to open a session against the local single-user database **while a D2NET command is running** (or while the user has manually started a bridge against `.D2NET/pgdb/`). Authentication is implicit / single-user (no real password security is assumed for a per-developer local file-backed DB); the password placeholder is recorded only for ODBC string completeness.
- The per-invocation bridge model implies a small, predictable startup/shutdown cost on every D2NET command (including the read-only inspection options). This is acceptable for a developer CLI; throughput-sensitive workloads are not in the scope of D2NET.
- `phase_sequence` and `phase_status` are created empty by init. Population (which phases exist, in what order, and with what initial status) is the responsibility of subsequent D2NET commands (e.g. `D2NET.Scaffold`, `D2NET.Analyze`). The spec fixes only the shape of these tables, not their initial contents.
- The `--current-phase` semantics ("the row not in COMPLETED status") is interpreted as "the lowest-sequence row whose status is not exactly the literal string `COMPLETED`". The set of legal status values is not constrained by this spec — it is whatever downstream commands write.
- The full path stored in `dart_files.full_path` is relative to the repository root and uses forward slashes on every OS (per FR-014, e.g. `glp_runtime/lib/runtime/runner.dart` on Windows and Linux alike). The bare filename column stores only the leaf filename.
- The exclusion-marker substring set in FR-007 — `archive`, `archives`, `backup`, `backups`, `bak`, `old`, `obsolete`, `deprecated`, `legacy`, `attic` — is treated as case-insensitive substring matches against the directory's leaf name (not the full path). The list is fixed by this spec; tuning it is out of scope for the MVP.
- The well-known tool subdirectories prompted for in FR-006 are at minimum `.git`, `.dart_tool`, `build`, `.idea`, `.vscode`; the implementation MAY extend this list (e.g. `node_modules`, `bin`, `obj`) but MUST always include the listed minimum.
- The case spelling `--FORCE` and `--DELETE-EXISTING` follows the user's explicit request (uppercase). The implementation MAY accept `--force --delete-existing` as case-insensitive synonyms but MUST accept the uppercase spelling exactly as the documented interface.
- Symbolic links and junctions inside the source tree are followed at most one level deep when discovering Dart files; loop detection is out of scope for the MVP.
- The init command does not validate the contents of any `.dart` file beyond noting its existence. Parse errors, encoding issues, etc. are deferred to downstream phases.
