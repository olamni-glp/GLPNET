Engineer ruling **R3** was: *codexreview the feat commits first, then cut the release, then backfill
the tags missing GitHub Releases.* The first two are done — the review cleared after eleven rounds
and **v2026.08.21.3** is cut, tagged and on `main`. This is the third part.

The count is 59, not the 56 recorded on 2026-08-20, because three tags were cut since:
`v2026.08.21.1`, `v2026.08.21.2` (another lane) and `v2026.08.21.3` (this remediation).
`buildkit release` creates the git tag but does not create a GitHub Release, so every future cut
adds one to this list until that is changed.

Every one of the 59 is an **annotated** tag object, so its own message is the natural release note.

## Blocked on

`gh release create` is refused by the auto-mode permission classifier. R4 granted `gh api -X PATCH`
and containment-verified remote branch deletion; it did not cover release creation. A Bash
permission rule for `gh release create` (or an equivalent grant) unblocks this.

## The command, ready to run

Oldest first, with `--latest=false` on every backfilled tag so the **Latest** badge stays on
`v2026.08.21.3`, and `--verify-tag` so a typo cannot mint a tag by accident:

```
git tag --list 'v*' | sort > /tmp/tags.txt && gh release list --limit 200 --json tagName -q '.[].tagName' | sort > /tmp/rel.txt && comm -23 /tmp/tags.txt /tmp/rel.txt | while read -r t; do gh release create "$t" --title "$t" --notes-from-tag --latest=false --verify-tag || echo "FAILED $t"; done
```

Then put the badge back where it belongs:

```
gh release edit v2026.08.21.3 --latest
```

**Verify by content, not by exit code** — a prior session recorded a false green from a stale exit
status. The check is that the two lists match:

```
gh release list --limit 200 --json tagName -q '.[].tagName' | sort > /tmp/rel2.txt && comm -23 /tmp/tags.txt /tmp/rel2.txt | wc -l
```

which must print `0`.

## Worth fixing at the source

The recurrence is mechanical: `buildkit release` tags without publishing a Release. Backfilling by
hand today leaves the same gap open tomorrow. The durable fix is for the release step to create the
GitHub Release as part of the cut — the same shape of root-cause fix as W09, where enabling
`delete_branch_on_merge` stopped the 145-branch accumulation instead of sweeping it repeatedly.
