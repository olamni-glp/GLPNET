# LLVM / MLIR Feasibility for the GLP Binary Intermediate Language

**Epic:** Separation of REPL Front-end from Engine Execution & Scheduler
**Feature:** Persistent, Embeddable GLP Engine — binary wire/persistence intermediate language (§3, §7b)
**Stage:** SCOUT (feature-definition §7b: "LLVM exploration (staged): (1) scout … (2) conditionally go deeper … (3) potentially a verification spike")
**Authored:** 2026-06-08
**Status:** Scout complete — verdict below.

---

## 0. The question, precisely

§7b of the feature definition asks whether **LLVM compiler technology** — LLVM IR,
bitcode, the optimization-pass pipeline, ORC JIT, and MLIR custom dialects — would
be useful for **generating or modifying the GLP intermediate language / binary
format**, for **optimization or other purposes**.

GLP is a **flat concurrent / committed-choice logic language** (the Concurrent
Prolog / FCP / Flat GHC / KL1 family): unification, single-reader/single-writer
(SRSW) logic variables, **goal suspension on an unbound reader and reactivation
when a writer binds**, and **three-phase HEAD / GUARD / BODY** reduction. The §3
artifact under design is a **stable, versioned, DB-persisted, cross-runtime
(C# / Dart / C++) binary interchange format** that survives restarts (§6) and can
even be **generated by the engine at runtime** (§3, "engine occasionally generates
new intermediate language at runtime").

The honest answer has three parts: a narrow band where LLVM/MLIR genuinely **could
help**, a wide band where it is a **poor structural fit**, and a **conditional,
strictly-off-the-critical-path recommendation** on going deeper.

---

## 1. Where LLVM / MLIR could plausibly help

These are real, evidence-backed capabilities — but every one of them sits
**downstream of the GLP runtime semantics**, never inside them, and none of them is
the §3 IL itself.

### 1.1 LLVM as an optional leaf-level accelerator for *ground, deterministic* kernels

After the GLP runtime has already resolved unification and committed a clause,
the **straight-line numeric / arithmetic-guard / struct-field-access fragments**
of a reduction are ordinary imperative code. LLVM's SSA pass pipeline (inlining,
GVN, DCE, constant propagation, register allocation, vectorization, LTO/PGO) is
genuinely good at exactly that layer. This is the documented GHC experience: the
LLVM backend for GHC gave **~20% on numeric / array-heavy code and little on
average**, at a compile-time cost — useful for the scalar layer, not the language's
core ([An LLVM Backend for GHC, Terei & Chakravarty, Haskell Symposium 2010](https://llvm.org/pubs/2010-09-HASKELLSYM-LLVM-GHC.html);
[Klebinger, "Opinion piece on GHC backends"](https://andreaspk.github.io/posts/2019-08-25-Opinion%20piece%20on%20GHC%20backends.html)).
The only concrete logic-language-on-LLVM artifact we found — the "L2" sub-machine
of a WAM tutorial reconstruction with a JIT built on LLVM — confirms both the
possibility and its limits: it is explicitly **"not 100% complete"** and models
**sequential backtracking Prolog**, not committed-choice concurrency
([rupertlssmith/hak_wambook](https://github.com/rupertlssmith/hak_wambook);
[gabrielsoule/WAM-L2](https://github.com/gabrielsoule/WAM-L2);
[Warren Abstract Machine, Wikipedia](https://en.wikipedia.org/wiki/Warren_Abstract_Machine)).

### 1.2 ORC JIT genuinely matches the "engine generates new IL at runtime" need (§3)

§3 requires that the engine can emit and run new IL while live. LLVM's **ORCv2**
JIT is purpose-built for this: modular, language-agnostic, supporting **lazy /
on-demand compilation (lazy-reexports), concurrent multi-threaded compilation, and
even out-of-process JIT-linking** ([ORCv2 Design and Implementation](https://llvm.org/docs/ORCv2.html);
[Building a JIT: Per-function Lazy Compilation](https://llvm.org/docs/tutorial/BuildingAJIT3.html);
[Building a JIT: Extreme Laziness](https://llvm.org/docs/tutorial/BuildingAJIT4.html)).
So *if* a GLP fragment were already lowered to LLVM IR, runtime codegen of new
clauses is a solved capability. (The footprint cost of this, against §7a, is in
§2.4.)

### 1.3 MLIR is the strongest LLVM-family option — as *infrastructure*, not as the IL

MLIR is explicitly an **extensible infrastructure**, not a fixed IR: you define a
**custom dialect** (your own ops/types — e.g. `glp.unify`, `glp.suspend`,
`glp.commit`, `glp.clause_try`) and **progressively lower** it through your own
passes toward the LLVM dialect as the native-codegen "exit"
([MLIR home](https://mlir.llvm.org/);
[MLIR: A Compiler Infrastructure for the End of Moore's Law, Lattner et al., arXiv 2002.11054](https://arxiv.org/pdf/2002.11054);
[MLIR paper, uwaterloo mirror](https://rcs.uwaterloo.ca/~ali/cs842-s23/papers/mlir.pdf);
[Jeremy Kun, "MLIR — Lowering through LLVM"](https://www.jeremykun.com/2023/11/01/mlir-lowering-through-llvm/)).
This matches "define the GLP IL once and lower it" far better than raw LLVM IR.
There is real declarative uptake: **LingoDB** defines custom MLIR dialects
(`relalg`, `db`) to compile SQL to machine code, reusing MLIR/LLVM passes and
beating DuckDB/Hyper/Umbra on TPC-H/DS
([LingoDB, VLDB vol.15 p.2389](https://www.vldb.org/pvldb/vol15/p2389-jungmair.pdf);
[dbdb.io LingoDB](https://dbdb.io/db/lingodb)). And **bollu/lz** shows a custom MLIR
dialect for a non-imperative (lazy STG) evaluation model is at least explorable
([bollu/lz](https://github.com/bollu/lz)). **But all of these prove MLIR can host a
declarative front-end as a dialect — relational-algebra set-at-a-time semantics, or
laziness — not unification + SRSW + suspension.** MLIR supplies the dialect
scaffolding and the rewrite/lowering framework; it does **not** supply a GC, term
tagging, a suspension scheduler, or a unification engine — you build all of those.

### 1.4 The one *well-precedented* logic↔LLVM touchpoint is inverted: logic *drives* the optimizer

The demonstrated way logic / Datalog meets MLIR is as a **rewrite-rule / optimization
engine over the IR**, not as a source language lowered into it. **egglog** unifies
Datalog and equality saturation; **DialEgg** translates MLIR → egglog, applies user
rewrite rules, and translates back; "Better Together" shows e-graphs are relational
databases ([egglog, PLDI 2023](https://ztatlock.net/pubs/2023-pldi-egglog/2023-pldi-egglog.pdf);
[DialEgg, ACM 3696443.3708957](https://dl.acm.org/doi/pdf/10.1145/3696443.3708957);
[Better Together, arXiv 2304.04332](https://arxiv.org/pdf/2304.04332)). For GLP this
suggests that if we ever want **principled IL optimization**, expressing rewrite
rules in a logic/relational DSL **over** the GLP IL is better-precedented than
lowering GLP's runtime semantics **into** LLVM IR.

## 2. Where LLVM / MLIR fits poorly

### 2.1 SSA cannot represent a logic variable being destructively bound

LLVM IR register values are **SSA — there is no way to change an SSA value**; only
*memory* objects may be mutated ([mcyoung, "An introduction to LLVM IR"](https://mcyoung.xyz/2023/08/01/llvm-ir/);
[LLVM tutorial LangImpl07, mutable variables](https://llvm.org/docs/tutorial/MyFirstLanguageFrontend/LangImpl07.html)).
A GLP logic variable is a single-writer cell that is unbound, then **destructively
bound** by a writer MGU, while readers suspend on it. This forces logic variables +
the heap + any trail into **LLVM memory (loads/stores/pointers)**, at which point
LLVM's strongest, value-level SSA optimizations **cannot see the unification that
dominates GLP execution**. Every surveyed logic compiler confirms this: the hard
parts live in a **hand-built runtime**, not in IR constructs — including the recent
Prolog PoC that compiles unification by compile-time specialization plus an explicit
trail and choice-point frames ([Orange Kiwi, "A fast Prolog compiler proof-of-concept"](https://www.orange-kiwi.com/posts/a-fast-prolog-compiler-proof-of-concept/)).

### 2.2 Goal suspension / reactivation is the "non-C runtime model" LLVM is documented-weak-at

GLP goal suspension on an unbound reader + reactivation when a writer binds is
operationally a **coroutine / heap-allocated continuation**, not a C call/return
stack. The Manticore (Parallel ML) LLVM work states LLVM's **"design is based on a
traditional runtime model which is not well suited to alternative compilation
strategies … such as the use of heap-allocated continuation closures"** — and that
supporting constant-time `callcc` + lightweight threads required a **new custom LLVM
backend** ([Compiling with Continuations and LLVM, arXiv 1805.08842](https://arxiv.org/abs/1805.08842),
quote verified against the abstract). LLVM's own **coroutines are stackless** —
they suspend **only at explicitly-marked points** — and the docs warn that
function-splitting at suspend points defeats optimizations (LICM had to be disabled
for loops containing `coro.suspend`) ([LLVM Coroutines](https://llvm.org/docs/Coroutines.html),
verified). GLP's **any-goal-can-suspend-on-any-reader** model is exactly the
stackful pattern LLVM coroutines handle poorly. The §7a "cooperative
run-to-completion chain" scheduler hits the same wall.

### 2.3 Committed-choice concurrency itself is unprecedented on LLVM, and LLVM IR has no concurrency model

No surveyed LLVM/MLIR work targets committed-choice / flat-concurrent-logic
semantics. The **nearest production analog deliberately chose C, not LLVM**: **KLIC**
is the **KL1-to-C compiler**, KL1 being an implementation of **Flat GHC** — the same
committed-choice family as GLP — relying on the C compiler for machine-dependent
optimization ([KL1, Wikipedia](https://en.wikipedia.org/wiki/KL1), verified;
[KLIC, SAL](http://www.sai.msu.su/sal/C/1/KLIC.html);
[Ueda, study overview](https://www.ueda.info.waseda.ac.jp/~ajiro/study-e.html)).
Separately, **LLVM IR "was not designed for parallelism"**; bolting parallelism on
via metadata/intrinsics breaks conventional serial analysis
([UPIR, arXiv 2209.10643](https://arxiv.org/pdf/2209.10643)). GLP's concurrency is
lost before any optimization could see it.

### 2.4 The footprint / dependency cost is antithetical to the §7a many-instances goal

§7a wants **many minimal-footprint single-threaded instances** sharing static
machinery. LLVM is a **heavyweight dependency**: a trivial JIT example is multiple
MB statically linked, a full build needs 15–20 GB, and per-instance JIT means
**warm-up latency + resident codegen memory in every instance**
([LLVMdev, "Why are LLVM libraries enormous?"](https://groups.google.com/g/llvm-dev/c/InMxMlH5fXg);
[Building a Distribution of LLVM](https://llvm.org/docs/BuildingADistribution.html)).
This is the opposite of a tiny, fast-to-spawn engine.

### 2.5 Bitcode is the wrong substrate for a stable, persisted, cross-runtime IL (§3, §6)

This is the most direct mismatch. The §3 IL must be **stable, versioned, persisted
to a DB across very-long-lived restart-resume (§6), and shared identically across
C# / Dart / C++**. LLVM **bitcode is explicitly non-portable and non-stable** — it
"changes over time as optimization and language requirements change," is
architecture-dependent, and was designed for **temporary** link-time-optimization
serialization, with only **backward** compatibility guaranteed, not forward or
cross-implementation ([LLVM BitCodeFormat](https://llvm.org/docs/BitCodeFormat.html),
verified: only legacy-decode is guaranteed, the format evolves;
[LLVM LangRef](https://llvm.org/docs/LangRef.html);
[ENOSUCHBLOG, "LLVM internals part 1: the bitcode format"](https://blog.yossarian.net/2021/07/19/LLVM-internals-part-1-bitcode-format)).
Adopting bitcode as the persisted GLP IL would **couple the engine's durable state
to a specific LLVM version** — directly against §6. There is no C++ ANTLR4 / Dart
counterpart that produces or consumes LLVM bitcode for free either.

### 2.6 MLIR's own authors flag the GLP-relevant gaps as open challenges

Even MLIR — the best-fit option — lists the exact areas GLP needs as open:
**"Supporting garbage-collected languages, higher-order and polymorphic type systems
with type inference are open challenges"** ([MLIR paper, arXiv 2002.11054](https://arxiv.org/pdf/2002.11054)
/ [uwaterloo mirror](https://rcs.uwaterloo.ca/~ali/cs842-s23/papers/mlir.pdf),
confirmed via search). GLP needs a GC'd, tagged/boxed term heap (logic variables,
structs, SRSW writers) — precisely the flagged-hard region.

### 2.7 The whole logic-language field bypassed LLVM for high-level / compact targets

The convergent prior art is decisive. **Mercury** targets C / Java / C# — **no LLVM
backend** ([Mercury backends](https://mercurylang.org/about/backends.html);
[Mercury, Wikipedia](https://en.wikipedia.org/wiki/Mercury_(programming_language))).
**Souffle** (Datalog) lowers a **domain-specific Relational Algebra Machine (RAM) IR
to specialized parallel C++**, with domain-specific index/join optimization LLVM
cannot express — and Souffle is used to *analyze* LLVM, not generated from it
([Souffle tutorial](https://souffle-lang.github.io/tutorial);
[Souffle applications](https://souffle-lang.com/applications)).
**GNU Prolog** goes WAM → a purpose-built **"mini-assembly"** IL → native, without
LLVM ([GNU Prolog manual §9](http://www.gprolog.org/manual/html_node/gprolog009.html)).
**Ciao / imProlog** compiles a WAM emulator written in a Prolog dialect to C and
lands **within ~8% of hand-tuned YAP — without LLVM**
([imProlog, arXiv 1411.5573](https://arxiv.org/abs/1411.5573);
[imProlog TR](https://cliplab.org/papers/morales09:improlog-tr.pdf)). The
performance answer in this field is a **domain-specific IL lowered to C/C++**, which
is exactly the FCP/WAM/KL1 lineage the feature already cites — and exactly what the
ANTLR4 multi-target (C# / Dart / C++) plan in §2a/§2b naturally produces.

## 3. Recommendation — CONDITIONAL, off the critical path

**Do NOT base the §3 binary IL, the persistence format, or the engine's mandatory
codegen substrate on LLVM/MLIR.** Design a **GLP-native, compact, self-versioned
binary IL** in the WAM / FCP / KL1 lineage, single-sourced from the ANTLR4 grammar
(§2a) and lowered to C# / Dart / C++ (the Mercury / Ciao / GNU-Prolog / Souffle
route). This satisfies §3's stability + cross-runtime requirement, §6's durable
persistence, and §7a's minimal footprint — all of which LLVM bitcode and the LLVM
toolchain actively work against (§2.4, §2.5).

**Conditionally YES to going deeper — but only behind a hard gate.** The condition:
**only if and when a §2b high-performance C++ engine variant is actually being
built AND profiling shows ground, deterministic numeric / guard-arithmetic
reduction kernels are a measured bottleneck.** In that and only that situation, an
*optional, opt-in* native-code accelerator for those kernels is worth a verification
spike. It must **never** be on the many-instance minimal-footprint path, never the
IL, never carry committed-choice/unification/suspension semantics, and never become
a load-bearing dependency of the C#/Dart engines. The MLIR rewrite infrastructure
(and the egglog-style "logic-drives-the-optimizer" direction, §1.4) is a *separate*,
also-deferred candidate for IL-level optimization tooling — not for lowering GLP into
LLVM.

If no high-performance C++ variant materializes, or kernels never bottleneck, the
correct answer is **no** — close the LLVM thread and keep the GLP-native IL + C/C++
lowering.

## 4. Verification spike (only if the §3 condition is met)

**Goal:** confirm — cheaply, in isolation — that LLVM can accelerate *only the
post-commit ground kernel layer* without contaminating the IL, the persistence
format, or the footprint budget.

**Build (timeboxed, ~1 week, throwaway, NOT on the engine critical path):**

1. Pick **one** hot, fully-ground, deterministic GLP reduction chain that is
   arithmetic/struct-shaped (e.g. an integer-guard + arithmetic-body loop already
   committed — no unbound readers, no suspension, no choice). Capture it as a small
   slice of the GLP-native IL.
2. Lower **that slice only** to LLVM IR (or an MLIR `glp` dialect → LLVM dialect),
   and JIT it with **ORCv2** at runtime, invoked by the existing C++/C# runtime
   *after* unification/commit has happened in the hand-built runtime.
3. Keep the unification, SRSW binding, suspension queue, and scheduler **entirely in
   the existing runtime** — the spike compiles **none** of them.

**Measure / what it proves:**

- **Speedup** of the JIT'd ground kernel vs the interpreted IL on a representative
  workload (the GHC bar: is it ~20%+ on numeric-heavy chains, or negligible?).
- **Per-instance footprint delta** (static link size + resident JIT memory + cold
  warm-up latency) measured against the §7a many-instances budget — the gating
  number; if it blows the budget, the accelerator is rejected regardless of speedup.
- **Containment:** demonstrate the IL on the wire and in the DB is unchanged
  GLP-native bytecode (no bitcode persisted, no LLVM version coupling), proving the
  accelerator is a pure downstream consumer.

**Decision rule:** proceed past the spike only if speedup is material on the target
workload **and** the footprint delta is acceptable for the C++ variant **and**
containment holds (zero LLVM coupling in IL/persistence/wire). Any one failing →
drop LLVM, keep the GLP-native IL lowered to C/C++.

---

## 5. One-line verdict

LLVM/MLIR is **not** the GLP intermediate language and must not touch the §3/§6
persisted wire format or the §7a footprint path; its only defensible role is an
**optional, gated, downstream native-code accelerator for ground deterministic
kernels of a future C++ engine variant** — a bounded benefit (GHC-style ~20% on
numeric code) against a high cost (footprint, build weight, version-unstable
bitcode, and a fundamental SSA/runtime-model mismatch with unification +
suspension + committed-choice concurrency). Every nearest analog in the field
(KLIC, Mercury, GNU Prolog, Ciao, Souffle) chose a domain-specific IL lowered to C —
the route this feature is already on.
