Critically, **Claude is restricted to structural generation only — no LM on the verification path**; the MLIR parser/printer + equality check are the oracle (`RESULT.md:49-54`, `MLIR-GLP-DIALECT.md:61-66`).

What is **only PROPOSED (deferred to seeds #4/#11)**: the full opcode set, the production dialect + TableGen + verifier, and all lowering passes (`MLIR-GLP-DIALECT.md:38-48,84-90`). ## (b) Compiling to a machine language — CONCLUDED: serialize the existing ISA, don't invent one

The research programme's net recommendation is explicit: **"Serialize the existing v2.16.3 ISA — do not invent a new ISA"** (`research-programme.md:212-213`), because the glpnet GLP bytecode is already WAM-shaped, so the wire format is "a serialization of an ISA the engine already executes" (`research-programme.md:37-39,209`). The closest precedent is the **FCP sequential abstract machine** (Houri & Shapiro, CS86-20; CARMEL-2 = **29 instructions**), proving a committed-choice ISA is tiny (`research-programme.md:25-32,202`). Committed-choice removes backtracking/choice-points/trail ⇒ **redo-only WAL, no undo** — a major simplification (`research-programme.md:16-17,184-185`).

Two further concluded directions: **one codec for BOTH wire and persistence** (SICStus `.po` == saved-state; BinProlog continuation-as-term) (`research-programme.md:48-52,205,214-216`); and **mode-as-bit-field** — the V2 ISA already folds reader/writer pairs into one opcode + `isReader` flag (`research-programme.md:57-60,219-220`). These are **PROPOSED designs / SPIKE plans** (SPIKE-2 "one codec, two uses", `research-programme.md:429-432`), not yet built — note that #29 il-codec-spike has since shipped per project memory, but that is outside these documents. Within this corpus there is **zero serialization in the engine**: `BytecodeProgram.Instructions` is in-memory `IReadOnlyList<object>`, `ToDisassembly()` is human-readable only, no Serialize/Encode/ToBytes (`16-research-programme-and-llvm-feasibility.md:79-84`; `11-…factor-out-compiler.md:66-67`).

## (e) Lowering to LLVM/imperative as a BACKEND step — SCOUTED, verdict CONDITIONAL-NO

`llvm-feasibility.md` is a completed SCOUT (`:8`). Verdict: **do NOT base the IL, persistence format, or mandatory codegen on LLVM/MLIR** (`:214-220,278-281`). Reasons, each primary-sourced: SSA cannot represent a destructively-bound logic variable (`:110-122`); goal suspension/reactivation is the heap-allocated-continuation model LLVM is documented-weak-at (Manticore needed a custom backend; LLVM coroutines suspend only at marked points) (`:124-140`); committed-choice concurrency is unprecedented on LLVM and "LLVM IR was not designed for parallelism" (`:141-154`); bitcode is non-portable/version-unstable — wrong for a stable persisted cross-runtime IL (`:165-179`); MLIR's authors flag GC'd/polymorphic type systems as open challenges (`:181-188`); and the whole field (Mercury, Souffle, GNU-Prolog, Ciao, KLIC) chose a **domain-specific IL lowered to C/C++**, the route already taken (`:190-208`).

The **only defensible LLVM role**: an *optional, gated, downstream native-code accelerator* for **ground/deterministic post-commit numeric kernels** of a *future C++ engine variant* — gated on a C++ engine actually being built AND a profiled bottleneck (GHC-style ~20% on numeric code) (`:212-237,276-286`). MLIR-as-infrastructure (custom `glp` dialect, progressive lowering — `:71-92`) and egglog "logic-drives-the-optimizer" IL-rewriting (`:93-104`) are noted as separate deferred candidates. A throwaway ~1-week verification spike is *designed but NOT executed*, conditional on the C++-engine gate (`:240-274`; gating noted in `16-…:135-152,196-207`).
