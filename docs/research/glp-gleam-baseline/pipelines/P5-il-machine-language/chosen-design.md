# Recommended GLP Front/Back Seam — Synthesis

## 1. RECOMMENDED SEAM

**What crosses front→back: the compiled machine language plus a heap-independent result envelope — nothing else.** The forward artifact is a serialized `BytecodeProgram` (flat instruction list + derivable label table, `runner.dart:50-64`) in the existing WAM/FCP-shaped **v2.16.3 ISA** (`docs/glp-bytecode-v216-complete.md`; "directly follows the Flat Concurrent Prolog Abstract Machine," `bytecode-v216:548`). The return artifact is a **self-contained result envelope** — `{Status, Bindings, Error}` resolved *server-side* into heap-independent values, plus the three components codegen already computes but drops: var-name→writer-id map, suspended-goal detail, captured output (G4 §1.3; INV-5, design-dossier line 416). All three outcomes Success/Suspend/Fail ride it. The **same two artifacts are identical in-process and over-the-wire** — in-process the `BytecodeProgram` passes by reference and the envelope is a struct; remotely both are framed through a byte codec. Resolving bindings server-side closes today's worst leak: `Bindings` are currently live `VarRef`s into engine-owned heap (G4 §1.3 line 84).

**Where the compiler lives: the front-end** (relocated from engine-internal `GlpEngine._compiler`, `glp_engine.cs:148`; "primarily a project/reference boundary change," 11-…:69-70). Pipeline: ANTLR `.g4` → AST → partial-eval → type-check → analyze → **GLP-IL → lower → v2.16.3 bytecode → codec**.

**Logic-IL role: a front-end-internal codegen + verification aid, NOT the seam.** The four-primitive GLP/FCP dialect — `head_unify` / `guard_test` / `body_spawn` / `suspend_reactivate` (`MLIR-GLP-DIALECT.md:22-31`; spike-PASS round-trip `RESULT.md:1-7`) — sits between analyzer and codegen, where Mercury puts HLDS before backend selection (`mercurylang.org/.../compiler_design.html`). It makes GLP's invariants statically checkable (phase-order HEAD<GUARD<BODY, single-writer/SRSW — the named op-verifier obligation, `MLIR-GLP-DIALECT.md:46-48`) and hosts clause-indexing / guard-simplification before emission. **The IL never crosses the boundary; only the bytecode does.** This is the owner's Q3 hypothesis and BinProlog's shipped design — binarization is "a source-level transform that produces the ISA" (arXiv:1102.1178; W3 Option C).

**Separate seam — the maGLP agent-link (M2).** Inter-agent execution carries neither bytecode nor IL; its wire unit is a **globalized GLP term + global name** (`_w(p,i):=T↑` / `_r(p,i):=T↑`; GLP_IMPLEMENTATION.pdf Def 6.12-6.13, 6.25; G2 §3). Two seams, two payloads — kept distinct.

## 2. DIRECT ANSWERS — Q1–Q6

**Q1 — parser→backend hand-off.** The abstract-machine language is normally the seam; an IL *above* it is the Mercury/LingoDB exception for multi-target/analysis (W3). Systems compile source→AST→machine-ISA→runtime directly: SWI's ZIP VM, BinWAM (arXiv:1102.1178), KL1-B "unification, goal-manipulation, suspension instructions" (ICOT TR-246), CARMEL (W1/W2). Logix additionally splits **persistent module (compile unit) vs ephemeral computation (run unit)** — the documented front/back precedent (W2).

**Q2 — compile DIRECTLY to a logic ML as the seam?** Yes. The front-end already compiles AST→v2.16.3 with no IL (`compiler.dart:56-128`; `codegen.dart:107-133`), and the FCP/CARMEL lineage proves a committed-choice ISA is tiny (CARMEL-2 = 29 instructions) and directly targetable (W2). Shapiro's FCP Sequential Abstract Machine (Houri & Shapiro CS86-20; US 5,222,221A) has four categories ≈ HEAD/GUARD/BODY + a `suspend` instruction and activation queue — but defines only a *single-cell read-only reference*, not writer-MGU (W2 §4). "Align with FCP" means *stay shaped like it*, not adopt verbatim; v2.16.3's two-cell writer/reader extension is what keeps M1 faithful.

**Q3 — need an IL; would a logic-centric IL help generate the ML better?** Not for the seam — the bytecode suffices (Q2). But the owner's hypothesis holds and is what this design recommends: a front-end-internal GLP/FCP IL **generates the bytecode better** by making SRSW / phase-order / writer-MGU machine-checkable *before* emission (`MLIR-GLP-DIALECT.md:46-48`) and hosting cross-target optimization once (Mercury HLDS, W3) — strictly more analyzable than the syntax-directed emitter, which checks only locally (the gap behind the two live F4 review bugs: self-bind→`Unbound`, suspension-drop; G4 §1). **Caveat:** these verifiers are the #11 obligation, *not yet built* (G3(a)).

**Q4 — clean separation; thin/heterogeneous front-end; ANTLR grammar.** Achieved because the contract — bytecode + server-resolved envelope — is *identical* in-process and on-wire (§3); the engine does "no parsing/compilation/display" (design-dossier §1.1). ANTLR has **no BEAM target** (`antlr4/doc/targets.md`), so a `.g4` grammar generates a parser in a supported target (C#/Dart) → thin heterogeneous front-end emitting bytecode to a pure-Gleam engine (W4 Option A). No `.g4` exists today (`12-…:50`).

**Q5 — preserves M1, M2, Gleam/AtomVM?** Yes. **M1** is observable-outcomes-only — three-valued verdict, deref result, activation set; internal heap layout free to differ (spec 034 line 27; FR-009/SC-005). The IL changes *how* bytecode is generated, not what the engine observes; the shipped Gleam F4 kernel already realizes the faithful model (writer-only binding `heap.gleam:59-64`; self-bind→`Unbound` `heap.gleam:165-175`; suspension forwarding to terminal writer `heap.gleam:251-278`). **M2** is bounded at outcome-equivalent globalized-term exchange (G2 §3; Remark 3.35) *and* byte-identical codec parity (FrameCodec/Crc32, G4 §2.5). **Do not** treat ISA-identity as sufficient for M2 — parity is the term protocol + byte-identical codec, which sit above/beside the ISA (critique). **AtomVM:** all compile-time machinery stays off-device; the device runs only compact bytecode + an interpreter — "plain sequential BEAM code (fine for AtomVM); only the spawn primitive needs the raw form" (F1 dossier line 134), via raw `erlang:spawn` + Subjects, no `gleam_otp` (FR-010), immutable threaded store (`heap.gleam:69-71`).

**Q6 — in practice for GLP.** Committed-choice = `ClauseTry`→guards→`Commit`/`NoMoreClauses`, no backtracking/trail (`bytecode-v216:171-237`). Three-phase HEAD/GUARD/BODY is the ISA's structure and the IL's enforced op order. SRSW + two-cell writer/reader are IL-verifiable operands, then realized by the engine. Suspension/reactivation: `suspend_reactivate` lowers to in-reader suspension records + activation lists (`bytecode-v216:42-75`; `heap.gleam:251-278`). The seam transmits compiled clauses; the engine runs them unchanged.

## 3. SEPARATION

Clean separation rests on one property: **the crossing contract is the same object in-process and on-wire.** The engine's public surface is `GlpEngine` + `ExecutionResult` (design-dossier §1.2); the front-end owns I/O, dispatch, display; the engine owns lower+execute+schedule+suspend. Because the envelope is resolved server-side and heap-independent (INV-5), a local call and a framed message carry identical payloads — so splitting front from back becomes a deployment choice, not a re-architecture. The thin front-end is enabled by an **ANTLR `.g4` single source of truth** generating C#/Dart parsers (W4 Option A) — one analyzable grammar, multi-host, feeding the IL. **M1** is unperturbed because the IL/codec change generation/transport, not observable outcomes (spec 034 line 27). **M2 on Gleam/AtomVM** holds because every runtime executes the same frozen ISA *and* agrees a byte-identical codec + globalized-term protocol; heap re-expression (Gleam immutability) stays a private back-end concern. Critically, **M1 (outcomes) and M2 (byte-identical wire) are parity at different layers and meet only at the seam** — which is why the seam must be the machine language + envelope, never the heap (G4 §4).

## 4. GENUINE FORKS FOR THE OWNER

**Fork A — Machine-language identity.** (a1) *Keep + freeze/version v2.16.3* — the GLP-correct heir of the FCP machine, already on-disk and more completely specified than any open FCP artifact (W2). Consequence: least churn; must resolve the v1/v2 opcode split and stabilize before it crosses (SWI `.qlf` "Sensitive to VM instruction numbering," W3). (a2) *Re-align toward Shapiro's FCP four-category machine* — matches a published lineage, but FCP lacks writer-MGU and any multiagent layer; adopting verbatim breaks M1 (W2 §4). On-disk net recommendation favors **a1** ("serialize the existing ISA — do not invent one," research-programme.md:212-213).

**Fork B — IL: build it at all, and as what?** The load-bearing fork (Design 1 vs Design 3), governed by *backend count + analysis ambition* (W3 pivot). (b1) *No IL* (Design 1) — lowest surface, matches research-programme.md:212-213; forgoes static SRSW/phase/writer-MGU checking and shared optimization — acceptable only if the project stays single-target Gleam with no optimization ambition. (b2) *IL front-end-internal* (recommended here) — buys analyzability + multi-target codegen; net-new layer over a working emitter, justified only once ambition is declared. (b3) *IL as the seam* (Design 2) — **disqualified for AtomVM**: MLIR is C++ infrastructure, cannot run on-device (G4 §3); contradicts research-programme.md:212-213 and llvm-feasibility.md:214-220. If b2, sub-fork: **real-MLIR dialect** (free verifier/rewrite infra, heavy C++/Python dep that ran only on WSL2, `RESULT.md:22-46`) vs **lightweight in-language IR** on the 4 primitives (no dep; hand-built verifiers).

**Fork C — Compiler placement / what's on the wire.** (c1) *Compiler in front-end, compiled-ML-on-wire* (recommended) — enables thin heterogeneous clients + the single ANTLR grammar; larger refactor; obligates the Section-15 codec to Dart↔C#↔Gleam byte-parity, de-embedding `Object?`/`StructTerm` operands (G1 §5), *and* an AtomVM bit-syntax spike (G4 §3 — **do not** cite 029's C# `IlCodec` as proof; build + spike here). (c2) *Compiler engine-side, source-on-wire* — only a result codec is net-new, no compiler relocation (G4 Opt 1 line 319); but the seam is then *not* the machine language, so thin clients and an ANTLR front-end are **not** enabled.
