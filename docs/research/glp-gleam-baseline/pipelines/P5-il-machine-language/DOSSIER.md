# GLP Front/Back Seam — Intermediate Language vs Machine Language (decision dossier)

## Executive answer

Yes — we can compile **directly into a logic machine language as the seam**: the front-end already emits the WAM/FCP-shaped **v2.16.3 bytecode ISA** with no intermediate language (`compiler.dart:56-128`; `codegen.dart:107-133`), and the FCP/CARMEL/KL1 lineage proves a committed-choice ISA is tiny (CARMEL-2 = 29 instructions) and directly targetable (W2; W1). So **no separate IL is required for the seam itself.** We do **not need** an IL to *cross the boundary*. We *do* benefit from one **inside the front-end** — the owner's Q3 hypothesis, and BinProlog's shipped design: a 4-primitive GLP/FCP IL that makes SRSW / phase-order / writer-MGU machine-checkable before emission and hosts cross-target codegen, while **only the bytecode crosses** (`MLIR-GLP-DIALECT.md:22-31,46-48`; arXiv:1102.1178). **Recommendation:** seam = serialized v2.16.3 bytecode **+ a server-resolved, heap-independent result envelope**, identical in-process and on-wire; compiler relocates to the front-end; the logic-IL is a front-end-internal generation/verification aid, not the wire artifact; the maGLP agent-link stays a *separate* term-level seam. Two genuine owner forks remain (build the IL at all; ML-on-wire vs source-on-wire).

## Q1–Q6 answered

**Q1 — How logic languages structure the parser→backend hand-off.** The abstract-machine language is normally the seam; an IL *above* it is the exception used for multi-target/analysis. Systems go source→AST→machine-ISA→runtime directly: SWI's ZIP VM (arXiv:1011.5332), BinWAM (arXiv:1102.1178), KL1-B "unification, goal-manipulation, suspension instructions" (ICOT TR-246), GNU-Prolog (mini-assembly sits *below* WAM, JFLP 2001), CARMEL (W1/W2). Logix adds the documented front/back precedent: **persistent module (compile unit) vs ephemeral computation (run unit)** (nongnu.org/efcp; W2). Mercury is the IL exception — HLDS→MLDS/LLDS→{C,Java,C#} for analysis-high, multi-target reach (mercurylang.org/.../compiler_design.html).

**Q2 — Compile DIRECTLY to a logic ML as the seam?** Yes. The front-end already does AST→v2.16.3 with no IL (`codegen.dart:107-133`); the runner consumes a flat `BytecodeProgram` = instruction list + derivable label table (`runner.dart:50-64`) — a clean in-process seam today. Shapiro's FCP Sequential Abstract Machine (Houri & Shapiro CS86-20; US 5,222,221A) has four instruction categories ≈ HEAD/GUARD/BODY + a `suspend` instruction and activation queue — but defines only a *single-cell read-only reference*, **not writer-MGU**. So "align with FCP" means *stay shaped like it*, not adopt verbatim; v2.16.3's two-cell writer/reader extension is what keeps M1 faithful (W2 §conclusion). The doc self-describes as "directly follow[ing] the Flat Concurrent Prolog Abstract Machine" (`bytecode-v216:548`).

**Q3 — Do we need an IL; would a logic-centric IL help generate the ML better?** Not for the seam — the bytecode suffices (Q2). But the owner's hypothesis holds and is what we recommend: a front-end-internal GLP/FCP IL — `head_unify`/`guard_test`/`body_spawn`/`suspend_reactivate` (`MLIR-GLP-DIALECT.md:22-31`, real-MLIR round-trip PASS `RESULT.md:1-7`) — **generates the bytecode better** by making SRSW / phase-order (HEAD<GUARD<BODY) / writer-MGU machine-checkable *before* emission (`MLIR-GLP-DIALECT.md:46-48`) and hosting indexing/guard-simplification once (Mercury HLDS, W3). This is strictly more analyzable than the current syntax-directed emitter, which checks only locally — the gap behind the two live F4 review bugs (self-bind→`Unbound`, suspension-drop; G4 §1). **Caveat: these verifiers are the #11 obligation, not yet built** (G3(a)). BinProlog's binarization is the shipped precedent: "a source-level transform that produces the ISA" (arXiv:1102.1178; W3 Option C).

**Q4 — Clean separation; thin/heterogeneous front-end; ANTLR grammar.** Achieved because the crossing contract — bytecode + server-resolved envelope — is *identical* in-process and on-wire (§Recommended). The engine does "no parsing/compilation/execution/scheduling/suspension" (design-dossier §1.1). ANTLR has **no BEAM target** (10 targets, no Erlang/Gleam; `antlr4/doc/targets.md`), so a single `.g4` generates a parser in a supported target (C#/Dart) → thin heterogeneous front-end emitting bytecode to a pure-Gleam engine (W4 Option A). No `.g4` exists today (`12-antlr4-shared-grammar-spike.md:50`); both runtimes use hand-written recursive descent.

**Q5 — Preserves M1, M2, Gleam/AtomVM?** Yes. **M1** is observable-outcomes-only — three-valued verdict, deref result, activation set; internal heap layout is "free to differ once the heap is re-expressed for Gleam" (spec 034 line 27; FR-009/SC-005). An IL changes *how* bytecode is generated, not what the engine observes; the shipped Gleam F4 kernel already realizes the faithful model (writer-only binding `heap.gleam:59-64`; self-bind→`Unbound` `heap.gleam:165-175`; suspension forwarding to terminal writer `heap.gleam:251-278`). **M2** is parity at a *different* layer: byte-identical codec (FrameCodec/Crc32, FR-060/061) **plus** outcome-equivalent globalized-term exchange (`GLP_IMPLEMENTATION.pdf` Def 6.12-6.13, 6.25; Remark 3.35). **Do not treat ISA-identity as sufficient for M2** — parity is the term protocol + byte-identical codec, which sit above/beside the ISA (critique). **AtomVM:** all compile-time machinery stays off-device; the device runs only compact bytecode + an interpreter — "plain sequential BEAM code (fine for AtomVM); only the spawn primitive needs the raw form" (F1 dossier line 134), via raw `erlang:spawn` + Subjects, no `gleam_otp` (FR-010), immutable threaded store (`heap.gleam:69-71`).

**Q6 — In practice for GLP.** Committed-choice = `ClauseTry`→guards→`Commit`/`NoMoreClauses`, no backtracking/choice-point/trail (`bytecode-v216:171-237`; W1 §2). Three-phase HEAD/GUARD/BODY is the ISA's structure *and* the IL's enforced op order. SRSW + the two-cell writer/reader model are IL-verifiable operands (the per-instruction `isReader` flag, `opcodes_v2.dart:29,47,65`), then realized by the engine. Suspension/reactivation: `suspend_reactivate` lowers to in-reader suspension records + activation lists (`bytecode-v216:42-75`; `heap.gleam:251-278`). The seam transmits compiled clauses; the engine runs them unchanged.

## Recommended seam design

**What crosses front→back: the compiled machine language plus a heap-independent result envelope — nothing else.** Forward artifact = a serialized `BytecodeProgram` (flat instruction list + derivable label table, `runner.dart:50-64`) in the v2.16.3 ISA. Return artifact = a **self-contained `{Status, Bindings, Error}` envelope resolved server-side** into heap-independent values, plus the three components codegen already computes but drops: var-name→writer-id map, suspended-goal detail, captured output (design-dossier §1.3, line 84-92; INV-5 line 416). All three outcomes Success/Suspend/Fail ride it. The **same two artifacts are identical in-process and over-the-wire** — in-process the program passes by reference and the envelope is a struct; remotely both frame through a byte codec. Resolving bindings server-side closes today's worst leak: `Bindings` are currently live `VarRef`s into engine-owned heap (G4 §1.3).

**Where the compiler lives: the front-end** (relocated from engine-internal `GlpEngine._compiler`, `glp_engine.cs:148`; "primarily a project/reference boundary change," `11-factor-out-compiler.md:69-70`). Pipeline: ANTLR `.g4` → AST → partial-eval → type-check → analyze → **GLP-IL → lower → v2.16.3 bytecode → codec**.

**Logic-IL role: a front-end-internal codegen + verification aid, NOT the seam.** It sits between analyzer and codegen, where Mercury puts HLDS before backend selection. The IL never crosses the boundary; only the bytecode does (owner's Q3; BinProlog's design). **Separate seam — the maGLP agent-link (M2):** inter-agent execution carries neither bytecode nor IL; its wire unit is a globalized GLP term + global name (`_w(p,i):=T↑`; `GLP_IMPLEMENTATION.pdf` Def 6.12-6.13, 6.25; G2 §3). Two seams, two payloads, kept distinct.

## How it actually works for one GLP clause (merge/3)

Take the canonical stream merger, clause 1:
`merge([X|Xs?], Ys?, Zs) :- Zs := [X|Zs1?], merge(Xs?, Ys?, Zs1).`

1. **ANTLR parse.** The `.g4` lexes the READER token `?` (`Xs?`, `Ys?`, `Zs1?`) and GUARD_SEP `|` (token vocab pinned `token.cs:1-71`), producing an AST adapted to the existing `AstNode` hierarchy: head with one list-cons arg + two args; body = an output-binding goal + a recursive call.

2. **GLP-IL.** Lowering emits `head_unify` ops for the three head args, `body_spawn` for the recursive `merge`, and (none here) `guard_test`. **Before emitting bytecode**, the op-verifiers check: phase order HEAD<GUARD<BODY; SRSW (each variable's writer/reader pair occurs once — `X` writer in head, `X` read in body via `[X|Zs1?]`; `Zs` writer in head, written in body); single-writer (only `Zs`, `Zs1` are writers) (`MLIR-GLP-DIALECT.md:46-48`). A non-faithful clause is *rejected here*, not at runtime.

3. **Machine language (v2.16.3).** Codegen walks the annotated AST and emits: arg1 `[X|Xs?]` → `HeadList`, then `GetVariable`(X, writer, first-occurrence) + `UnifyVariable(isReader)` for `Xs?` (`codegen.dart:275-313,345-385`); arg2 `Ys?` → `GetVariable(isReader)`; arg3 `Zs` → writer slot. Body: `Zs := [X|Zs1?]` → `PutStructure`/`SetVariable` building the cons (`codegen.dart:461-575`); then the recursive call → `PutVariable`/`PutValue` for args + `Spawn`. Output: `BytecodeProgram(ctx.instructions)`. This serializes via the (to-be-built) Section-15 codec; only this crosses to the engine.

4. **Execution incl. suspension.** Run goal `merge(As?, Bs?, Cs)` with `As?` an **unbound reader**. `HeadList` attempts to match `As?` against `[X|Xs?]`: reader × structure where the reader is unbound → three-valued unify returns **Suspend, not Fail** (the most common GLP correctness error if mishandled; `unify.gleam:93-95`). The engine stores a suspension record *in `As?`'s reader cell* and adds the goal to U (`bytecode-v216:42-75`; `heap.gleam:251-278`). No backtracking — clause-try simply suspends. Later, when some writer binds `As?` to e.g. `[a|As1?]`, binding-to-value emits the armed activation; the goal reactivates at κ and re-runs the head match, now succeeding and committing. The envelope returned to the front-end carries `Status=Suspend` + the suspended-goal detail + the var→writer-id map — heap-independent, identical whether the call was local or framed over the wire.

## Owner decision forks (options-with-consequences)

**Fork A — Machine-language identity.** *(a1) Keep + freeze/version v2.16.3* — the GLP-correct heir of the FCP machine, on-disk and more completely specified than any open FCP artifact (W2). Least churn; must resolve the v1/v2 opcode split and stabilize *before* it crosses (SWI `.qlf` "Sensitive to VM instruction numbering," W3). *(a2) Re-align to Shapiro's four-category FCP machine* — matches a published lineage but lacks writer-MGU and any multiagent layer; verbatim adoption breaks M1 (W2 §4). On-disk net recommendation favors **a1** ("serialize the existing ISA — do not invent one," `research-programme.md:212-213`).

**Fork B — IL: build it at all, and as what?** The load-bearing fork, governed by *backend count + analysis ambition* (W3 pivot). *(b1) No IL* — lowest surface, matches `research-programme.md:212-213`; forgoes static SRSW/phase/writer-MGU checking + shared optimization; acceptable only if the project stays single-target Gleam with no optimization ambition. *(b2) IL front-end-internal* (recommended) — buys analyzability + multi-target codegen; net-new layer over a working emitter, justified only once ambition is declared. *(b3) IL as the seam* — **disqualified for AtomVM**: MLIR is C++ infrastructure, cannot run on-device (G4 §3); contradicts `research-programme.md:212-213` and `llvm-feasibility.md:214-220`. If b2, sub-fork: **real-MLIR dialect** (free verifier/rewrite infra, heavy C++/Python dep that ran only on WSL2, `RESULT.md:22-46`) vs **lightweight in-language IR** on the 4 primitives (no dep; hand-built verifiers).

**Fork C — Compiler placement / what's on the wire.** *(c1) Compiler in front-end, compiled-ML-on-wire* (recommended) — enables thin heterogeneous clients + the single ANTLR grammar; larger refactor; obligates the Section-15 codec to Dart↔C#↔Gleam byte-parity, de-embedding `Object?`/`StructTerm` operands (G1 §5), *and* an AtomVM bit-syntax spike (do **not** cite 029's C# `IlCodec` as proof — build + spike here, G4 §3). *(c2) Compiler engine-side, source-on-wire* — only a result codec is net-new, no compiler relocation (design-dossier Opt 1); but the seam is then *not* the machine language, so thin clients and an ANTLR front-end are **not** enabled.

## Proposed verifiable SPIKE

**Goal:** confirm that ANTLR-parse → logic-IL → v2.16.3 bytecode produces an *execution-equivalent* program to the existing codegen, for one clause, with the IL verifiers actually firing.

**Smallest experiment (one clause, `merge/3` clause 1 above):**
1. Write a minimal `merge.g4` covering exactly its tokens (READER `?`, GUARD_SEP, list-cons, atoms, vars); generate the **C# or Dart** parser (a supported ANTLR target) — adapt its parse tree to one `AstNode`.
2. Lower that AST through the 4-primitive IL; run the **two op-verifiers** (phase-order, single-writer/SRSW) and assert they PASS on the faithful clause and FAIL on a deliberately mutated SRSW-violating variant (proves the analyzability win is real, not paper).
3. Lower IL → v2.16.3 bytecode; **disassemble and diff** against `CodeGenerator.generateWithMetadata` output for the same clause. Where they differ, justify (indexing/order) or reconcile.
4. **Execution-equivalence:** load both programs into the existing runner and run goal `merge(As?, Bs?, Cs)` with `As?` unbound; assert both yield `Status=Suspend` with the same suspended-goal/var map; then bind `As?` and assert both reactivate and commit identically.

**Pass bar:** verifiers fire correctly (3a), and the two pipelines are execution-equivalent on success + suspension (3b/4). This needs **no** codec, no MLIR-on-device, no Gleam port — it isolates exactly the owner's Q3 claim ("IL helps generate the ML better, verifiably") against the existing emitter. (A second, *separate* spike — Section-15 byte-codec round-trip on AtomVM bit-syntax — gates Fork C/c1 and should not be conflated with this one.)

## Open questions / primary-source confirmation still needed

1. **AtomVM binary/bit-syntax** for the ML codec is *unspiked* — F1 evidenced spawn + sequential execution, not binary decoding on-device (G4 §3). Required before relying on c1. Do **not** cite 029 `IlCodec` (C#, project-memory) as proof for the Dart/Gleam path.
2. **Section-15 "Instruction Encoding" is `NOT IMPLEMENTED`** (`bytecode-v216:1350-1352`) — there is no wire format today; `Object?`/`StructTerm` operands embed in-process objects (`opcodes.dart:99,116,133`; `codegen.dart:652-653`) and must be de-embedded.
3. **The IL op-verifiers are the #11 obligation, not built** (`MLIR-GLP-DIALECT.md:46-48`; G3(a)) — only a 4-op round-trip smoke PASSes (`RESULT.md`, ILFRAG-1, WSL2). The recommendation's analyzability payoff is *to-be-built*, not demonstrated end-to-end.
4. **CARMEL-2's 29-instruction figure** is from the paywalled publisher abstract, not full text (W1 note) — fine as a minimality datum, not a spec.
5. **v1/v2 opcode split** must be resolved and the ISA frozen+versioned before it crosses (SWI `.qlf` fragility, W3; risk 7).
6. **M2 owner-set ambition:** building the IL (Fork B) is unearned unless declared optimization/multi-target ambition exists — the W3 decision pivot. This is a product decision, not a technical one.
