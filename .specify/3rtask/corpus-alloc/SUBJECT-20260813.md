# Subject — optimal distributed pipeline design for the glpnet three-host fleet (2026-08-13)

## The decision to be designed

Produce an **optimal allocation and execution design** by which the three-host fleet
(**ARIELLAS**, **OLAMNIT**, **GAVRIELLA**) drives every not-closed roadmap feature through the
full buildkit pipeline, coordinated by `/bk-scheduler` (CPM/PERT with a derived critical path)
and recorded by `/bk-marathon`, under the engineer's **per-host ONE-AT-A-TIME** ruling:
three lanes run in parallel; within a lane, features are worked strictly one at a time,
end-to-end.

Per-feature chain, in strict order, for every allocated feature:

```
[safe restart] specify → clarify → plan → tasks → analyze
[safe restart] implement
[safe restart] codexreview → ship → close → roadmap sync round → status/sitrep
```

## Questions the design must answer

1. **Allocation.** Which features go to which host, in what within-lane order, and on what
   stated basis? The portfolio is 25 not-closed rows of which only 23 are allocatable (2 are
   already shipped and need close-out only). Several rows carry no WSJF and no RICE at all —
   the design must say explicitly how it placed those rather than implying a priority order it
   cannot justify.
2. **Critical path.** What is the honest CPM/PERT critical path given that PERT triples exist
   for only 2 of 23 features, both self-declared estimates from a single host? What may be
   published, and what must be refused rather than invented?
3. **Work-package set.** What must the scheduler board be re-seeded with, given that its three
   existing work packages all resolve to features that are already closed?
4. **Serialisation points.** Which items genuinely cannot run in parallel — hard `blocked-by`
   edges, shared implementation surfaces, environment-blocked work, engineer-gated work — and
   therefore constrain any lane assignment?
5. **Protocol.** What must the hardened CRDT work protocol contain for the fleet to run three
   lanes safely, and what is its true binding status given that one host has not ACKed?
6. **Degradation.** How does the design behave when a host is silent, when a lease expires,
   when a claimed lane is abandoned, and when a tool reports success without proving it ran?
7. **Risk.** Which known defects will corrupt the design's own execution if not accounted for,
   and what does each one force the design to do differently?

## Evidence partition (pairwise disjoint)

- **Slice A — PORTFOLIO (the WHAT):** feature identity, state, WSJF/RICE, spec path, blocking
  edges, sequencing, duration data.
- **Slice B — HOSTS (the WHO):** per-host declared capability, caps freshness, current load,
  availability, delivery track record, host-specific constraints.
- **Slice C — PROTOCOL (the HOW):** coop CRDT rules, scheduler/marathon/pipeline contracts,
  comms semantics, and defects in the tooling itself.

No builder may consult a slice other than its own; every claim must cite a source inside its
own slice.

## Output required

A design that names, per host: the ordered lane, the work-package set to seed, the honest
schedule (including what is refused), the serialisation constraints it respects, the protocol
amendments it depends on, and its degradation behaviour — each attributed to evidence.
