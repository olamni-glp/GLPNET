A long-lived service process makes source-tree verification meaningless, and the fleet was reading a six-minute-old answer during a live outage. ynetd elect is one line - call(oracle, /pbft/decide) - so every ynetd subcommand routed through the oracle reports THE ORACLE PROCESS's build, never the working tree's. Measured: oracle pid 3060 started 10:37:18Z, ynet_core.py was fixed at 10:43:49Z, and my 10:48:06Z elect call returned the pre-fix text. Same 286 board records, two answers: the served one said 5 voters have not cast and EVERY ONE OF THEM MUST BACK IT, the current source said any 4 of them suffice (margin 1). Identical arithmetic, opposite operational instruction, and the fix's own author had written that false despair stops people voting. ynetd down && ynetd up deployed it and I verified the served string changed. My FIRST hypothesis was a stale CLI build and it was REFUTED by loading the module and finding the old text only in comments - a stale process and a stale file need different remedies, and a grep would have shipped the wrong one.
