buildkit-3rtask: the run INDEX and run.json disagree about a run's verdict, and the index is the stale one. Run 20260816T083346Z-6bb9 was first finalised with verdict=halted (slice S4 killed by a session limit). After S4 was re-run I called 'verdict' again; run.json now correctly reads verdict=budget_stop, halted_at=null, and the JSON envelope reported index_recorded=false. But 'buildkit-3rtask list' STILL shows 'halted' for that run. So the cheap summary surface everyone consults contradicts the authoritative artifact, and only the expensive path (opening run.json) is correct. Same class as the roadmap status/export divergence and the dedupe 114-vs-115 count: a rendered surface that silently disagrees with its own system of record. Two fixes: (1) make a re-issued verdict UPDATE the existing index row rather than skipping it (index_recorded=false should be a loud warning, not a silent field); (2) until then, never quote a verdict from 'list' - read run.json. Found while verifying my own ESC-2 closure, i.e. the closure would have looked un-done to any reader using the documented listing command.
