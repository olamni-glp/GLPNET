A REFUSAL MESSAGE UNDERCOUNTED WHAT WAS MISSING, and the undercount would have sent the next lane down a two-line path for a job that needs a feature. The send verb's exit-8 text said the signing identity 'is the remaining step' before the wire could send. MEASURED against QuicOutbound's actual constructor - (NodeIdentity self, NodeId peerNode, PeerIdentity peer, IPEndPoint remote) - the identity was ONE of FOUR, and the genuinely missing one is peerNode: NOTHING in this fleet resolves a lane name to a node id, which is the unbuilt Resolve half of ynet-minted-lane-identity-resolve-address-independent. The message now names that gap and refuses rather than inventing an id, because a wrong peer node id authenticates against the wrong key and fails looking exactly like a network fault. GENERAL RULE: a refusal that names ONE cause when there are FOUR is not merely unhelpful, it is actively misleading about the size of the work - check the callee's full signature before writing what is 'remaining'.
