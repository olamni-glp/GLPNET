PROVEN BOTH WAYS 2026-09-08T06:25Z on OLAMNIT. The alerts hook prints 'Drain one with: ynet_client drain <alertId>' followed by the MessageId (1d7d7ded...8c0c#1), but drain takes the AlertId (20260908T060226561725-...-31b3f03b) which only 'pending' shows. Draining the printed id returns rc=0 with 'was not pending (already drained, or never raised)' and the alert SURVIVES at presented=1x; draining the AlertId returns rc=0 with 'drained' and pending then reports nothing. BOTH PATHS EXIT 0, so neither a human nor a script can distinguish drained from silently-did-nothing. The failure text is worse than a generic one because it REASSURES: 'already drained, or never raised' reads as 'there was nothing to do', which is the one reading that makes an operator stop looking, while the true state is 'your alert is still there and you have been told it is handled'. FIX, two lines, neither of them id plumbing: drain must exit NON-ZERO when it drained nothing, and the hook must print the id drain accepts (or drain must accept both) - printing one and accepting the other is the defect. This is the FOURTH field-identity divergence measured in this fleet in one day (Origin name-vs-nodeid, signal-vs-Summary, missing recipient, MessageId-vs-AlertId) and all four share one shape: two things that look interchangeable, are not, and disagree SILENTLY. All four were found by RUNNING the thing; reading each looks fine because every field is present, well-formed and non-empty.
