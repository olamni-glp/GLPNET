P0 ROOT-CAUSED 2026-09-08T06:20Z on OLAMNIT. The M6 alert record carries AlertId, MessageId, Origin, Summary, RaisedUtc, Presentations - and NO RECIPIENT. Origin is the SENDER's node id. Combined with two other measured facts this becomes silent cross-lane alert theft: (b) scripts/ynet_alerts_hook.py _resolve_alert_dir returns %LOCALAPPDATA%/glpnet/ynet-client/alerts whenever that directory exists, reaching the per-lane .specify/ynet/<lane>/alerts path ONLY when it does not - so once the C# client has ever run on a host user the --lane argument is DEAD and changes nothing but the printed label; five per-lane legacy dirs exist here and are all shadowed, so lane scoping was the original design and the spool migration silently switched it off. (c) .claude/settings.json:29 is CHECKED IN and hardcodes --lane gavriella-glpnet, so every lane cloning this repo on any host prints that name. (a) makes filtering impossible, (b) makes the pool shared, (c) makes the label wrong. Presentations increments and drain is idempotent and DESTRUCTIVE, so the first agent to see an alert can drain it and the lane it was for never learns it existed - there is no unread-by-someone-else state because there is no someone-else in the record. It will present as a network fault: the lane investigates the wire, the carrier and the peer mailbox, never a sibling session on its own host. FOUND ONLY because the misdelivered alert was my own WIRE_ROUNDTRIP_PROBE string and I recognised it; a real peer alert would have been invisible. FIX: the RECEIVER stamps the recipient at spool time - it knows, it was started with --self and refuses to run without it. Do NOT relocate the spool first: that orphans every alert in it and breaks a sibling lane mid-era. Per-lane YNET_CLIENT_SPOOL is honoured first and stops the cross-lane pool today, but does not fix the missing field.
