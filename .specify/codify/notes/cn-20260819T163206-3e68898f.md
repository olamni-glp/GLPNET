Measuring which artifacts on unmerged branches are missing from origin/develop, I used 'git cat-file -e origin/develop:.claude/skills/bk-opskit/SKILL.md' and then 'git rev-parse --verify origin/develop:.claude/...'. BOTH reported the file ABSENT. 'git ls-tree origin/develop -- .claude/skills/bk-opskit/SKILL.md' returned a real blob (68ce1b9a) - the file is PRESENT. The <rev>:<path> revision syntax mis-resolves paths beginning with a dot, and it fails SILENTLY as a normal not-found rather than as a syntax error. I was one step from telling the engineer that six bk-opskit skill docs were unshipped work needing recovery, when they were already in develop. Rule: for existence-in-a-tree questions use 'git ls-tree <rev> -- <path>' and check for a blob line; never use <rev>:<path> with cat-file/rev-parse on a path that starts with a dot. Same family as the standing rule 'verify by CONTENT, never by exit code' - here the exit code lied in the safe-looking direction.
