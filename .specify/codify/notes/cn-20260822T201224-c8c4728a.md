ROOTCAUSE of "no steady feature stream from the scheduler" - measured 2026-08-22 on the glpnet board (I:/coop/glpnet/sched, engine 2026.8.18.2) by reading the engine source and the live board. It is NOT one defect. It is FOUR independent breaks in series, which is why every single-point fix attempted so far produced no stream.

BREAK 0 - REFUTED, and this matters: supply is NOT the bottleneck. `ingest --from-catalog --dry-run` reports eligible=17 promoted / already_minted=17 / would mint=0 / needs_effort=0 / promoted_not_minted=0. Every promoted roadmap feature is already on the board. The fleet has repeatedly framed this as a supply outage and spent effort on refill; that framing is wrong on this board.

BREAK 1 - minted packets land in `backlog` and NOTHING IN THE ENGINE CAN EVER MOVE THEM TO `ready`. readiness.py says it outright: "Nothing in this engine computes readiness. `ready` occurs seven times in the scheduler package and all seven are READS; derive_board initialises state to the literal backlog and the only assignment that moves it is an explicit transition op." The only ready-WRITERS are operator verbs: confirm, allocate --ready, ingest --ready, transition. R-B1 states no cycle path writes it. This is CONTRACT, not bug - the whole toolchain is advisory and the allocator only ever emits status=proposed. So the board is architecturally incapable of self-feeding, deliberately, while the fleet operating model assumed it would self-feed. That gap between the contract and the assumption is the primary root cause.

BREAK 2 - the readiness recommender is vacuous on this board. views/readiness/2026-08-22T17Z.json: candidates=23, edge_coverage={candidates_constrained: 0, candidates_unconstrained: 23, edges_confirmed: 0}. Zero dependency edges exist, so "all prerequisites satisfied" is vacuously true for all 23. readiness.py warns about exactly this: promoting them all "would be correct arithmetic on the wrong predicate". So the one surface that could unblock BREAK 1 cannot be trusted to, until edges exist.

BREAK 3 - even once ready, the effort estimates make them unplaceable. Candidates carry e_t_s 288000s (80h) and 144000s (40h) against a per-engineer-per-day capacity of 86400s. The allocator still EMITS the proposal, then `load` declines to bill it, and the lane reads idle at remaining=86400. An unplaceable proposal is emitted SILENTLY instead of being reported unplaceable.

BREAK 4 - the allocate VIEW contradicts the durable allocate OPS. Durable: ariellas:000035 glptutorial->ariellas, ariellas:000036 occurs-checked->ariellas, ariellas:000038 coordination-feature-stream->olamnit. View 2026-08-22T17Z proposes glptutorial->olamnit, occurs-checked->olamnit, verification-receipts->ariellas, and even proposes a WP transitioned to done minutes earlier. The view is not a function of the durable allocations; it re-proposes from scratch each cycle and contradicts the system of record on every row. This is why all three lanes carry dispatched-but-never-converted cards.

CONSEQUENCE: fixing any ONE of these yields nothing measurable, because they are in series. That is precisely why three hosts each independently investigated, each found a real defect (D1/D2/D8/D10), each fixed or reported it, and the stream still did not start.

INTEGRATE INTO TOOLING: the durable remedy is a named, per-repo STANDING READINESS PROCEDURE that a lane runs every cycle - readiness -> confirm - plus (a) making an unplaceable proposal a loud refusal rather than a silent emission, (b) deriving the allocate view FROM the durable allocate ops rather than recomputing it, and (c) requiring edge coverage before readiness recommendations may be mass-confirmed. Items (a) and (b) are already scoped into glpnet feature 082-feature-stream-superset US1/US2/US3.
