## Rationale and research provenance (per non-trivial construct)

### rf-dart-completer-to-csharp-taskcompletionsource — `boot()` Ready-counting completion

- Deep analysis. The Dart `boot()` method uses `final readyCompleter = Completer<void>();` and `await readyCompleter.future;` to gate the boot completion until all spawned agents have reported Ready. The Completer is the externally-completable Future source; the listener completes it once `readyCount == expectedCount`.
- Authoritative Dart: official Dart API doc for `Completer<T>` at https://api.dart.dev/stable/dart-async/Completer-class.html — "A way to produce Future objects and to complete them later with a value or error. ... Most of the time, the simplest way to create a future is to just use one of the Future constructors to capture the result of a single asynchronous computation. Completer should be used when there is no other way to create a Future."
- Authoritative .NET: official Microsoft Learn API doc for `TaskCompletionSource` (parameterless form, returning `Task`) at https://learn.microsoft.com/dotnet/api/system.threading.tasks.taskcompletionsource — "Represents the producer side of a Task unbound to a delegate, providing access to the consumer side through the Task property." The canonical externally-completable Task source — `SetResult()` / `SetException(e)` resolves the awaited Task. The `!readyCompleter.isCompleted` check before complete maps to `!readyTcs.Task.IsCompleted` before SetResult; both throw on double-complete.
- Decision. `Completer<void>` → `TaskCompletionSource`; `readyCompleter.future` → `readyTcs.Task`; `readyCompleter.complete()` → `readyTcs.SetResult()`. Authoritative; no escalation.

### rf-dart-sealed-class-hierarchy-to-csharp-abstract-base-with-subclasses — `IsolateMessage` hierarchy

- Deep analysis. The Dart `sealed class IsolateMessage {}` with four concrete subclasses (`Ready`, `Start`, `NetworkMsg`, `UIEvent`) is a Dart 3.0+ closed-hierarchy declaration. Sealed classes in Dart enforce that all subclasses are in the same library, enabling exhaustive switch.
- Authoritative Dart: official Dart language reference at https://dart.dev/language/class-modifiers#sealed — "A sealed class is implicitly abstract. ... Marking a class sealed allows the language to ensure that the compiler can definitively know all of its subtypes ... and so exhaustively switch on the subtypes."
- Authoritative .NET: Microsoft Learn 'Pattern matching overview' at https://learn.microsoft.com/dotnet/csharp/fundamentals/functional/pattern-matching documents the `is X x` and `switch`-expression-with-exhaustiveness pattern. C# 11+ documentation on 'Generic math support' touches on sealed-style hierarchies. CRITICAL: Dart `sealed` means "closed hierarchy"; C# `sealed` means "cannot be inherited" — OPPOSITE semantics. The faithful translation is `abstract` base + open subclasses + optional `switch`-expression exhaustiveness.
- Decision. `public abstract class IsolateMessage` + four concrete subclasses inheriting it; the dispatching `if (msg is Ready ready) { ... }` chain preserves the Dart shape; OR a `switch (msg) { Ready ready => ..., NetworkMsg netMsg => ..., _ => ... }` expression for exhaustiveness analysis. Both forms are documented; codegen prefers the if-chain for byte-for-byte Dart-shape fidelity. Authoritative; no escalation.

### rf-dart-const-class-with-default-named-params-to-csharp-init-properties — `TraceConfig`

- Authoritative .NET: Microsoft Learn 'init keyword' at https://learn.microsoft.com/dotnet/csharp/language-reference/keywords/init — "An init only property (or indexer) is set just like any other property or indexer, but only during object initialization." Init-only properties provide the C# counterpart of "settable at construction, immutable thereafter".
- Decision. `init`-only auto-properties with default values; static readonly singleton for `Off`; object-initialiser syntax at construction sites. Authoritative; no escalation.

### rf-dart-named-required-partly-defaulted-to-csharp-positional-with-defaults — `AgentConfig`

C# does not have a "required named" syntax; the documented counterpart is positional parameters with the required ones having no default and the optional ones having defaults.

If the parameter is the only required parameter, you can call the method either by using a positional argument or by using a named argument."
