## Rationale and research provenance

### rf-dart-isolate-singlethread-to-csharp-actor-or-pinned-thread — reused (per-agent single-owning-thread invariant)

- Reused verbatim from `lib/multiagent/global_writers_table.dart.md` (the canonical recording of this idiom). `GlobalSendRegistry` is the second per-agent isolate-local state holder in `lib/multiagent/` (after `W_p` / `GlobalWritersTable`) — created once per agent inside that agent's Dart isolate, accessed only by code running on the agent's owning event loop, never shared across isolates. The Dart source reflects this directly: no `Mutex`, no `Lock`, no `Future`-returning mutators, no `Completer`, no `synchronized` package.
- Authoritative Dart. Same official Dart concurrency overview (https://dart.dev/language/concurrency): isolates are isolated, single-threaded by language design, no shared mutable state.
- Authoritative .NET. Same documented options for preserving isolate ownership: pinned `Thread` per agent, single-threaded `TaskScheduler` (`ConcurrentExclusiveSchedulerPair.ExclusiveScheduler`), actor-style mailbox over `Channel<T>`, or synchronisation-context binding (https://learn.microsoft.com/dotnet/core/extensions/channels, https://learn.microsoft.com/dotnet/api/system.threading.tasks.concurrentexclusiveschedulerpair). The choice is deferred to the `isolate_manager.dart` port.
- Why `ConcurrentDictionary` would be wrong here is the SAME reasoning as for `GlobalWritersTable`: `OnWriterBound` is a compound `remove` -> `globalize(...)` -> `Select.ToList()` sequence that no per-collection container can make atomic; the atomicity guarantee MUST come from the isolate-ownership invariant. Per-collection concurrent containers would advertise a thread-safety property the surrounding code does not honour. Authoritative; no escalation.
