## Rationale and research provenance

### rf-dart-isolate-singlethread-to-csharp-actor-or-pinned-thread -- the load-bearing concurrency decision

- Deep analysis. `GlobalWritersTable` is `W_p`, the per-agent global-writers table from madGLP-spec Section 3. The surrounding multiagent runtime (`lib/multiagent/isolate_manager.dart`) spawns one `dart:isolate` per agent via `Isolate.spawn(_agentIsolateEntry, agentConfig)`. Each isolate has its own heap and event loop; cross-isolate communication is `SendPort`/`ReceivePort` message passing only. `MadContext` owns one `GlobalWritersTable wp` and lives entirely inside one isolate. No code path in `lib/multiagent/` shares a `GlobalWritersTable` instance across isolates. Therefore every read and write of `_globalizeEntries`, `_localizeEntries`, `_nextIndex`, and `_serializerWriterAddr` happens on a single isolate thread, serialised by the isolate's event loop. The Dart source code reflects this directly: no `Mutex`, no `Lock`, no `Future`-returning mutators, no `Completer`, no `synchronized` package.

- Authoritative Dart. The official Dart concurrency overview (https://dart.dev/language/concurrency) describes isolates verbatim: 'In Dart, all code runs inside of isolates ... isolates are isolated from each other and have their own memory and a single thread of control. There is no shared mutable state between isolates.' This makes the single-threaded-per-isolate property a language guarantee, not a coding convention. Authoritative for the Dart side.

- Authoritative .NET. .NET has no isolate primitive. The closest correctness-preserving patterns are: (a) a pinned dedicated `System.Threading.Thread` per agent with a single-threaded message loop; (b) a single-threaded `TaskScheduler` (`ConcurrentExclusiveSchedulerPair.ExclusiveScheduler`); (c) an actor-style mailbox (e.g. a `System.Threading.Channels.Channel<TWork>` consumed by exactly one reader Task); (d) a synchronisation-context-bound execution. .NET's `System.Threading.Channels` documentation (https://learn.microsoft.com/dotnet/core/extensions/channels) confirms `Channel<T>` semantics: 'A single producer/single consumer scenario can use a bounded or unbounded channel ... only one consumer task reads from the channel at a time.' .NET's `ConcurrentExclusiveSchedulerPair` documentation (https://learn.microsoft.com/dotnet/api/system.threading.tasks.concurrentexclusiveschedulerpair) confirms its exclusive scheduler runs tasks one at a time. Any of these is sufficient to preserve the isolate-ownership invariant; choosing among them is the responsibility of the .NET port of `isolate_manager.dart`, not this file.

- Why `ConcurrentDictionary` / `Interlocked` would be wrong here. `System.Collections.Concurrent.ConcurrentDictionary<TKey,TValue>` documentation (https://learn.microsoft.com/dotnet/api/system.collections.concurrent.concurrentdictionary-2) states: 'All public and protected members ... are thread-safe and may be used concurrently from multiple threads. However, members accessed through one of the interfaces ... including extension methods, are not guaranteed to be thread safe.' Crucially, per-member thread-safety does not extend to multi-step compound operations. `GlobalWritersTable.addLocalizeEntry` is a textbook compound operation (`findByRemote != null` THEN `add`); even on a `ConcurrentBag<LocalizeEntry>` the race between the scan and the add is unprotected. The lock-free path is therefore not only unnecessary (no real contention) but actively misleading -- it advertises a safety property the surrounding logic does not enforce. The correct port preserves isolate ownership and uses the same plain `Dictionary`/`List`/`int` that the Dart source uses, for the same reason the Dart source uses them.

- Decision. (i) `Map<int, GlobalizeEntry>` -> `Dictionary<int, GlobalizeEntry>` (NOT `ConcurrentDictionary`). (ii) `List<LocalizeEntry>` -> `List<LocalizeEntry>` (NOT `ConcurrentBag`). (iii) `int _nextIndex` -> `int _nextIndex` (NOT `Interlocked.Increment`). (iv) `int? _serializerWriterAddr` -> `int? _serializerWriterAddr`. (v) No `lock`, no `SemaphoreSlim`, no async signature on any method. (vi) The spec records a precondition that the .NET port of `lib/multiagent/isolate_manager.dart` MUST provide a single-owning-thread / single-threaded-scheduler / actor-mailbox boundary equivalent to the Dart isolate. Fully decided from authoritative documentation on both sides; no escalation needed.

### rf-dart-final-named-required-ctor-to-csharp-getonly-properties -- entry classes

- Deep analysis. `GlobalizeEntry` and `LocalizeEntry` are immutable holders: two and three `final` fields respectively, single named-only constructor with `required` on every parameter, an `@override String toString()`, no `==`/`hashCode` override (so Dart uses identity equality). They are stored in collections owned by `GlobalWritersTable` and looked up by index (dict) or by predicate (list); the surrounding code never compares them by value.

- Authoritative .NET. WebFetch https://learn.microsoft.com/dotnet/csharp/programming-guide/classes-and-structs/properties (and the autoproperty subsection) -- query: 'How do get-only auto-properties model an immutable reference-type holder initialised by a constructor?' Conclusion: `public string Name { get; }` with constructor-assigned value is the canonical .NET shape for an immutable holder; setting in the constructor is permitted, no setter is exposed. The reference-types page (https://learn.microsoft.com/dotnet/csharp/language-reference/builtin-types/reference-types) confirms `class` instances are reference objects with identity by default (matching Dart). ### rf-dart-map-remove-to-csharp-dictionary-remove -- idempotent map removal

- Deep analysis. Dart `Map.remove(key)` is idempotent on absent keys (returns `null`, no exception); the surrounding code relies on this (the doc-comment explicitly says 'Safe to call on non-existent index (idempotent)').

- Authoritative .NET. https://learn.microsoft.com/dotnet/api/system.collections.generic.dictionary-2.remove -- 'Returns true if the element is successfully found and removed; otherwise, false. This method returns false if key is not found in the `Dictionary<TKey,TValue>`.' No exception on miss. Direct semantic match. The boolean return is discarded (Dart `Map.remove` returns the removed value, also discarded by the source). Authoritative; no escalation.

### rf-dart-list-removewhere-to-csharp-list-removeall -- predicate-based removal

- Deep analysis. `removeLocalizeEntry` uses `List.removeWhere((e) => ...)` which removes every match. .NET `List<T>.RemoveAll(Predicate<T>)` (https://learn.microsoft.com/dotnet/api/system.collections.generic.list-1.removeall) is the documented counterpart: 'Removes all the elements that match the conditions defined by the specified predicate. Returns the number of elements removed.' The defensive multi-match shape is preserved -- silently narrowing to a 'remove first match' translation would change the contract. Authoritative; no escalation.
