## Rationale and research provenance

### rf-dart-isolate-singlethread-to-csharp-actor-or-pinned-thread — REUSED (per-agent single-owning-thread invariant)

- Reused verbatim from `lib/multiagent/global_writers_table.dart.md` (the canonical recording of this idiom; also reused in `global_send.dart.md` and `message_queue.dart.md`). `MadContext` is the PER-AGENT OWNER — created once per agent inside that agent's Dart isolate (`lib/multiagent/isolate_manager.dart` spawns one `Isolate.spawn(_agentIsolateEntry, agentConfig)` per agent), accessed only from the agent's owning event loop, never shared across isolates. ALL state reachable through `MadContext` (`Wp`, `Mp`, `GlobalSendRegistry`, `_serializer`, the runtime heap and goal queue, both callback fields) is per-instance and isolate-local.
- Authoritative Dart and .NET citations are recorded in `global_writers_table.dart.md` — the same isolate-ownership invariant applies uniformly across the multiagent files. The .NET port MUST preserve single-owning-thread access via the `isolate_manager.dart` port (a pinned `Thread`, a single-threaded `TaskScheduler`, an actor mailbox via `Channel<T>`, or a synchronisation-context binding — choice deferred to the isolate-manager port).
- Why `lock`/`SemaphoreSlim`/`ConcurrentDictionary`/`ConcurrentBag`/`Interlocked` inside `MadContext` methods would be WRONG: identical reasoning as for `GlobalWritersTable` / `GlobalSendRegistry` / `MessageQueue` — compound check-then-act sequences (`HandleMadAssignment` dispatch + `_Handle*Assignment` + reactivate; `FlushMessages` snapshot-then-drain) are not protected by per-collection or per-method locking; the atomicity is end-to-end at the isolate-ownership level. Authoritative; no escalation.

### rf-dart-typedef-function-to-csharp-delegate — `MessageDeliveryCallback` named delegate

- Deep analysis. The Dart source declares `typedef MessageDeliveryCallback = void Function(String destination, OutboundMessage message);` at the top level — a Dart 2.13+ generalised typedef giving a name to a two-arg void function-type. It is used downstream as the type of the nullable callback field on `MadContext`, set by the coordinator and invoked from `flushMessages`.
- Authoritative .NET. Microsoft Learn 'Delegates' (https://learn.microsoft.com/dotnet/csharp/programming-guide/delegates/) documents the `public delegate void X(A, B);` declaration as the canonical .NET counterpart of a named function-type alias — a delegate is a NOMINAL REFERENCE TYPE (assigned by value compatibility but typed by name). `Action<A, B>` (Microsoft Learn 'Action<T1,T2> Delegate' — https://learn.microsoft.com/dotnet/api/system.action-2) is the GENERIC two-arg void delegate; it is the right structural counterpart but DROPS the named-typedef domain intent.
- Decision. The named delegate `MessageDeliveryCallback` is the FAITHFUL counterpart of the Dart named typedef — both languages express the same intent (named two-arg void callable type with domain meaning). The trace-sink field uses `Action<string>?` (anonymous Dart function-type → generic .NET delegate) because the Dart source itself did NOT name that callable — preserving the asymmetry. Authoritative; no escalation.

### rf-dart-named-required-ctor-with-initialiser-list-to-csharp-positional-ctor — `MadContext` constructor

- Deep analysis. The Dart constructor `MadContext({required this.agentId, required this.runtime}) : wp = GlobalWritersTable(agentId), mp = MessageQueue(), globalSendRegistry = GlobalSendRegistry(agentId) { _serializer = PayloadSerializer(agentId); }` mixes named-required arguments with an INITIALISER LIST that derives three fields (`wp`, `mp`, `globalSendRegistry`) from the `agentId` parameter and a constructor BODY that assigns the `late final _serializer` (the initialiser list cannot reference `late` fields). C# has no constructor-initialiser-list syntax at the field level (only `: this(...)` / `: base(...)` for ctor chaining), so the documented .NET counterpart is to collapse all field initialisation into the constructor body.
- Authoritative .NET. Microsoft Learn 'Constructors (C# Programming Guide)' (https://learn.microsoft.com/dotnet/csharp/programming-guide/classes-and-structs/constructors) documents constructor-body field initialisation as the canonical form. `readonly` fields can be initialised either inline at declaration or in any constructor that runs before the constructor exits.
- Decision. Single non-optional-parameter constructor `public MadContext(string agentId, GlpRuntime runtime) { AgentId = agentId; Runtime = runtime; Wp = new GlobalWritersTable(agentId); Mp = new MessageQueue(); GlobalSendRegistry = new GlobalSendRegistry(agentId); _serializer = new PayloadSerializer(agentId); }` — all six fields initialised in the body. `late final` Dart maps to `readonly` C# (eagerly assigned). Authoritative; no escalation.

### rf-dart-nullable-callback-invocation-to-csharp-null-conditional-invoke — `_trace` and `flushMessages` callback invocation

- Deep analysis. The Dart source uses the idiom `if (callback != null) callback!(args)` (explicit null-check + bang-assert) to invoke a nullable callback. This pattern appears in `_trace` and (inverted as an upfront early-return) in `flushMessages`.
- Authoritative .NET. Microsoft Learn 'Null-conditional operators ?. and ?[]' (https://learn.microsoft.com/dotnet/csharp/language-reference/operators/member-access-operators#null-conditional-operators--and-) documents `Delegate?.Invoke(args)` as the canonical safe-invocation idiom for nullable delegates — atomically null-checks and invokes. ## Notes

- **Per-agent single-owning-thread invariant.** `MadContext` is the per-agent OWNER and the per-agent entry point — all state reachable through it (`Wp`, `Mp`, `GlobalSendRegistry`, `_serializer`, the runtime heap and goal queue, the two callback fields) is per-instance and isolate-local. The invariant recorded once on `GlobalWritersTable.dart.md` is reused HERE and across `GlobalSendRegistry`, `MessageQueue`, and `PayloadSerializer`. No `lock`, no `SemaphoreSlim`, no `ConcurrentDictionary`, no `Interlocked` — the atomicity for compound check-then-act sequences (`HandleMadAssignment` → `_Handle*Assignment`; `FlushMessages` snapshot-then-drain; `_fireGlobalSendGoalIfExists` lookup-then-spawn) is end-to-end at the isolate-ownership level.

- **Spec Section 5.1 writer-passive / reader-active asymmetry.** The `Send` method has a LOAD-BEARING comment explaining that globalize-writer entries do NOT get an `onBind` callback (because the spawning happens at the OTHER agent, by `localize`). Codegen MUST emit this comment verbatim — it is the only documentation in the file establishing the writer-vs-reader asymmetry of madGLP's bind-cascade.

- **Spec Section 8.3 three-case dispatch (`HandleMadAssignment`).** The dispatcher's case order (serializer-first, then writer-with-Index>0, then reader-implicit-else) is LOAD-BEARING. Codegen MUST preserve the order — case (a) `IsWriter && Index == 0` MUST test FIRST because case (b) `IsWriter` alone would otherwise swallow case (a).

- **Push model in `ProcessSuspension`.** The method is INTENTIONALLY a no-op-modulo-logging. The trailing `// No explicit request messages needed in madGLP push model` comment is load-bearing documentation explaining WHY no message-queue add appears here. Codegen MUST preserve the no-op-modulo-logging body.

- **Permanent vs transient W_p entries.** The serializer entry at index 0 is NEVER removed (`_HandleSerializerAssignment` calls `UpdateSerializerWriter`, never `RemoveGlobalizeEntry`). Globalize entries at index > 0 are TRANSIENT (`_HandleWriterAssignment` calls `RemoveGlobalizeEntry(Index)`). Localize entries are TRANSIENT (`_HandleReaderAssignment` calls `RemoveLocalizeEntry(Agent, Index)`). The index-0 guard inherited from `global_writers_table.dart.md`'s `RemoveGlobalizeEntry` is bypassed structurally by the dispatch order — `_HandleWriterAssignment` is reached only when Index > 0.

- **Method-tear-off / method-group conversion is the canonical idiom** in this file for passing callbacks: `Runtime.Heap.IsReader` (no parentheses) → `Func<int, bool>`; `_LookupVariableForSerialization` → `Func<int, (string, int, bool)>`. Identical receiver-capture behaviour in both languages.

- **Per-iteration closure capture (explicit local).** Every `foreach` that installs a heap callback uses an explicit per-iteration local (`capturedAddr`, `capturedReaderAddr`) to document intent — C# 5+ already captures per-iteration, but the explicit form removes ambiguity and makes the capture visible at the language level.

- **Snapshot-before-mutating-iterate in `FlushMessages`.** The `Mp.Destinations.ToList()` snapshot is LOAD-BEARING — `Mp.Poll(dest)` mutates `Mp.Destinations`. Codegen MUST preserve the snapshot — iterating the live destinations would throw `InvalidOperationException: Collection was modified`.

- **Inlined four-step localization sequence.** The pattern `ExtractGlobalNames → Localize → RegisterGlobalSendSpawns → LocalizeTermWithResult` is repeated INLINE across `_HandleSerializerAssignment`, `_HandleWriterAssignment`, `_HandleReaderAssignment`, and (split across two phases) `HandleMadAssignmentWithGlobalNames`. The C# port preserves the inlined repetition — refactoring would risk shared-state via captured locals and would obscure per-call-site downstream operations.

- **List-cell heap representation, NOT Dart Stream.** The network input stream is represented in the heap via `StructTerm('.', [head, tail])` list cells (with the functor `\".\"`), NOT via Dart `Stream<T>`. The C# port preserves this — codegen MUST NOT introduce `IAsyncEnumerable<Term>` or `IObservable<Term>` for the stream-extension semantics in `_HandleSerializerAssignment`. The list-cell construction `new StructTerm(\".\", new List<Term> { content, new VarRef(freshReader) })` is the faithful counterpart.

- **Named delegate `MessageDeliveryCallback` preserved.** The Dart `typedef MessageDeliveryCallback = ...` becomes a C# `public delegate void MessageDeliveryCallback(string destination, OutboundMessage message);` — NOT replaced by `Action<string, OutboundMessage>`. Preserving the named delegate preserves the domain intent the Dart source documented.

- **Async/Stream/Future/Completer/Mixin/Sealed/Extension nuances are ABSENT** from this file across the board — correctly not asserted (per the spec quality bar: address the nuances that exist, do not invent translations for shapes the source doesn't contain). The whole file is synchronous; the C# port MUST stay synchronous (introducing async would force every consumer — the GLP runtime, isolate manager, message queue — into await and would break the synchronous send-then-flush and bind-then-dispatch idioms).

- **Zero escalations.** Every non-trivial construct is grounded in official Dart and/or .NET documentation, or in a REUSED idiom from a sibling convspec in `lib/multiagent/` (`global_writers_table.dart.md`, `global_send.dart.md`, `message_queue.dart.md`, `mad_helpers.dart.md`, `payload_serializer.dart.md`) or `lib/multiagent/repl_play_runner.dart.md` (for the nullable-callback-field pattern). No `kind: undecidable` here.
