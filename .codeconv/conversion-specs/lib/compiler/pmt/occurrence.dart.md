### rf-dart-is-type-test-chain-to-csharp-pattern-switch (NEW)

- Deep analysis: two methods (`_classifyGoal`, `_collectVariables`) use
  the `is`-test-then-narrow pattern as a visitor over a Goal hierarchy
  (RemoteGoal / SpawnGoal / other Goal) and over a Term hierarchy
  (VarTerm / StructTerm / ListTerm / other Term). Each `is` test
  narrows the static type of the tested expression inside the branch
  (Dart flow analysis). The chain has a meaningful no-op or
  fall-through default — for `_classifyGoal` the default iterates
  `goal.args`, for `_collectVariables` the default is a no-op
  documented by a `///`-comment.
- Authoritative .NET (WebFetch
  https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/
  operators/patterns): Microsoft Learn, "Patterns" — "A type pattern
  also allows declaration of a variable of the type being tested. …
  `if (expr is Type variable) { /* use variable */ }`." Decisive on
  the C# rendering: `is T name` introduces a typed local in the same
  step. Microsoft Learn additionally documents the `is` expression
  without a variable for type-test-only branches: "the result of the
  `is` operator is `true` when the expression result is non-null and
  any of the following conditions are met: …".
- Authoritative Dart (WebFetch https://dart.dev/language/operators):
  Dart `is` and `as` — "Use the `is` and `is!` operators to check the
  type of an object at runtime. … The Dart analyzer can recognize
  type-promoting `is` checks and use the type information in the body."
  Decisive: Dart `is` narrows the static type inside the branch, same
  as C# `is`.
- Authoritative both sides; recorded as a NEW finding. The `switch

### rf-dart-nullable-field-bang-after-null-check-to-csharp-flow-analysis (NEW)

- Deep analysis: `classifyClause` performs the Dart idiom `if (clause
  .body != null) { for (final goal in clause.body!) ... }` — the bang
  `!` force-unwraps inside the branch even though the surrounding
  null-check has already established non-null-ness. Dart flow analysis
  recognises type-promoting `!= null` checks for LOCAL variables but
  NOT for FIELD accesses (because another thread or another method
  could mutate the field between the check and the use) — hence the
  required bang on `clause.body!`. C# nullable-flow analysis is more
  liberal here in practice for read-only-looking field accesses but
  also issues no warning when the dereference immediately follows the
  null check in a single uninterrupted branch.
- Authoritative .NET (WebFetch
  https://learn.microsoft.com/en-us/dotnet/csharp/nullable-references):
  Microsoft Learn, "Nullable reference types" — "The compiler uses
  static flow analysis to determine the null-state of any reference.
  … If you check `if (variable != null)`, the compiler treats the
  variable as not null inside the if branch." Decisive: C# port can
  drop the bang because flow analysis narrows the nullable reference
  inside the `!= null` branch.
- Authoritative Dart (WebFetch
  https://dart.dev/null-safety/understanding-null-safety#type-promotion-
  on-fields): Dart spec — "Type promotion doesn't apply to fields,
  even for `final` fields. … the analyzer can't tell that the field
  won't change between when it is checked and when it is used." This
  is precisely WHY the Dart source uses `clause.body!` — to satisfy
  the analyzer despite the surrounding null check.
- Authoritative both sides; recorded as a NEW finding. The conversion
  IMPROVES the surface (C# can drop the bang) while preserving exact
  semantics — same throw-on-null behaviour (here: no throw because the
  null check has already excluded that branch). The conversion is
  decisive and unambiguous: prefer flow-narrowing over a `Body!`
  unwrap in C#.

- Authoritative Dart (WebFetch https://dart.dev/language/records):
