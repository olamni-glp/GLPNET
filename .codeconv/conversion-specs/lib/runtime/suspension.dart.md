## Rationale and research provenance

### rf-dart-shared-mutable-record-by-reference-to-csharp-class -- the load-bearing identity-vs-value decision

- Deep analysis. The file's leading doc-comment states the design intent explicitly: "One SuspensionRecord shared across multiple lists via wrapper nodes / Activated once, then disarmed to prevent double-activation." This is the canonical FCP shared-suspension-record idiom: when a goal suspends on multiple unbound readers, a single `SuspensionRecord` is allocated and referenced from one `SuspensionListNode` wrapper per reader cell. When ANY writer eventually binds ANY of those readers and activates the goal, `disarm()` mutates `goalId = null` on the shared record; every other `SuspensionListNode` that still points to that record observes `armed = false` on its next traversal and skips re-activation. The whole double-activation prevention is built on reference identity + shared mutable state. The Dart source enforces this by using `class` (Dart class instances are always reference types -- there is no `struct` in Dart), no `==` override, and a mutable `int? goalId` field that is the single point of state. The `SuspensionListNode.record` field is `final` (the reference itself never re-targets), and its three forwarding getters read `record.armed` / `record.goalId` / `record.resumePC` on every call (no caching).

- Authoritative Dart. The Dart language tour (https://dart.dev/language/classes) describes class instances as reference types: "Objects of a class are created using a constructor and stored on the heap; variables hold references to those objects." Combined with the explicit FCP design comment, the shared-by-reference contract is documented at both the language and the file level.

- Authoritative .NET. The C# reference-types page (https://learn.microsoft.com/dotnet/csharp/language-reference/builtin-types/reference-types) is unambiguous: "Variables of reference types store references to their data (objects), while variables of value types directly contain their data. With reference types, two variables can reference the same object; therefore, operations on one variable can affect the object referenced by the other variable." This is precisely the disarm-propagation contract the FCP design relies on. The records page (https://learn.microsoft.com/dotnet/csharp/language-reference/builtin-types/record) states: "Records use value-based equality. Two record instances are equal if they're of the same type and store the same values." Value-based equality is the OPPOSITE of what this file requires -- two distinct suspension records with identical (goalId, resumePC) represent distinct suspended goals (e.g. two callers of the same procedure suspended at the same PC) and MUST NOT compare equal. `record class` is therefore rejected. The structs page (https://learn.microsoft.com/dotnet/csharp/language-reference/builtin-types/struct) states: "Structure types have value semantics. That is, a variable of a structure type contains an instance of the type." `struct` and `record struct` would copy on every field read and on every assignment -- the `SuspensionListNode.Record` field would hold a private copy of the suspension record per wrapper, breaking the shared-state contract catastrophically. Both rejections are documented in the official language reference, not stylistic preferences.

- Auto-property-with-private-setter. The C# properties page (https://learn.microsoft.com/dotnet/csharp/programming-guide/classes-and-structs/properties) documents `{ get; private set; }` as the canonical shape for "publicly readable, modifiable only from within the class." This matches Dart's pattern of a bare mutable field with exactly one in-class writer (`disarm()`). Plain public mutable fields (`public int? GoalId;`) are rejected because they expose external write access that the Dart source intentionally does not.

- Decision. (i) Both `SuspensionRecord` and `SuspensionListNode` -> .NET `class` (reference type), NOT `record class` / `struct` / `record struct`. (ii) `int? goalId` -> `int? GoalId { get; private set; }`. (iii) `final int resumePC` and `final SuspensionRecord record` -> get-only auto-properties (`int ResumePC { get; }`, `SuspensionRecord Record { get; }`). (iv) `SuspensionListNode? next` -> `SuspensionListNode? Next { get; set; }` (mutable; the list chain is re-linked after construction). (v) The three forwarding getters on `SuspensionListNode` are expression-bodied get-only properties that read `Record.*` on every call -- NOT cached fields. (vi) No `==`/`Equals`/`GetHashCode` override -- default reference equality preserved. Fully decided from official Dart and .NET documentation on both sides; no escalation needed.

### rf-dart-library-directive-to-csharp-namespace-elision -- compilation-unit anchor

- Deep analysis. The `library;` directive on line 4 is the unnamed-library form -- it anchors the leading doc-comments to the library compilation unit. Dart's library system (https://dart.dev/language/libraries) describes libraries as compilation units; unnamed libraries (just `library;`) are common when the file is referenced only by path, not by symbolic name.

- Authoritative .NET. .NET has no `library` directive. The compilation unit is the source file plus its namespace declaration(s) (https://learn.microsoft.com/dotnet/csharp/fundamentals/types/namespaces). The doc-comments above the `library;` declaration migrate to a namespace-level comment (Dart `///` doc-comments -> .NET `///` XML doc comments on the namespace block) without semantic loss.

- Decision. Elide the `library;` directive; preserve the doc-comment content as a header comment on the .NET namespace declaration. Authoritative; no escalation.

### Null-interpolation observable-output preservation (cross-cutting)

- Dart string interpolation on a `null` value (e.g. `'$goalId'` where `goalId == null`) renders the literal four-character string `null` (Dart core spec / `Object.toString()` returns `'null'` for null receivers via implicit `.toString()`). .NET string interpolation `$"{GoalId}"` on a null `int?` renders the empty string (the formatter's null handling differs). To preserve the trace-diagnostic output verbatim (the `SuspensionRecord.ToString()` string is consumed by REPL traces and `:trace`/`:debug` output that humans and tests read), the .NET interpolation uses `{GoalId?.ToString() ?? "null"}`. This is a documented Dart-vs-.NET interpolation difference; codegen MUST emit the explicit two-step form, not the naked `{GoalId}` form.

## Notes

- The shared-mutable-record contract is the load-bearing FCP idiom for double-activation prevention. Every translation choice in this file (class-not-record-not-struct, mutable property with private setter, forwarding getters not caching, mutable `Next` not `init`-only) is in service of preserving that contract. Erasing any one of them silently breaks the contract.

- The two classes form one inseparable design unit (record + wrapper). They are speced as two constructs but share the same research finding (`rf-dart-shared-mutable-record-by-reference-to-csharp-class`) because the rationale is symmetric: BOTH must be reference types, BOTH must preserve identity equality, BOTH must avoid value-copy semantics.

- Async/Stream/Future/Completer/Mixin/Sealed/Isolate nuances are ABSENT from this file -- correctly not asserted. The data structures are purely synchronous in-memory state. The surrounding runtime (`lib/runtime/`) is responsible for the concurrency model and for choosing the ownership boundary for suspension lists; this file just defines the node shapes.

- Zero escalations. Every non-trivial construct is grounded in official Dart and/or .NET documentation. The value-vs-reference decision, the property-shape decision, the null-interpolation difference, and the `library;` elision are all authoritatively decidable; no `kind: undecidable` here.
