## Rationale and research provenance (per non-trivial construct)

### rf-dart-typedef-int-to-csharp-global-using-alias — opaque-int typedef mapping

- Deep analysis. `GoalId`, `Pc`, `ReaderId`, `WriterId` are declared as `typedef X = int;` with the doc comment 'opaque ints for now'. They are used as field types, map keys, and value types throughout the runtime. Crucially, the source NEVER converts between two kinds (no `goalId as Pc` reinterpretation) but it ALSO never enforces non-conversion (any `int` can be assigned to any `XId`-typed field — Dart typedefs are transparent aliases, not nominal types). The author has explicitly deferred nominal typing ('for now').
- Authoritative Dart. The Dart language tour at https://dart.dev/language/typedefs documents `typedef X = T;` as a *type alias* — purely a naming convenience, no nominal distinction: 'A type alias — often called a typedef because it's declared with the keyword typedef — is a concise way to refer to a type.' This confirms that a Dart typedef `= int` is structurally identical to `int` at every use site.
- Authoritative .NET. .NET (C#) does not have a per-file `typedef` for primitive types. The closest official feature is C# 10's `global using` alias (https://learn.microsoft.com/dotnet/csharp/language-reference/keywords/using-directive#using-alias) which allows `global using GoalId = int;` at the project or namespace level, producing a name that is transparently equivalent to `int` — exactly the Dart-source semantics. The alternative of introducing a `readonly record struct GoalId(int Value)` would be a NOMINAL wrapper, which the Dart source explicitly avoids ('opaque ints for now'); translating to a nominal wrapper would EXPAND the spec, not preserve it.
- Decision. Use `global using` aliases. If the future runtime decides to enforce nominal typing on identifier kinds, that is an explicit re-scope (escalate at that point, not a silent upgrade here). Authoritative; no escalation.

### rf-dart-enum-plain-to-csharp-enum — plain enum mapping (carry-over)

- Deep analysis. `GoalStatus { active, suspended, failed, succeeded }` is a plain tag-only enum: no constructor, no fields, no methods, no associated values. Used as a discriminator on `GoalState.status` and compared with `==`; ordinal values are never observed.
- Authoritative Dart. https://dart.dev/language/enums defines the plain `enum` form as a closed, fixed set of constants; enhanced enums add members, which this enum does NOT have.
- Authoritative .NET. https://learn.microsoft.com/dotnet/csharp/language-reference/builtin-types/enum defines `enum` as a value type with named constants, default underlying type `int` — the structurally exact target. The naming guideline https://learn.microsoft.com/dotnet/standard/design-guidelines/names-of-classes-structs-and-interfaces#names-of-enumerations prescribes PascalCase enum members.
- Decision. `enum GoalStatus { Active, Suspended, Failed, Succeeded }`. Authoritative both sides; no escalation. (Same idiom recorded for `MessageType` in `lib/multiagent/message_queue.dart.md`; reused here verbatim.)

### rf-dart-value-class-equality-override-to-csharp-readonly-record-struct — GoalRef

- Deep analysis. `GoalRef` is THE outlier in this file — the only class with a `==`/`hashCode` override. The two-field record-like value carrier is created in scheduler hot paths (every goal enqueue/dequeue, every successor edge) and compared for equality (queue contains-checks, scheduler de-duplication). Dart cannot avoid the heap allocation, but the conversion target can.
- Authoritative .NET. The C# language reference at https://learn.microsoft.com/dotnet/csharp/language-reference/builtin-types/record#positional-syntax-for-property-definition documents positional records (incl. `readonly record struct`): 'A record struct can be readonly … . When you declare a readonly record struct, all instance fields and properties must be readonly. … The compiler synthesizes Equals, GetHashCode, ToString, and Deconstruct methods that operate on the value of the record.' The struct-vs-class records doc at https://learn.microsoft.com/dotnet/csharp/fundamentals/types/records states the rule: 'Use a record struct for a small, immutable value type with value equality.' Two `int` fields, immutable, value equality — exactly the source's intent.
- Why not `class` with manual overrides. Faithful but loses .NET's standard `Deconstruct`/`ToString`/`with` machinery and pays per-instance heap allocation that a 2-field value type does not need.
- Why not `record class` (reference-type record). Provides value equality but still allocates per instance; the hot-path observation rejects it.
- Why not bare `struct`. Equivalent semantics with more boilerplate; the record-struct syntax is the documented modern .NET idiom.
- Decision. `public readonly record struct GoalRef(int Id, int Pc);`. Authoritative; no escalation.

### rf-dart-map-to-csharp-dictionary — SigmaHat mutable map

- Deep analysis. `SigmaHat = Map<WriterId, Object?>` is a mutable map; the runtime mutates it in place (`sigmaHat[w] = v` during HEAD; `sigmaHat.clear()` at clause_next/suspend; per the runtime spec).
- Authoritative .NET. https://learn.microsoft.com/dotnet/api/system.collections.generic.dictionary-2 defines `Dictionary<TKey,TValue>` as the canonical mutable hash-map; supports indexer assignment, `Clear`, `TryGetValue`, etc. — direct semantic match for Dart `Map`. The `IReadOnlyDictionary` interface (https://learn.microsoft.com/dotnet/api/system.collections.generic.ireadonlydictionary-2) is REJECTED here (the source mutates), and `ImmutableDictionary` (https://learn.microsoft.com/dotnet/api/system.collections.immutable.immutabledictionary-2) is also REJECTED (every mutation would allocate a new dictionary — silently changing both performance and aliasing semantics).
- Authoritative Dart. https://api.dart.dev/stable/dart-core/Map-class.html documents `Map` as the abstract mutable key-value mapping interface; `<K,V>{}` literal creates a `LinkedHashMap` instance — the .NET counterpart's iteration-order property differs (`Dictionary<K,V>` does NOT guarantee iteration order), but the source does NOT depend on σ̂w iteration order (it only does `[]=`, `[]`, `clear()`, and `containsKey` semantically). Iteration-order independence verified by reading the spec section that motivates σ̂w.
- Decision. `Dictionary<int, object?>` aliased as `SigmaHat`. Authoritative; no escalation.

### rf-dart-top-level-const-to-csharp-static-class-const — top-level integer constant

- Deep analysis. `const int tailRecursionBudgetInit = 26;` is a Dart top-level (library-level) compile-time constant. The literal `26` is load-bearing per the runtime spec.
- Authoritative .NET. https://learn.microsoft.com/dotnet/csharp/language-reference/keywords/const documents `const` as a compile-time constant; top-level statements in C# do NOT permit a `const` declaration outside a type (https://learn.microsoft.com/dotnet/csharp/fundamentals/program-structure/top-level-statements — local consts inside a top-level statement are allowed but are local; library-level constants must live in a type). The documented home is `public static class Constants { public const T Name = …; }`.
- Why not `static readonly`. `static readonly` is a runtime-initialised field, not a compile-time constant; it cannot be used in `[Attribute(value=…)]`, `switch case …:`, or `const` contexts. Dart `const` carries the compile-time-constant intent; `const` preserves it.
- Decision. `public static class MachineStateConstants { public const int TailRecursionBudgetInit = 26; }`. Authoritative; no escalation.

### rf-dart-mutable-state-class-identity-equality-to-csharp-class — GoalState

- Deep analysis. `GoalState` is the canonical per-goal mutable state container — PC advances, status transitions, tail budget decrements, σ̂w mutates and clears. It is stored in scheduler/queue/trail structures by reference; the runtime asks 'is this *the* goal I scheduled?' which is reference identity. NO `==`/`hashCode` override in the Dart source — default identity equality.
- Authoritative .NET. The C# guide on classes vs records (https://learn.microsoft.com/dotnet/csharp/fundamentals/types/records and https://learn.microsoft.com/dotnet/csharp/fundamentals/types/classes) is explicit: use `class` for reference identity + mutable state; use `record class` for value equality on an immutable bundle; use `struct`/`record struct` for value-type semantics + no-allocation small bundles. `GoalState` is mutable AND identity-equal AND held by reference — `class` is the only correct choice.
- Why not `record class`. Records inject `Equals`/`GetHashCode` that compare every field; two goals with coincidentally identical PCs/status would compare equal — a correctness bug at the scheduler/trail level.
- Why not `struct`/`record struct`. Structs are copied on assignment; `goalState.Pc = newPc` on a struct copy mutates the copy, not the canonical scheduler-owned state — a correctness bug in the mutator surface.
- Init-only-vs-set-properties. Dart `final` -> C# `{ get; }` (init-only via ctor, conservative form); Dart mutable -> `{ get; set; }`. The C# 9 init-only `{ get; init; }` is acceptable but unnecessary here.
- Default-empty-map idiom. The constructor's `sigmaHat ?? new SigmaHat()` is the documented Dart idiom for 'optional collection arg; default to a fresh empty one' — preserves non-aliasing across instances; the .NET port keeps the explicit null-coalesce.
- Decision. `public class GoalState { … }` with init-only and mutable auto-properties and an explicit constructor that null-coalesces `sigmaHat`. Authoritative; no escalation.

### rf-dart-named-required-ctor-with-defaults-to-csharp-positional-ctor-with-defaults — GoalState ctor

- Deep analysis. Dart 'named-only constructor with `required` on some args and defaults on others' is a call-site readability/refactor feature; semantically it is just non-optional vs optional with default. The conversion target preserves the parameter list shape (non-optional first, optional with defaults next) and lets the caller use named-argument syntax at the call site (`new GoalState(goalId: …, pc: …, kappa: …)`).
- Authoritative .NET. The C# 'Named and optional arguments' doc (https://learn.microsoft.com/dotnet/csharp/programming-guide/classes-and-structs/named-and-optional-arguments) documents both features and confirms named-argument call-site syntax is fully supported on positional ctors. C# 11's `required` modifier on properties (https://learn.microsoft.com/dotnet/csharp/language-reference/proposals/csharp-11.0/required-members) is REJECTED here because it requires the caller to use object-initialiser syntax, which the surrounding runtime port does not; consistency favours the constructor form.
- Decision. Positional ctor with named-argument call-site convention; defaults preserved verbatim; null-coalesce on `sigmaHat` preserved in the body. Authoritative; no escalation.

### rf-dart-queuelist-fifo-only-to-csharp-queue — GoalQueue

- Deep analysis. `QueueList<T>` from `package:collection` is a deque (List + Queue interfaces); this file uses ONLY the FIFO subset (`add` tail / `removeFirst` head / `isEmpty` / `length` / `Iterable` view). No tail-removal, no head-insertion, no random-access indexing.
- Authoritative .NET. https://learn.microsoft.com/dotnet/api/system.collections.generic.queue-1 documents `Queue<T>` as the FIFO collection with `Enqueue` / `Dequeue` / `Peek` / `Count` / `Clear` / IEnumerable iteration. Direct match for the FIFO subset used.
- Authoritative Dart. https://api.flutter.dev/flutter/package-collection_collection/QueueList-class.html documents `QueueList<E>` as 'A class that efficiently implements both `Queue` and `List`.' — confirming it is a deque, and that the FIFO subset is a strict subset.
- Why not `LinkedList<T>`. .NET's deque — larger surface than the source uses; introducing it would over-translate.
- Why not `ConcurrentQueue<T>`. The source is single-threaded; concurrent queue has snapshot-iteration semantics that differ subtly and pays unmotivated synchronisation cost.
- Nullable-on-empty. Dart `dequeue()` returns `null` on empty; `.NET Queue<T>.Dequeue` throws — so the wrapper MUST guard with `Count == 0 ? null : _q.Dequeue()` (preserved verbatim). Alternative `TryDequeue(out T result)` is semantically equivalent but the explicit `?` form mirrors the Dart shape; either is acceptable to codegen.
- Decision. `private readonly Queue<GoalRef> _q = new();` with the surface mapped above. Authoritative; no escalation.

### rf-dart-package-collection-queuelist-to-csharp-bcl-queue — dependency reduction

- Deep analysis. The Dart `package:collection` dependency is satisfied for THIS file's needs by the .NET BCL — no NuGet equivalent is needed. The `QueueList` import is REPLACED, not ported as a separate library.
- Authoritative .NET. `System.Collections.Generic.Queue<T>` is part of the BCL (System.Collections, https://learn.microsoft.com/dotnet/api/system.collections.generic.queue-1) — zero additional dependency.
- Decision. `using System.Collections.Generic;` — no NuGet package added. Authoritative; no escalation.

## Notes — well-known nuances explicitly addressed (FR-009 / US2 AS4)

- **Mutable state container vs record/struct/record-struct**: LOAD-BEARING. Two reference classes (`GoalState`, `GoalQueue`) and ONE value-type record-struct (`GoalRef`). The decision rule is documented per construct: identity-equal + mutable + held-by-reference -> `class`; immutable + value-equal + 2 ints in hot paths -> `readonly record struct`. NEVER `record` for `GoalState`/`GoalQueue` (would inject value equality and break scheduler identity); NEVER `struct` for `GoalState`/`GoalQueue` (would copy on assignment and break mutation propagation).
- **Reference identity** for `GoalState` and `GoalQueue` is the only equality semantics the source has (no `==` override); preserved verbatim. `GoalRef` (the sole value-equal class) is the explicit exception and gets the value-type treatment.
- **Aggregation of mutable sub-components**: `GoalState` aggregates a `SigmaHat` (Dictionary<int, object?>) — both the outer state and the inner dictionary are reference types in .NET; the outer-being-reference ensures the same dictionary instance is shared across all holders of the `GoalState` reference, mirroring the Dart semantics. `GoalQueue` aggregates a `Queue<GoalRef>` — value-type elements inside a reference-type container; `Dequeue()` returns a value-type copy (semantically equivalent to Dart's by-value return of an `int`-pair-record with value equality).
- **Trail / choice-points / WAM-style backtracking**: ABSENT from this file. `GoalState` does NOT carry a trail or choice-point chain — the runtime spec keeps those structures in the runner/heap-FCP layer, NOT here. The .NET port MUST NOT introduce trail/choice-point fields here — doing so would over-translate. Correctly not asserted (FR-009: address the nuances that exist, do not invent translations for shapes the source does not contain).
- **Null-safety**: `final Object? program` -> `object? Program { get; }` (nullable reference under enabled NRT); `SigmaHat? sigmaHat` ctor param + null-coalesce -> nullable parameter + default-empty-map; `Dequeue()` -> `GoalRef?` (Nullable<GoalRef> on a value-type record-struct); every other field/param is non-nullable. The 'nullable' annotations come straight from the Dart source's `?` markers — no invented nullability.
- **Concurrency model**: this file is single-threaded — no isolates, no locks, no async, no Future/Stream/Completer. The .NET port MUST use non-concurrent `Dictionary<K,V>` and `Queue<T>`, NOT `ConcurrentDictionary` / `ConcurrentQueue`. The single-owning-context invariant is enforced by the surrounding runtime (one goal-execution context per `GoalState`); silently upgrading to concurrent collections would advertise a safety property the surrounding logic does not need and would change snapshot/iteration semantics.
- **Async / Stream / IAsyncEnumerable / Future / Completer / Task / TaskCompletionSource**: ABSENT. No `async`, no `await`, no `Future`, no `Stream`. All members are synchronous. The .NET port MUST NOT introduce `Task` / `async` / `Channel<T>` / `IAsyncEnumerable` here.
- **Mixin / sealed**: ABSENT. The Dart classes are plain (no `mixin`, no `sealed`); the C# classes are plain (no `sealed`, no abstract); correctly not asserted.
- **Identifier casing**: Dart `camelCase` field/method names (`goalId`, `tailBudget`, `sigmaHat`, `enqueue`, `dequeue`, `isEmpty`, `items`) become `PascalCase` public members per the .NET capitalisation guideline (https://learn.microsoft.com/dotnet/standard/design-guidelines/capitalization-conventions); private fields stay underscore-prefixed camelCase (`_q`).
- **Top-level binding rehoming**: Dart permits library-level `const`/`typedef`/`enum`/`class` declarations side by side; C# requires top-level entities to be types. The free `const int tailRecursionBudgetInit` is rehomed into `MachineStateConstants`; the `typedef`s are rehomed into `global using` aliases; the `enum` and `class`es become normal namespace-scoped types — load-bearing rehoming, recorded so the codegen stage does not re-derive.
- **Zero escalations**: every non-trivial construct in this file is resolvable from authoritative Dart and .NET official documentation. The mutable state container, reference identity, value-type record-struct, default-empty-map idiom, FIFO subset of a deque, top-level-binding rehoming, and the nullable-on-empty contract are all authoritatively decidable; no `kind: undecidable` here (FR-013).
